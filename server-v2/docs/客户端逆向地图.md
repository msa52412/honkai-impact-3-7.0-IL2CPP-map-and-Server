## 0. 三十秒结论

| 问题 | 答案 |
|---|---|
| 客户端逻辑在哪 | `UserAssembly.dll`（190 MB，IL2CPP 编译的 C# 代码） |
| 代码可反汇编吗 | **可以**。`il2cpp` 节是标准明文 x64 机器码，capstone 直接吃 |
| 那为什么难 | **名字全在 `global-metadata.dat` 里，而它的 identifier 表被加密了** |
| metadata 全加密吗 | **没有**。只加密了「头部字段区 + identifier 字符串表」；**stringLiteral 表（60 万条代码字面量）是明文** |
| 资源可改吗 | 不可。`.wmv` 文件名 == 内容 md5（实测 3/3），改一字节 → `errorCode=10014` 并删文件 |
| 完整性清单 | `pkg_version`：186 条 JSONL（md5+size），**覆盖 global-metadata.dat 和 UserAssembly.dll 本身** |
| 反作弊 | 腾讯 ACE：内核驱动（ACE-DRV64.dll）+ 全模块 `.ace`/`.tvm0` 虚拟化节。私服环境下未激活 |
| 最有价值的突破 | **明文 stringLiteral 表**：客户端 UI 路径、本地化 key、1761 张数值表绑定全在里面 |

## 1. 运行时模块地图

```
BH3.exe            648 KB   7 个 .ace 节 —— 壳层启动器，本体基本全被 ACE 虚拟化
BH3Base.dll         27 MB   miHoYo 自家库：资源加载/解密/校验（.xmf、.wmv、md5 检查都在这层）
UnityPlayer.dll     28 MB   Unity 运行时（带 .tvm0 虚拟化节 —— 连引擎都被改过）
UserAssembly.dll   191 MB   IL2CPP 编译的游戏 C# 代码 ← 一切玩法的真身
global-metadata.dat 56 MB   IL2CPP 元数据（类型/方法/字段名）
ACE-DRV64.dll       17 MB   ACE 内核驱动（私服未加载）
ACE-Trace.dll      2.4 MB   ACE 跟踪组件
```

**保护特征普查**（pefile 实测节区名）：

| 模块 | 可疑节区 |
|---|---|
| BH3.exe | `.ace ×7`（整个文件没有正常节名） |
| BH3Base.dll | `.tvm0`、`.ace`、`.idata2`、`.reloc ×2` |
| UnityPlayer.dll | `.tvm0` |
| UserAssembly.dll | `.tvm0`（11.3 MB）、`.edata2`、`.reloc ×2` |

`.tvm0` = Tencent VM 0，ACE 的代码虚拟机节。`.reloc` 出现两次且大小完全相同（0x394480）
是保护壳重排节区的典型痕迹。**被搬进 `.tvm0` 的函数**（大概率是 metadata 解密、
hash 校验、.wmv 解包这类关键路径）静态分析成本等于重写一个虚拟机解释器。

## 2. IL2CPP 实测结构

### 2.1 UserAssembly.dll

```
Machine      0x8664 (x64)          构建时间 2023-10-18 03:22
SizeOfImage 187.7 MB
.text   0x1000      5.2 MB   入口点 0x4FF2E4 在这
il2cpp  0x52E000  103.2 MB   ★ 游戏代码本体
.rdata  0x6C56000  32.7 MB   只读数据（vtable、字符串池）
.data   0x8D0A000  17.5 MB
.pdata  0x9E85000  10.7 MB   异常目录
.tvm0   0xACD9000  11.3 MB   ★ ACE 虚拟化代码
```

**`il2cpp` 节抽查（capstone 反汇编 3 个采样点）——全部是正常明文机器码：**

```
0x18052f000: mov rsi, qword ptr [rbx + 0x48]
0x18052f004: mov rax, qword ptr [rip + 0x956a485]   ← il2cpp 静态字段访问模式
0x18052f00e: cmp byte ptr [rdi + 0x136], 0           ← 类初始化检查模式
0x18052f015: jne 0x18052f01f
0x18052f01a: call 0x18043e4c0                        ← il2cpp_runtime_class_init
```

这些是**教科书级的 IL2CPP 代码模式**。结论：游戏代码本体没有虚拟化，
问题只有一个——**没有名字**。所有函数地址 → 类名/方法名的映射在 metadata 里，而它被加密了。

### 2.2 global-metadata.dat（56.4 MB）—— 分区地图

魔数实测 `4d485900` = **`MHY\0`**（标准应为 `0xFAB11BAF`）。文件头 16 字节后全是高熵。

**熵扫描（4 KB 分块，脚本 `metadata_entropy_map.py`）**：

| 区间 | 大小 | 熵 | 判明内容 |
|---|---|---|---|
| 0 ~ 0.32 MB | 0.32 MB | 低 | **明文 int32 索引表**（`9b ee 02 00` 大量重复——不是加密，是查表数据） |
| 0.32 ~ 5.6 MB | 5.1 MB | 高 | 加密区 |
| 5.6 ~ 11.3 MB | 5.7 MB | 低 | 结构表（方法/类型定义，二进制但未加密） |
| 11.3 ~ 15.5 MB | 4.0 MB | 高 | 加密区 |
| 15.5 ~ 16.4 MB | 0.9 MB | 低 | 结构表 |
| 16.4 ~ 29.5 MB | 12.5 MB | 高 | **identifier 字符串表（加密）** |
| **29.5 ~ 32.3 MB** | 2.8 MB | 低/中 | **★ stringLiteral 表（明文！）** |
| 32.3 ~ 56.2 MB | 24 MB | 高 | 加密区/结构表混杂 |

**决定性证据（直接搜字符串）**：

| 探针 | 命中 | 说明 |
|---|---|---|
| `UltraEndlessPreparePageContext` | **0** | 类名 → identifier 表加密 |
| `GetMainData`、`MonoBehaviour`、`MoveNext`、`.ctor`、`Awake` | **0** | 同上（任何 IL2CPP 程序这些必然出现几万次） |
| `UI/Menus/Page/SinDemonEx/SinDemonExLevelPrepareInfoPanel` | **命中** | 代码字面量 → stringLiteral 表明文 |
| `_ExcelOutputAsset/OWEndlessSchedule` | **命中** | 同上 |
| `UnityEngine`、`mscorlib` | 1~2 次 | 出现在字面量区，非 identifier 表 |

**XOR 检测**（`metadata_xor_detect.py`）：对 5 个高熵区做单字节 XOR 全枚举 + 33 以内
密钥长度自相关，**没有找到短密钥 XOR 特征**（最优可打印率 0.63 出现在结构表区，
是二进制结构的自然属性）。加密大概率是流密码/分组密码，密钥在 UserAssembly.dll 的
`.tvm0` 虚拟化代码里（也就是最难啃的那块）。

### 2.3 这意味着什么

- **Il2CppDumper 直接用不了**：它需要明文头部 + identifier 表，两者都被加密。
- **但反汇编一直可用**：103 MB 明文机器码 + `.pdata`（10.7 MB）完整异常表，
  函数边界、调用关系、类初始化模式都能静态读。
- **结合服务端日志可以给函数"起名"**：客户端行为（`ClientReport | PlayerLog` 页面流、
  协议时序）+ 协议字段名（我们服务端已有全部 proto）足够把关键函数人工标注出来。
  这正是本项目一直在走的路线，成本可控。

## 3. 资源加密与校验链（由外到内四道）

### 3.1 `pkg_version` —— 启动完整性清单

```
{"remoteName": "BH3.exe", "md5": "1DB7...", "fileSize": 648848}
{"remoteName": "BH3_Data/Managed/Metadata/global-metadata.dat", "md5": "1002...", "fileSize": 56440956}
{"remoteName": "BH3_Data/Native/UserAssembly.dll", "md5": "2DB6...", "fileSize": 190867608}
```

186 条 JSONL。**核心二进制本体全部被 md5 钉死**。改 global-metadata.dat / UserAssembly.dll
中的任何一个字节，理论上都会在更新校验时被发现（启动器在线校验；私服直连时
未观察到强制校验，但没有做过完整实验，不要赌）。

### 3.2 `blockVerifiedVersion.txt` —— 资源版本钉

客户端字面量里实测存在 `blockVerifiedVersion.txt` 字符串。内容 `7_0_0_0`（7 字节无换行）。
它标记「资源块已通过校验的版本」。我们此前实测：**篡改 .wmv 后必须写回这个文件
+ 还原 .orig 才能恢复**，说明客户端按它决定要不要重查资源。

### 3.3 `.xmf` 清单 —— 明文结构 + 哈希资源名

```
Blocks.xmf       9,427,457 B   md5=7b6c1684166ba596b294a2fcd0adc879
Blocks_7_0.xmf   9,427,457 B   md5 同上（两文件字节级相同！）
BlockMeta.xmf       14,121 B
```

魔数 `93 7e 80 4a fe 1a b3 4d 3b 0d 9d 5f 0d 06 00 99`（3 个文件相同）。
清单本身**未加密**，能直接读到条目（`<u32 长度><hash>_<hash>.unity3d` 形式，
如 `4676398602449833006_4414169444065922392.unity3d`）。
**墙在资源名**：名字是两条长哈希拼的，不是可读路径。想定位「WorldMap 表对应哪个 bundle」，
要么逆出客户端的路径→哈希函数（在 BH3Base.dll，部分被 .tvm0 虚拟化），要么暴力建
「资源名→内容特征」的反查库。

### 3.4 `.wmv` 归档 —— 文件名 == 内容 md5（三道墙里最硬的）

实测 3/3：

```
01a54dda1864daa4ad900b4ecc98a026.wmv  内容 md5 = 01a54dda1864daa4ad900b4ecc98a026  ✓
040f64d0c6c4d34d43e01522bead132b.wmv  内容 md5 = 040f64d0c6c4d34d43e01522bead132b  ✓
10d8f3adca3f6d9c0c321cbcf89c72b0.wmv  内容 md5 = 10d8f3adca3f6d9c0c321cbcf89c72b0  ✓
```

444 个 .wmv 共 17 GB，全部是「多 bundle 拼接归档」。**文件名即校验值**：
改任何一个字节，内容 md5 变了 → 文件名对不上 → `errorCode=10014`，客户端直接把文件删掉
（此前实验实测）。而且改内容还必须改文件名 → `.xmf` 清单里的名字也要对应改 →
清单本身如果也被 pkg_version 钉死就死循环。

**结论不变：不能原地改 bundle。** 唯一理论出路是运行时 hook（见 §5）。

## 4. 反作弊与保护壳

| 层 | 机制 | 私服下状态 |
|---|---|---|
| 文件层 | pkg_version 186 条 md5 | 启动器在线校验，直连时未观察到强制执行 |
| 资源层 | .wmv 文件名==内容md5 + blockVerifiedVersion.txt | **强制执行**（errorCode=10014 实测） |
| 代码层 | .tvm0 虚拟化（关键函数搬进 VM） | 常驻（这些代码跑不了就是跑不了） |
| 进程层 | ACE 用户态（ACE-Trace.dll） | 未加载（dispatch 没下发反作弊指令） |
| 内核层 | ACE-DRV64.sys 驱动 | 未加载 |

值得注意：**反作弊是「服务器下发才激活」的模型**——私服的 dispatch/gateway 由我们控制，
所以 ACE 一直没起来。这也意味着私服环境里理论上可以 attach 调试器（未验证，
不排除 BH3Base.dll 有本地反调试；.tvm0 里常驻的代码可能自带完整性自检）。

## 8. 「破开加密 → 理清逻辑 → 更改」可行性评估（2026-10-22 12:40）

### 8.1 破开加密：可行（把握 90%+），但路线是「等它自己解密」，不是「破密码学」

关键事实链（全部当日实测）：

1. identifier 表的加密是**流/分组密码**，密钥在 `.tvm0` 虚拟化代码里 → 静态破密不可行，**也不必要**。
2. IL2CPP 运行时启动时**必须**把 metadata 解密到内存里才能工作（否则反射、类型系统全瘫）。
3. **反作弊是「服务器下发才激活」的模型**，私服下 ACE 内核驱动未加载 → 进程没有内核层保护。
4. **外部进程枚举+读取另一进程内存，实测可行**（`_ext/re/mem_scan.py`，OpenProcess(VmRead)
   + VirtualQueryEx + ReadProcessMemory，只读、零注入，已用标记字符串进程全链路验证：2008 次命中、地址正确）。

剩下的唯一未知：解密后的 metadata 在内存中的**布局**（是标准 v24/v27 结构还是 mihoyo 改过的布局），
以及 BH3Base.dll 有没有用户态反调试。这两点都能用同一个扫描器一锤定音：

> **用户把客户端跑到主界面，我跑 `mem_scan.py` 扫 BH3.exe 进程，
> 若 `UltraEndlessPreparePageContext` / `MonoBehaviour` / `std_magic` 命中 → 路线成立，
> dump 出来直接喂 Il2CppDumper（或自己解析）。5 分钟出结论。**

### 8.2 理清完整逻辑：可行，分两档

| 档 | 内容 | 前置 | 成本 |
|---|---|---|---|
| 定向逻辑 | 深渊入口判定、赛程开启条件、10014 检查位置、WorldMap 卡片渲染 | 8.1 的 dump | **数天**（dump.cs 里 grep + IDA 定位几个函数） |
| 全量逻辑 | 客户端全部玩法流程 | 同上 + 大量人工 | 数月，无必要 |

`.tvm0` 里 11.3 MB 虚拟化代码永远是黑盒，但那是加载器/校验层；
玩法逻辑本体（103 MB 明文机器码 + 10.7 MB .pdata 完整异常表）拿到名字后**全部可读**。

### 8.3 更改：分三档，各有一票

| 档 | 做法 | 可行性 | 依据 |
|---|---|---|---|
| **服务端驱动**（现路线） | 不改客户端字节，改喂的数据（WorldMapLists / 赛程 / 等级锁 / EndlessStatus） | **已验证可行** | 挑战页卡片、深渊状态全由服务端下发决定；客户端 26 张 OWEndless 表绑定健在 |
| **运行时内存补丁** | WriteProcessMemory NOP 掉 `.wmv` md5 检查 / hook 资源加载 | **中高** | 依赖 8.2 先定位函数；ACE 未激活，用户态补丁无内核对抗；不需要注入 DLL（外部改写即可，比注入少一半检测面） |
| **静态改文件** | 改 .wmv / metadata / 二进制 | **不可行** | 三道校验钉死：pkg_version 186 条 md5（含 metadata 本体）+ `.wmv` 文件名==内容md5 + `.xmf` 哈希资源名 + blockVerifiedVersion 版本钉。改一字节 → 10014 + 删文件（已实测） |

### 8.4 结论与第一刀
