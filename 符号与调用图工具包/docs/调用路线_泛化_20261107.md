# 调用路线：从方法表到「能调」

日期：2026-11-07　背景：主界面换角色成功后，把这套流程抽象成可复用路线。

这个方法解决的核心问题是：**符号表告诉你函数在哪，但不告诉你它要什么、怎么拿到
参数、能不能安全调**。下面这套六步法是从「换角色」那一次完整过程里提炼的，每一步
都对应一类会让人白白崩掉游戏（或静默得出错误结果）的坑。

---

## 1. 六步法

```
① 定位     功能关键字 → 方法表 → 类::方法
② 校验     RVA 是函数入口？是折叠桩？是 IFix 壳？
③ 读实现   反汇编主路径 → 要不要 this？this 在哪个寄存器？
④ 拿实例   静态访问器 → 全局槽 → 五跳链；或从场景对象 GetComponent
⑤ 定类型   参数按简写表装箱；返回值判 sret
⑥ 验证     先调只读 getter 交叉印证，再调写操作
```

### 每一步的判据

| 步 | 判据 | 做错会怎样 |
|---|---|---|
| ① | `route.py --search` 或 `awk` 按类/关键字 | 认错同名方法（`get_position` 有几十个） |
| ② | `is_fn_entry` / `aliasOf` / `IsPatched` | 跳半截函数 → 进程静默消失 |
| ③ | 主路径是否读 this、读哪个寄存器 | sret 方法把 `rcx` 当 this → 写穿对象头 |
| ④ | 是否有 `[rip+slot]` 全局链 | 去猜 `Find(路径)` + 组件类名，绕一大圈且易崩 |
| ⑤ | 简写类型表 + 字节数 | float 按 double 传 → 静默得 `0.0f` |
| ⑥ | 先只读后写 | 拿不确定的指针直接调 → AV |

## 2. 两个工具

### 2.1 `rea/_rea/route.py` —— 一条命令给方案

```bash
python rea/_rea/route.py "GalTouchModule::ChangeMainPageAvatar"
python rea/_rea/route.py 0x14A35E0                 # 按 RVA
python rea/_rea/route.py --search "MainPageAvatar" # 模糊找
```

输出四块：签名与模块、实现特征、全局槽、调用模板。实测三个典型：

**A. 静态访问器**（`BaseMonoUIAvatar::get_galTouchModule`）

```
IFix   是（patch id = 0x8197）
this   不需要 —— 保存了 rcx 但从未使用，是静态访问器（可从 [rip+slot] 直接起链）
静态全局槽：该类单例就在这里，可直接起链
  槽 RVA 0x9aa3488   （在 0x3082e37 处被引用）
```

**B. 需要 this 的普通方法**（`get_MainPageGalTouchAvatarID`）

```
this   需要 —— 证据：把 this 传出给 0x1814a6900 @0x1814a68ba
```

**C. sret 方法**（`Transform::get_position`，返回 Vector3）

```
this   需要 —— 证据：把 this 传出给 qword ptr [rip + 0x30bfc13]
返回 -> --ret vec3   （12 字节 -> sret，走 call_struct）
```

### 2.2 `rea/_rea/mgr.py` —— manager 槽的发现与获取

```bash
python rea/_rea/mgr.py scan          # 离线扫代码段，列候选全局槽
python rea/_rea/mgr.py probe         # 在线逐个走链验证，写 bh3_mgr_slots.tsv
python rea/_rea/mgr.py table         # 看已确认的槽表
python rea/_rea/mgr.py get 0x9aa3488 # 取实例（走链 + 类名自校验）
python rea/_rea/mgr.py fields 0x9aa3488  # dump 实例前 0x100 字节
```

`scan` 的判据：代码段里 `REX.W 8B /r [rip+disp32]` 且目标落在**可写段**（`.data`）。
本作有 260,311 个这样的位置 —— 绝大多数是普通静态字段。`probe` 用两道过滤收敛：

1. 先把 `.data` 整段（17.5 MB）读进本地，用 numpy 一次取出所有槽的 `G0`，
   只留下「像堆指针」的（`0x10000 < v < 0x7FF000000000` 且 8 字节对齐）；
2. 再对剩下的逐个走五跳链，类名读得出来且首字符是字母才算数。

已验证的两个槽是内置的，`probe` 没跑过也能用：

| 槽 RVA | 模块 | 出处 |
|---|---|---|
| `0x9AA3488` | `GalTouchModule` | `BaseMonoUIAvatar::get_galTouchModule` 主路径 |
| `0x9A988C8` | `AvatarModule` | `NewbieDialogContext::ReplaceGalTouchAvatar` 主路径 |

## 3. manager 单例：本引擎的通用形状

所有 manager 的取法都长这样（不是猜的，是从两个互不相关的方法里反汇编出来的同一形状）：

```
G0   = *(base + slot)        ; .data 段，每个 manager 一个全局槽
k1   = *(G0)                 ; klass；+0x136 是 class-init 标志，为 0 时要先 call Init
B    = *(k1 + 0x90); k2 = *(B)
inst = *(*(k2 + 0x28))
```

反汇编里的判据串：

```asm
mov rax, [rip + X]          ; X 就是 slot
mov rbx, [rax]
cmp byte [rbx + 0x136], 0
mov rax, [rbx + 0x90]
mov rbx, [rax]
mov rax, [rbx + 0x28]
mov rcx, [rax]
test rcx, rcx
```

看到这一串，`slot = 该指令末尾 + X`。

**为什么这条比「找组件」好**：`get_galTouchModule` 名义上是 `BaseMonoUIAvatar` 的
成员方法（`isStatic=0`），但它的主执行路径**一次都没读 this** —— 它直接走全局链。
也就是说拿 manager 根本不需要任何场景对象、不需要 `GetComponent`、
更不需要会崩的反射。

## 4. 判定「this 在哪」

这是最容易错的一步，因为它有四种情况：

| 情况 | this 在 | 判断依据 |
|---|---|---|
| 普通实例方法 | `rcx` | 反汇编里 `[rcx+disp]` 或 `mov rbx,rcx` 后被使用 |
| **sret**（返回值 >8 字节） | **`rdx`** | 返回类型是 `Vector3/Vector4/Quaternion/Color/Rect/Bounds` |
| 静态方法 / 静态访问器 | 无 | 保存了 rcx 但从未使用 |
| 静态方法带参数 | 无 | 第一个参数就从 `rcx` 开始 |

### 判断「保存了但没用」

`mov rbx, rcx` 出现得很频繁，**但保存不等于使用**。正确做法是追踪那个寄存器，
在它被覆盖之前有没有被用过：

- `BaseMonoUIAvatar::get_galTouchModule`：`mov rbx,rcx` 之后 rbx 立刻被
  `mov rbx,[rax]`（全局链的值）覆盖 → **this 未使用**
- `GalTouchModule::get_MainPageGalTouchAvatarID`：`mov rcx,rbx; call get_...Info`
  → **this 被传出**

`sret` 的情况还要注意：把 this 搬回调用约定时用的是 **`rcx`**，不是 `rdx`
（`mov rcx, rax; call`）—— 因为 call 的第一个参数永远在 rcx。

### 主路径 vs patch 分支

IFix 壳里，`jne <patch_branch>` 之后才是 patch 分支，那里面才用 this 调 wrapper。
**必须在主路径范围内判定**，否则 `get_galTouchModule` 会被误判成「需要 this」。
`route.py` 的 `split_main_path()` 就是干这个的。

## 5. 完整案例复盘：主界面换角色

| 步 | 实际做法 | 结果 |
|---|---|---|
| ① 定位 | `grep -iE "gal\|talk"` 类名 → `GalTouchModule` | `ChangeMainPageAvatar` @`0x14A35E0` |
| ② 校验 | `is_fn_entry` 通过；无 aliasOf；IFix patch `0x8244` | 可调，但真逻辑读不出 |
| ③ 读实现 | `callers.py who 0x14A35E0` 反查到 `NewbieDialogContext::ReplaceGalTouchAvatar` | 看到 `xor r8d,r8d` → `touchType=0` 是代码事实 |
| ④ 拿实例 | 反汇编 `ReplaceGalTouchAvatar` 发现全局槽 `0x9A988C8`；`get_galTouchModule` 发现 `0x9AA3488` | 五跳链，零调用拿到 `GalTouchModule` |
| ⑤ 定类型 | `(int, GalTouchType, bool)` → `int,int,int`；返回 bool → `& 0xFF` | 注意 `CanChange` 返回 `True` 时 rax=`0xFFFFFF01` |
| ⑥ 验证 | 先 `get_MainPageGalTouchAvatarID` 对照内存读；再 `CanChange` 预检；最后 `Change` | 507 → 101 → 301 全部成功 |

关键的一条：`ChangeMainPageAvatar` 最后走
`NetworkManager::RequestSetWarshipAvatar` —— **换角色本质是服务器请求**，
本地硬改显示存不下来。所以路线里第 ⑥ 步的「先只读后写」不只是为了安全，
也是为了先确认语义再动真格。

## 6. 这套路线的边界

**能做**：
- 调任意函数入口，只要参数能装箱（整数/浮点/字符串/对象指针/枚举）
- 从任意全局槽拿单例
- sret 结构体返回（`Vector3/Vector4/Quaternion/Color/Rect/Bounds`）
- 读任意内存、走任意指针链

**做不了**（架构级限制，不是待办）：
- **会抛托管异常的方法**：反射（`Type::GetType`、`MethodInfo::Invoke`）、
  字符串解析（`Convert::ToInt32`）、越界访问、`Activator::CreateInstance`。
  托管异常要沿 native 栈找 il2cpp 的 catch 帧，而 stub 是直接 `call` 进去的，
  栈上没有那样的帧 → 进程 abort。
- **>8 字节结构体按值传参**：需要手动 marshalling，没有自动装箱。
- **泛型方法**：缺 MethodInfo，无法实例化。
- **字符串长期持有**：`S()` 造的是借用对象，不在 GC 堆上。

**已知校验缺口**：
- `route.py` 的 this 判定基于前 60 条指令，超长函数的尾部分支可能漏判；
- `mgr.py probe` 只覆盖「通过 `mov reg,[rip+slot]` 取槽」的 manager，
  如果某个 manager 用 `lea` 或经过函数返回值，会漏。
