## 0 三句话结论

> 本节结论在 2026-10-21 晚经过三轮实测修订。原判断「补 handler 就行」已被推翻，原因见 §6.3–6.5 与 §9。

1. **迪拉克之海的协议是活的，但界面开不出来**。客户端确实会发 `GetOpenworldEndlessDataReq`（实测 14 次，
   切 `selected_endless_type=2` 后立刻发 `type=2`），协议层零缺失；
   但**入口卡片出不来** —— 它由客户端加密 ASB 里的 prefab + 客户端表决定，服务端改任何数据都点不亮。
   补 45 个 handler 只会得到「有数据、没入口」。
2. **量子奇点没有独立界面**。它没有独立协议族（走同一个 `GetOpenworldEndlessDataReq` 的 `type=3`），
   也没有独立 UI（metadata 里 `QTEndless` 只剩 3 个表名串、UI prefab 0 个）。
   只能作为迪拉克之海界面里的一个难度分支，不会有独立入口。
3. **超弦空间是"能进但打不了"**。4 个 handler 全是假数据（`ScheduleId=1028`、
   `CupNum=2000`、`MaxScore=0`、`IsUpFloor=false`），界面能开、楼层永远不晋级。
   **这是当前唯一值得投入的方向**（§10.4）。

## 1 四套深渊在协议里的关系

深渊不是一个玩法，是**一个协议族 + 一个 type 字段**的四套皮。CmdId 分布：

| 体系 | 协议族 | CmdId 范围 | 主入口 | type 值 |
|---|---|---|---|---|
| 超弦空间 | `UltraEndless*` | 5200–5299 | `UltraEndlessGetMainDataReq` (5202) | 独立协议，不用 type |
| 迪拉克之海 | `(Get)OpenworldEndless*` | 3419–3451 | `GetOpenworldEndlessDataReq` (3419) | `ENDLESS_TYPE_OPENWORLD = 2` |
| 量子奇点 | 同上（无独立族） | 同上 | 同一个 3419 | `ENDLESS_TYPE_QUANTUM = 3` |
| 贪婪深渊 | `GreedyEndless*` | 3453–3465 | `GreedyEndlessEnrollReq` (3453) | `ENDLESS_TYPE_GREEDY = 5` |
| 前哨无尽 | `FrontEndless*` | 4064–4066 | `FrontEndlessActivityBattleBeginReq` | `ENDLESS_TYPE_FRONT = 6` |

中立件（四套共用）：

- `GetEndlessStatusReq` (3432) —— **总开关**。响应里的 `selected_endless_type` 告诉客户端
  "现在主推哪一套"，客户端据此去拉对应玩法的数据和排行。
- `EndlessSelectTypeReq` (3462) —— 玩家主动切换。**7.0 客户端一次都没发过**（说明界面上没给切入口）。
- `EndlessType` 枚举：`None=0, Normal=1, Openworld=2, Quantum=3, Ultra=4, Greedy=5, Front=6`。

关键结构（`GetOpenworldEndlessDataRsp`）一个响应同时装三种：

```
GetOpenworldEndlessDataRsp
├── type                    ← 回显请求的 type
├── group_id / group_level / begin_time / end_time / close_time
├── endless_data_list[]     ← 每个玩家一行（score / max_score / reward_progress / group_level）
├── brief_data_list[]       ← 好友简要
├── monster_group_list[]    ← 怪物组进度
├── battle_config_id        ← 指向 OWEndlessBattleConfig 表
├── quantum_endless         ← ★ 只有 type=3 才填
└── greedy_endless          ← ★ 只有 type=5 才填
```

|---|---|---|---|

**① 客户端真的进过超弦空间并打了一关**

  {"stageID":146013,"stageType":"STAGE_ULTRA_ENDLESS","endStatus":"STAGE_EXIT",...}

## 4 服务端现状：实现度

| 功能 | handler | 状态 |
|---|---|---|
| `GetEndlessStatusReq` 3432 | ✅ | 返 Ultra + selected=5（矛盾，已修，见 §5） |
| `UltraEndlessGetMainDataReq` 5202 | ✅ | **假数据**：`ScheduleId=1028`、`CupNum=2000`、`MaxScore=0` |
| `UltraEndlessEnterSiteReq` 5211 | ✅ | 回 `Succ` + SiteId，不校验 |
| `UltraEndlessReportSiteFloorReq` 5206 | ✅ | 回 `Succ`，但 `IsUpFloor=false` → **永不晋级** |
| `UltraEndlessGetTopRankReq` 5200 | ✅ | `IsFeatureClosed=true, MyRank=1, MyScore=0` |
| `GetOpenworldEndlessDataReq` 3419 | ❌ → ✅ | **本次新增**（见 §5） |
| 其余 45 个旧深渊协议 | ❌ | 全部未实现 |

`UltraEndlessGetMainDataReq` 的关键缺陷（`UltraEndlessGetMainDataReqHand.cs`）：

```csharp
ScheduleId = 1028u,          // 写死，不对应任何真实排期
CupNum = 2000u,              // 奖杯数写死
DynamicHardLevel = abyssDynamicHard,
// 每个楼层的 MaxScore 都填 0 → 客户端认为一层都没打过
MaxScore = 0u
```

`UltraEndlessReportSiteFloorReq` 的 `IsUpFloor=false` 是最要命的一条 ——
不管打多少分，楼层永远不升。所以现在是「能进图、能打完、结算没反应」。

## 5 本次改造（已落地）

### 5.1 新增 `GetOpenworldEndlessDataReq` handler

文件：`Server\Handlers\GetOpenworldEndlessDataReqHandler.cs`

做法：**按请求里的 `type` 回显一份合法数据**，先验证「界面能不能被点亮」，
真数据（排期/分组/怪物组）等界面确认后再接表。

```csharp
Packet.c.Log($"[Abyss] GetOpenworldEndlessDataReq type={(int)req.Type} level={req.Level} ...");

EndlessType type = req.Type;
if (type == EndlessType.EndlessTypeNone) type = EndlessType.EndlessTypeOpenworld;

rsp = { retcode=Succ, Type=type, GroupId=1, GroupLevel=user.AbyssGroupLevel,
        EndTime=now+604800, CloseTime=now+604800+1200,
        BattleConfigId=1001, CurTopGroupLevel=22, ... };
rsp.EndlessDataLists.Add(new OpenworldEndlessPlayer { Uid=user.Uid, GroupLevel=..., ... });
if (type == Quantum) rsp.QuantumEndless = new QuantumEndless { ... };
if (type == Greedy)  rsp.GreedyEndless  = new GreedyEndless  { ... };
```

**那行 `[Abyss]` 日志是本次最重要的观测点** —— 它会直接告出客户端在要 `type=2` 还是 `type=3`。

### 5.2 `GetEndlessStatusRsp` 去掉自相矛盾

原来 `CurStatus.EndlessType` 和 `SelectedEndlessType` 是两处硬编码、互相打架。
现在统一由 `Server\GameServer\AbyssConfig.cs` 决定：

```csharp
AbyssConfig.SelectedEndlessType = 5u;                            // 默认 = 原状
AbyssConfig.CurStatusType       = EndlessType.EndlessTypeUltra;  // 默认 = 原状
AbyssConfig.SetSelected(uint n);                                 // 0..6 自动推导 CurStatus
```

**默认值和改之前完全一致**，不改变现有行为。

### 5.3 新增热切换命令 `abyss legacy <n>`

游戏内聊天框直接输（不加斜杠）：

```
abyss legacy 2     ← 迪拉克之海
abyss legacy 3     ← 量子奇点
abyss legacy 4     ← 超弦空间（当前）
abyss legacy 5     ← 贪婪深渊（原默认）
```

热生效，不用重启。服务端日志会打 `[Abyss] SelectedEndlessType=2 CurStatus.EndlessType=2`。

`AbyssCommand` 顺手修了一个越界 bug：原代码 `args[1]` 在只输一个词时会抛
`IndexOutOfRangeException`，现在改成 `args.Length > 1` 判断 + `TryParse`。

### 6.3 第一次实测结果（2026-10-21 17:18）—— 客户端支持，但没有界面

命令热切换**生效了，而且客户端立刻跟着换**：

```
17:18:57 [Abyss] GetEndlessStatus -> SelectedEndlessType=2 CurStatus.EndlessType=2
17:18:57 [Abyss] GetOpenworldEndlessDataReq type=2 level=0 finishFront=False   ← 迪拉克之海
17:18:57 [Abyss] GetOpenworldEndlessDataReq type=2 level=0 finishFront=False
17:19:06 [Abyss] SelectedEndlessType=3 CurStatus.EndlessType=3
17:19:09 [Abyss] GetOpenworldEndlessDataReq type=3 level=0 finishFront=False   ← 量子奇点
```

**这证明客户端 100% 支持这两套旧深渊** —— 它按 `selected_endless_type` 去拉对应数据，
连 `level` 参数都带上了。协议层没有任何缺失。

但界面没变。原因从 UI 轨迹里看得很清楚：

```
13:56:47  Click .../Challenge/Task_3/Cover
          → Enter UltraEndlessPreparePageContext     ← Task_3 = 超弦空间入口
          Click .../Challenge/Task_4/Cover
          → Enter SinDemonExMainStubPageContext      ← Task_4 = 罪神EX

17:18:56  Click .../Challenge/Task_3/Cover
          → （什么页面都没打开）                      ← 切成 type=2 后，超弦页不开了，
                                                        而迪拉克之海的 Prepare 页并不存在
```

**「挑战」面板只有两张固定卡片**（Task_3 / Task_4），点位由客户端地图配置决定，
服务端改 `selected_endless_type` 改不动它。

那迪拉克之海的入口在哪？在**世界地图**上，是一张独立卡片：

```json
// run\Resources\ExcelOutputAsset\WorldMap.json
{ "EntryID": 1012, "FeatureType": [108],
  "EntryImagePath": "SpriteOutput/WorldMap/OWEndless/Cover_11",
  "UnlockLevel": 25, "UnlockHintLevel": 22, "EntryRewardID": 1224007, "ID": 15 }
```

整个 `WorldMap.json`（228 条）里，`EntryImagePath` 含 `OWEndless` 的只有 3 条：
1012（`Cover_11`，FeatureType 108）和两条 `EntryID 9999` 的占位（`Cover_8` / `Cover_12`，FeatureType 18）。

→ 所以下一步是填 `GetEndlessStatusRsp.NextStatusLists`（v2 里**一直是空的**），
看客户端会不会因为这个列表而在地图上/面板里多画一张卡。

### 6.4 第二次实测（17:26）—— NextStatusLists 也不是开关

`NextStatusLists` 填了 3 条（Openworld / Quantum / Greedy）并确认下发：

```
17:26:27 [Abyss] GetEndlessStatus -> SelectedEndlessType=5 CurStatus.EndlessType=4
17:26:27 [Abyss] NextStatusLists = 3 条
17:26:27 [Abyss] GetOpenworldEndlessDataReq type=0 level=0 finishFront=False
```

界面依然没有变化。**结论：挑战面板的卡片列表不是由 `NextStatusLists` 决定的。**

顺带一个观察：`selected=5`（贪婪）时客户端发的是 `type=0`，而 `selected=2/3` 时发 `type=2/3`。
说明 `type` 参数只承载「开放世界系」的两种，贪婪走 `greedy_endless` 子消息、不带 type。

### 6.5 真正的断点：开放世界章节没实现

回到日志里另一条被忽略的缺口：

```
OpenworldChapterGetDataReq (4565)   x33   ★未实现
OpenworldChapterGetShopDataReq (4575) x12  ★未实现
```

迪拉克之海在旧版**不是挑战面板里的独立卡片**，而是「开放世界」章节里的一个玩法。链路是：

```
WorldMap.json  EntryID 1012（SpriteOutput/WorldMap/OWEndless/Cover_11）
  └─ 进入开放世界章节  OpenworldChapterGetDataReq(mapId=?)
      └─ OpenworldChapter.EndlessChallengeLists[]
          └─ ChapterOWEndlessChallenge 表（15 条，MapID 全是 801，Group 1..5 × ChallengeID 1..15）
              └─ GetOpenworldEndlessDataReq(type=2)  ← 迪拉克之海本体
```

**客户端每次进世界地图都会发 33 次 `OpenworldChapterGetDataReq`，服务端一直没回。**
章节数据拿不到 → 开放世界进不去 → 迪拉克之海的入口自然出不来。
这比 `selected_endless_type` 和 `NextStatusLists` 都更靠前，是真正的第一道门。

已补 `Server\Handlers\OpenworldChapterGetDataReqHandler.cs`：
返回最小可用 `OpenworldChapter`，`MapId == 801` 时填 15 条 `EndlessChallengeLists`，
并打日志 `[Abyss] OpenworldChapterGetDataReq mapId=?` —— **这个 mapId 值就是下一个关键观测点**。

## 9 世界地图入口取证：为什么改服务端点不亮

这一节是 6.5 之后的新分支 —— 既然开放世界章节补了也不见效，就回头查「世界地图上的入口卡片」到底由谁决定。

### 9.1 `GetWorldMapDataRsp` 是硬编码的 protobuf blob

`Server\Handlers\GetWorldMapDataReqHandler.cs` 里那串十六进制就是整个响应的序列化结果，字段结构：

```
GetWorldMapDataRsp
  1 retcode
  2 WorldMapLists[]  ── WorldMapData: 1 WorldMapId / 2 BeginTime / 3 EndTime
                                     4 HighLightMinLevel / 5 HighLightMaxLevel
                                     6 Weight / 7 AdvanceTime / 8 Id
```

解码后只有 **16 条**，其中 15 条的 `EndTime = 2035-04-13`（长期开放），**1 条已经过期**：

| Id | WorldMapId | BeginTime | Weight | EndTime | 备注 |
|---|---|---|---|---|---|
| 385 | **2267** | 2023-05-17 | 122 | **2023-06-28** | ★ 唯一过期项 |
| 307 | 2221 | 2021-01-27 | 1 | 2035-04-13 | |
| 121 | 2107 | 2019-07-14 | 205 | 2035-04-13 | |
| 1–12 | 1–12 | 2011-03-13 | 0–1 | 2035-04-13 | 主线章节 |
| 286 | 18 | 2011-03-13 | 1 | 2035-04-13 | |

`Id` 与 `WorldMapSchedule.json` 的 `ID` 字段一一对应（2267 → ID 385），
所以这张响应的真实含义是「**哪些世界地图版本当前开放**」，而不是「哪些入口显示」。

### 9.2 入口卡片是客户端资源，不是服务端数据

`WorldMap.json`（228 条）里，迪拉克之海那条是：

```json
{ "ID": 15, "EntryID": 1012, "FeatureType": [108],
  "EntryImagePath": "SpriteOutput/WorldMap/OWEndless/Cover_11",
  "UnlockLevel": 25, "EntryRewardID": 1224007,
  "isShowActivitySchedule": false, "VersionTag": false }
```

三个决定性事实：

1. **`FeatureType=108` 全表只出现这一次** —— 它是迪拉克之海专属枚举值。
   同一批旧玩法还有 `105 → Cover_9`、`109 → Cover_10`，说明 105/108/109 是一组。
2. **`WorldMap.json` 里没有 `WorldMapID` 字段**（228 条全是 `None`）——
   入口和地图版本的关联不在服务端能改的地方。
3. **`BaseExcelReader` 只从 `Resources\ExcelOutputAsset\` 读表供服务端自己算数**：

```csharp
// Common/Common.Utils.ExcelReader/BaseExcelReader.cs:37
All = JsonConvert.DeserializeObject<Scheme[]>(
        File.ReadAllText("Resources\\ExcelOutputAsset\\" + FileName));
```

日志里 `<Factory> UltraEndlessSite Excel Loaded From UltraEndlessSite.json` 是**服务端**读表，
不是客户端拉表。客户端的表在加密的 `Asb/pc/*.wmv` 里，服务端发不下去。

**所以，改 `run\Resources\ExcelOutputAsset\WorldMap.json` 不会影响客户端显示。**
入口卡片是客户端 prefab + 客户端表共同决定的，属于服务端能力之外。

### 9.3 晚间复查：章节链路其实是通的，卡在「开放世界主页面秒退」

把 17:31–17:32 那次登录的日志逐帧重看，推翻了「客户端不调用章节 handler」的旧判断：

客户端真实请求 801/1001/701 三张章节图并全部拿到响应，**章节数据链路是通的**。
问题只剩 UI 层：PlayerLog 显示用户点了 `Attack/OpenWorld/OpenWorldBtn` 进入
`OpenWorldMainStubPageContext` 后**每次 2 秒内退出**，反复 5 次 —— 页面里的内容被判定为空。

## 10 后续路线

### 10.1 先说一个共同的坑：所有排期表都停在 2023 年

```
UltraEndlessSchedule   292 条   2020-09-15 → 2023-06-30
OWEndlessSchedule       82 条   2020-09-15 → 2022-04-01
QTEndlessSchedule      233 条   2020-09-15 → 2022-12-05
GreedyEndlessSchedule  152 条   2022-01-24 → 2023-07-07
```

现在是 2026 年 10 月，**没有任何一张表的排期覆盖今天**。

所以「接表」不是简单的 `查当前时间 → 找排期`，必须先决定时间策略，二选一：

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **按周循环**（推荐） | `index = (now - t0) / 604800 % 表长` | 不用改表，永远有排期 | 周期会重复，赛季内容原地打转 |
| 时间偏移 | 全局把 `now` 减到 2023 年再查表 | 保留真实赛季顺序 | 客户端显示的时间会穿帮 |

顺带解释了一件事：**为什么 v2 现在的 `ScheduleId=1028` 是写死的** ——

## 12 等级锁（高级区 / 终极区）—— 2026-10-22 新增

### 12.1 用户的机制假设被证据坐实

用户提出：**「80 级以上为终极区、超弦空间，需要手动开启等级锁后才能进入」**。
翻协议和配置，这个机制在代码里是**明确存在**的，只是 v2 从来没实现过。

**证据一：协议自带三个失败码**

```
SetLevelLockReq  (1488)  level_lock_id: uint
SetLevelLockRsp  (1489)  retcode: Succ / Fail / NOT_MEET_MAX_LEVEL / NOT_NEXT_ID
                         level_lock_id: uint
```

`NOT_MEET_MAX_LEVEL`（没到当前档等级上限）和 `NOT_NEXT_ID`（目标不是下一档）
这两个码不可能凭空存在 —— 它们就是「突破等级锁」这套校验的返回值。

**证据二：`PlayerLevelLock.json` 全表只有 2 行**

| LockID | MaxLevel | MaxLayUpExp | MissionList | EventID | 头像框 | TutorialVideoID |
|---|---|---|---|---|---|---|
| **1** | **80** | 25000 | **空** | 40388 | `LbFrameBlue` | 0 |
| **2** | **88** | 1000 | **45 条**（78213…78573） | 40480 | `LbFrameRed` | 20 |

即：1 = 高级区（未突破，蓝框，封顶 80）；2 = 终极区（已突破，红框，封顶 88，带突破任务和教程视频）。

**证据三：v2 的状态是自相矛盾的**

```
GetMainDataReqHandler.cs:52   getMainDataRsp.LevelLockId = 1u;   ← 硬编码「高级区」
存档                          Exp = 300257 → 88 级
```

客户端收到的组合是「**你 88 级，但你还在高级区（封顶 80）**」。
这个组合在真实游戏里不可能出现，客户端没法判断该按哪一档渲染。

**证据四：突破协议从来没被应答过**

```
grep -rn "SetLevelLock" --include=*.cs Server/   → 0 个 handler
grep -a -c "SetLevelLockReq" v2_Server.log       → 0 次
```

客户端就算想走「突破」流程，发上来的包也会被当成未知包丢掉。

### 12.2 已落地的修复

| 文件 | 改动 |
|---|---|
| `Common/Common.Utils.ExcelReader/PlayerLevelLockExcel.cs` | **新建**，映射 `PlayerLevelLock.json` |
| `Common/Common.Utils.ExcelReader/PlayerLevelLock.cs` | **新建**，`Get(id)` / `Next(id)` / `MinLockId()` / `MaxLockId()` |
| `Server/GameServer/LevelLockConfig.cs` | **新建**，`Resolve(level)` 自动推档 + `Validate()` 校验 |

**`Resolve()` 的规则**（`ForcedLockId==0` 即 Auto 时）：

从最低档往上爬，只要 `玩家等级 > 当前档 MaxLevel` 就升一档。

- 88 级 → **2（终极区）** ← 当前存档
- 80 级 → **1（高级区）**
- 79 级 → 1

这条规则的意义：**`level 80` 和 `level 88` 这两条聊天命令会自动把档位一起带过去**，
不用分别改等级和等级锁，天然自洽。

### 12.3 为什么默认是 Auto 而不是钉死 2

钉死 2 会让「降级到 80 做高级区实验」永远测不了；
钉死 1 就是原来的 bug。Auto 同时满足两种实验，且默认落在与 88 级自洽的 2 上。

要强制：`abyss lock 1` / `abyss lock 2` / `abyss lock 0`（回自动）。

### 12.4 这一步的**可观测信号**（很重要）

等级锁这条路和「深渊能不能开」是**两件事**，但它有一个**完全独立、肉眼可见**的信号：

> 登录后主界面**头像框应该从蓝框变成红框**，等级条上限从 80 变成 88，
> 首次可能播 `TutorialVideoID=20` 的突破教程视频。

- 框变红 → **客户端确实在按 `LevelLockId` 渲染**，等级锁链路通了 → 再谈深渊
- 框没变 → 客户端根本没读这个字段（或读了别的来源）→ 这条线到此为止，
  直接转去查赛程过期（§12.5）

### 12.5 顺带查到的第二个阻塞：**深渊赛程全部过期**

顺手把四套深渊的赛程表时间跨度算了一遍（`TimeStampForBakedReader`）：

| 表 | 条数 | 最早 | **最晚** |
|---|---|---|---|
| `OWEndlessSchedule.json`（迪拉克之海） | 82 | 2020-09-15 | **2022-04-01** |
| `QTEndlessSchedule.json`（量子奇点） | 233 | 2020-09-15 | **2022-12-05** |
| `UltraEndlessSchedule.json`（超弦空间） | 292 | 2020-09-15 | **2023-06-30** |
| `GreedyEndlessSchedule.json`（贪婪深渊） | 152 | 2022-01-24 | **2023-07-07** |

而**服务器系统时间是 2026-10-22**（`date` 实测）。

两件事叠在一起：

1. **所有深渊赛程都在 2022~2023 就断了**，当前时间一条都不覆盖。
2. 服务端 `UltraEndlessGetMainDataReqHand.cs:19,25` **硬编码 `ScheduleId = 1028`**，

→ 客户端拿到「赛程 1028」去查自己的表，算出来是 2020 年的场次，
配合 2026 的当前时间，**任何按时间判定的开启条件都会判成"已结束"**。
这很可能是「点 Task_3 有 12/23 次什么都不打开」的直接原因。

**注意这条和等级锁是独立的**，可以分开验证。
待做：`ScheduleId` 改成 3225、`BeginTime/EffectTime` 设成 `now-3600`、
`EndTime` 设成 `now+7d`（做法沿用 §9.4 里 2267 延 EndTime 的先例）。

## 13 迪拉克之海「模式数据」修正（2026-10-25 17:45）

### 13.1 现象与字段定位

|---|---|---|---|
| 当前所处区域（原罪/禁忌/苦痛/红莲/无限）显示为**最低** | `group_level` | `21` | 21 属于 `OWEndlessGroup` 里 **playerGroup 2** 的阶梯（21~24，只有 4 档）；界面上那 5 个段位图标 `IconGroup_3..7` 对应的是 **playerGroup 3** 的 31~35。客户端按 5 档阶梯查不到 21 → 退到第一档 → 永远「原罪」 |
| 扰动幅度为 **1** | `hard_level` | `1u` 写死 | 正确值是 `OWEndlessGroup.groupHardLevel`（35 → 7） |
| 玩家ID 显示不正常 | `brief_data_list` | **空** | 客户端渲染自己/排行那一行时拿不到昵称头像，只能退回显示裸 uid |

### 13.2 关键发现：`OWEndlessGroup` 有两条阶梯

`run\Resources\ExcelOutputAsset\OWEndlessGroup.json` 共 22 行，按 `(GroupLevel, Type)` 唯一：

```
Type=2（迪拉克之海）9 行
  playerGroup=2  21 22 23 24        扰动 2 3 4 5    icon IconGroup_3..6   （4 档）
  playerGroup=3  31 32 33 34 35     扰动 3 4 5 6 7  icon IconGroup_3..7   （5 档 ★）

Type=3（量子奇点）13 行
  playerGroup=1  11 12 13 14        扰动 1 1 2 3
  playerGroup=2  21 22 23 24        扰动 4 4 5 6
  playerGroup=3  31 32 33 34 35     扰动 7 8 9 10 11
```

**段位图标只有 `IconGroup_3..7` 五个**，所以「原罪→无限」这五档只能是 31..35 那条阶梯。
之前文档 §AbyssConfig 注释里写「mode=2 只有 21~24」是**扫表时漏了 playerGroup 3**，
这条已被推翻。

> 附：`OWEndlessGroup` 的 `Type` 就是 `EndlessType` 枚举值（Openworld=2 / Quantum=3），
> 不是另外一套编号 —— 枚举是顺序定义的，没有显式赋值。
