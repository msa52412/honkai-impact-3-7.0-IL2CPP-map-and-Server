# 通用函数调用 · 2026-11-07

> 目标：把 `icall` 从「只能调 4 个整数参数的函数」扩成「能调任意 C# 方法」。
> 全部离线完成，未启动游戏，未改任何游戏文件。

## 1. 原来卡在哪

旧 stub 只做四件事：`mov rcx/rdx/r8/r9` ← 信箱里的 4 个 qword，`call`，存 `rax`。
于是三类方法完全调不了：

| 调不了的原因 | 例子 |
|---|---|
| 有浮点参数 | `SetOWEndlessLevelScoreMode(bool,bool,string,bool)` 里的字符串、`InitBattleScorePlugin(float,float,int)` |
| 参数超过 4 个 | 5 参以上走栈，旧 stub 只 `sub rsp,0x20` 留影子空间，没写栈参数 |
| 要托管对象 | 传 `string` 必须给 `Il2CppString*`，得自己造 |

## 2. 三项扩展

### 2.1 浮点参数（xmm0-3）

Windows x64 的规则容易记错：**前 4 个参数按「位置」占槽，不是整数、浮点各数各的**。
参数 0 用槽 0（整数→rcx，浮点→xmm0），参数 1 用槽 1，依此类推。

所以 stub 不需要任何分支：无条件把 4 个整数寄存器和 4 个 xmm 全写一遍，
调用方在「该是浮点的槽」填浮点位模式、另一侧填 0 即可。

**`float` 与 `double` 必须区分**，这是最容易静默出错的地方：

```
float 1.5f   位模式 = 0x3FC00000
double 1.5   位模式 = 0x3FF8000000000000   ← 低 32 位恰好是 0
```

按 double 传一个 float 参数，被调函数用 `movss` 读低 32 位会得到 `0.0f`。
不崩、不报错，只是结果莫名其妙。因此引入 `F32` 标记类型：

```python
I.F32(1.5)   # → 0x3FC00000   正确
1.5          # → 0x3FF8...    按 double 传
```

### 2.2 栈参数（第 5~20 个）

栈参数位置必须按 callee 视角推算，不是按 caller 的：

```
call 前 rsp = R（16 对齐）
call 压返回地址 → rsp = R-8
callee 入口 [rsp+0x28] = R+0x20 = 第 5 个参数
```

所以 stub 在 `sub rsp,0x100` 之后，把第 5+i 个参数写到 `[rsp+0x20+8i]`。
影子空间 `[rsp+0x00..0x20)` 保持不动（那是 callee 的草稿纸）。

固定搬 16 个，不做数量判断 —— 多搬的写进 xmm 备份区之前的空位，无害。

### 2.3 xmm 备份（这条最容易漏）

被 hook 的函数入口处，`xmm0-3` 是**它自己的浮点参数**。stub 为了发起调用会覆盖它们，
不换回来，`orig` 那几条指令看到的就是错的浮点值。

```asm
movsd [rsp+0xA0], xmm0..xmm3    ; 进入时备份
...                              ; 发起调用，覆盖 xmm
movsd xmm0..xmm3, [rsp+0xA0]    ; 换回来
```

这类错误不崩、只算错，比崩溃难查得多，所以专门在测试里断言。

### 2.4 托管字符串

`Il2CppString` 的实际布局（不是想当然的 +0x18）：

```
+0x00  klass
+0x08  monitor
+0x10  length   int32，单位 UTF-16 码元
+0x14  chars[]  utf-16le
```

问题是要造这个对象就得知道 `System.String` 的 `Il2CppClass*`，而它只在运行时的
托管堆里 —— 静态文件拿不到（元数据加密、API 表 dump 不可用）。

解法是 **bootstrap**：调 `UnityEngine.Application::get_dataPath`（RVA `0x6AB8500`，
静态无参返回 string，随时可调），拿到返回值后读 `[ptr+0]` 就是 String klass。
再读 `klass->name`（`Il2CppClass+0x10`）验证是不是 `"String"` —— 这一步顺便
验证了 Il2CppClass 的布局假设，不是白读。

```bash
python icall.py bootstrap     # 只跑一次，klass 存进 .icall.json
```

## 3. 验证方式

不装 unicorn（本机 pip 拉不动），自己写了个只认 stub 用到的指令的解释器：
`test_icall_asm.py`。遇到不认识的助记符直接抛异常，不会「跑过去了但结果不对」。

模拟完整路径：入口 → 判魔数 → 存现场 → 搬参数 → `call`（就地扮演 target）→
回写返回值 → 还原现场 → 原始指令 → 跳回。

```
stub 476 字节，88 步执行到 jmp 回原函数处

[1] target 收到的参数
  OK rcx/rdx/r8/r9      8 个槽位全部正确
  OK xmm0..xmm3         位模式一致
  OK [rsp+0x28]..[rsp+0x40]   第 5~8 个参数
  OK callee rsp 对齐    %16 == 8

[2] 返回值回写
  OK ret_rax = 0xDEADBEEF
  OK ret_xmm0 = 2.718281828 的位模式
  OK done = 1，pending 已清零

[3] 回到原函数前，现场必须干净
  OK rsp / rbx / rbp / rcx / rdx / r8 / r9 全部还原
  OK xmm0..xmm3 全部还原成入口值
```

过程中被这套验证抓到的两个真问题：

1. **ModRM 编码方向错**：`mov r11,[rbx+8]` 被编成 `mov rbx,[r11+8]` —— ModRM 的
   `reg` 字段对应 `REX.R`（0x44），我误用了 `REX.B`。反汇编一眼看出来，实际跑
   会读任意地址。
2. **测试初值不符合 ABI**：第一次把初始 rsp 设成 16 对齐，导致 callee 的 rsp 变成
   `%16==0`。真实函数入口必然是 `%16==8`（call 压了返回地址），是测试条件错，
   不是 stub 错。

## 5. 边界（别当万能）

| 项 | 现状 | 说明 |
|---|---|---|
| 参数个数 | 20 个 | 4 寄存器 + 16 栈 |
| 浮点 | float / double 都行 | 必须用 `F32` 标明 float32 |
| 返回值 | `rax` 与 `xmm0` 双通道 | 结构体返回值（走隐藏第一参数）未实现 |
| 字符串 | **借用对象** | 见下 |
| struct 按值 | 不支持 | 见下 |
| 泛型方法 | 调不了 | 需要 MethodInfo，符号表里没有 |

**字符串是「借用」的**：拼在 scratch 里，不是 GC 堆对象。调用期间读没问题
（比如 `GetAsbInfoByAssetFullPath` 查路径、`SetActive` 后显示文本），但
**不能被游戏长期持有** —— 如果某个方法把字符串存进托管对象，之后 GC 扫到
会访问一块未注册内存。需要长期持有就必须走 `il2cpp_string_new`（要 API 表，
目前 dump 不可用）。

**struct 按值传递**：Windows x64 对 9 字节以上的结构体改为「传指针给调用方
分配的副本」。`Vector3`(12B) 这类参数需要自己在 scratch 里放好数据再传地址，
工具不会自动 marshal。

## 6. 安全措施（沿用 + 新增）

原有三道闸全部保留：

1. `pending` 必须等于 `0xA5`，内存被写脏时最坏是「本次不执行」
2. `target` 为 0 不调用（2026-10-25 崩过一次）
3. 拒绝执行时 `done=2`，外部可观测

新增两道：

4. **`target` 必须落在 `UserAssembly.dll` 映像内**（原有，`_submit` 里保留）
5. **`install` 时检查原指令能否搬移**：`orig` 里有 rip 相对寻址或相对跳转时，
   搬到 stub 后位移不变而基址变了，目标就错。之前只有 `hook` 检查，`install`
   漏了 —— stub 变长后风险一样，已补上（`unsafe_replay`）。

当前宿主 `MonoClientPacketConsumer.Update` 的入口是纯 `push` + `sub rsp`，
检查通过。

## 9. sret：按值返回 >8 字节的结构体

MS x64 ABI 规定，返回值超过 8 字节不进寄存器，改为**调用方提供缓冲区、指针占
第 0 个整数槽**。il2cpp 把 `this` 当普通首参，所以顺序是：

```
rcx = 缓冲区   rdx = this   r8 = 第 1 个参数 ...
```

`call_struct(target, args, nbytes)` 已实现该路径：缓冲区固定在 `scratch+0x1F00`，
预填 `0xCC`，调用后统计实际写入字节数；`rax` 回来应等于缓冲区地址（可作交叉校验）。
`call_name.py` 的 `RET_STRUCT` 表会自动识别 `Vector3/Vector4/Quaternion/Color/
Rect/Bounds` 并格式化输出。

**反例（重要）**：裸 `call_typed` 调 `Vector3` getter 会把 `this` 放在 rcx，函数却
把 rcx 当返回缓冲区往里写 12 字节 —— 写穿的是对象头。这不是"取到垃圾"，是静默
破坏内存。所以结构体返回必须走 `call_struct`。

## 10. 两类必崩的调用（地址正确也救不回来）

### 10.1 跳进函数半截

把 `0x6918300` 当成函数入口（实际 `Transform::get_forward` 是 `0x6917FF0`，
该地址落在 `Transform::get_right` 内 +0x40）。从函数中间开始执行，进程直接消失，
无 crash dump、无 WerFault。

已加护栏：投递前查符号表入口表（311,382 项，加载 0.17s），非入口一律拒绝并报告
它落在哪个函数第几字节；`--force` 才放行。

### 10.2 托管异常无人接管

调 `Type::GetType(name, null, null, throwOnError:true)` —— 地址正确、签名匹配，
但空委托导致游戏线程抛 `NullReferenceException`。il2cpp 的托管异常是 C++ 异常，
必须沿 native 栈找到 il2cpp 帧上的 catch；而 stub 是直接 `call` 进去的，栈上没有
那样的帧，于是直接 abort。

已加护栏：`call_name.py` 检测参数里的 `Func`/`Action`/`Predicate` 一律拒调
（我们只能传 null 委托），`--force` 才放行。

**推论**：凡是「可能抛异常」的方法都危险 —— 反射（`Type::GetType`、`MethodInfo::Invoke`）、
字符串解析（`Convert::ToInt32`、`int::Parse`）、越界访问（`Array::GetValue`）、
`Activator::CreateInstance`。这类能力在「直接在游戏线程 call」的架构下**做不了**，
除非先给 stub 装一个能接住 il2cpp 异常的帧（未实现）。
