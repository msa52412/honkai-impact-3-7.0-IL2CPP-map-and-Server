# BH3 7.0 DLL 注入能力实现概况

> 整理时间：2026-11-04
> 适用：BH3 7.0（Unity 2017.4.18f1 + 米哈游定制引擎）
> 说明：本文只描述**手法与机制**，不含游戏本体资源的再分发。

---

## 一、总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ 游戏进程 BH3.exe                                              │
│                                                              │
│  BH3.exe 启动                                                 │
│      │ 系统按名加载 version.dll（同目录优先）                  │
│      ▼                                                        │
│  version.dll  ← 侧加载垫片（转发所有系统导出）                 │
│      │ 读 libraries.txt                                       │
│      ▼                                                        │
│  bh3bypass.dll ← 注入载荷                                     │
│      │ DllMain → 起工作线程                                    │
│      │ 等 UserAssembly.dll 就绪 → 扫描 6 处 RVA → 写补丁        │
│      ▼                                                        │
│  [静态补丁] 资源校验恒假 / 下载弹窗压制 / 校验结果恒真          │
│                                                              │
│  ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ←   │
│      ↑ 共享内存信箱（Python 工具 → 游戏主线程）                │
│      │ {target, args[4], ret, seq}                            │
│  MonoClientPacketConsumer.Update 钩子（每帧取走执行）          │
└──────────────────────────────────────────────────────────────┘
              ▲
              │ ReadProcessMemory / WriteProcessMemory
              │ VirtualAllocEx / VirtualProtectEx
┌─────────────┴────────────────────────────────────────────────┐
│ 外部工具进程（Python）：tools/*.py                            │
└──────────────────────────────────────────────────────────────┘
```

两条通道分工：

| 通道 | 时机 | 优点 | 限制 |
|---|---|---|---|
| **静态补丁**（DLL 内 C 代码） | 启动早期，UserAssembly 刚映射 | 最先执行、能拦住校验 | 只能做等长字节改写 |
| **运行时信箱**（Python → 主线程） | 游戏运行中 | 能调任意 il2cpp / 引擎函数、能构造对象 | 依赖游戏主循环在跑 |

## 二、侧加载注入

### 2.1 原理

Windows 加载 DLL 时优先搜索**可执行文件所在目录**。把自制 `version.dll` 放到 `BH3.exe` 同目录，系统就会加载它而不是 `System32\version.dll`。

### 2.2 version.dll 做的事

1. **转发全部系统导出**（`GetFileVersionInfoA/W`、`VerQueryValue*` 等）——用 `.def` 导出表 + `#pragma comment(linker, "/export:...")` 或转发器写法，保证任何调用方看起来行为一致。
2. **DllMain 中不当场做事**（加载器锁内不能 LoadLibrary），另起线程：
   ```
   读同目录 libraries.txt（一行一个 DLL 名）
   → LoadLibraryW(完整路径)
   ```
3. 逐个加载，失败只写日志不阻断。

### 2.3 载荷选择

`libraries.txt` 目前只有一行：

```
bh3bypass.dll
```

想做别的实验（例如再注入一个观察用 DLL）只需追加一行。

## 三、静态补丁：6 处字节改写

### 3.1 定位

所有目标函数都在 `UserAssembly.dll`（il2cpp 编译产物）里，用**文件内 RVA**定位，运行时加模块基址：

```c
BYTE *ua = (BYTE*)GetModuleHandleW(L"UserAssembly.dll");
BYTE *fn = ua + RVA_XXX;
```

### 3.2 补丁表

| # | RVA | 函数 | 写入字节 | 作用 |
|---|---|---|---|---|
| 1 | `0x02FAD6D0` | NeedRefreshMemoryMappedData | `33 C0 C3` | 永不重建 asb.dat |
| 2 | `0x02FADA80` | NeedToVerifyBlocks | `33 C0 C3` | 跳过块校验 |
| 3 | `0x02FAD520` | NeedDownloadPatchX | `33 C0 C3` | 补丁块不触发下载 |
| 4 | `0x02753570` | NeedShowDownloadResourceDialog | `33 C0 C3` | **压掉「要求下载」弹窗** |
| 5 | `0x02FAD470` | NeedDownloadAsbX | `33 C0 C3` | ASB 不触发下载 |
| 6 | `0x01F1A600` | OnCheckStreamingAssetBundleComplete | `FF 25 00 00 00 00` + 8 字节指针 | 校验结果恒真 |

前 5 个是**同构的"恒返回 false"**：`xor eax,eax; ret`（bool 返回 0）。
第 6 个不能用同样手法（它返回值会被当作"成功"走后续逻辑），所以用 **jmp 到自建 stub**：

```asm
mov dl, 1      ; B2 01
mov al, 1      ; B0 01
ret            ; C3
```

### 3.3 工程要点

* **幂等**：写之前先读，已是目标字节就跳过（避免重复注入/热重载时破坏）。
* **改保护**：`.text` 是 `PAGE_EXECUTE_READ`，先 `VirtualProtect` 成 `RWX`，写完改回，再 `FlushInstructionCache`。
* **日志**：每条补丁落地都写 `bh3bypass.log`，便于确认"补丁是否真的生效"。

### 3.4 ★ 绝对不能补的函数

**`GetDownloadBlockSize`（RVA `0x2753210`）——禁止打补丁。**

恒返回 0 会让 `DownloadResources` 走 `==0` 分支**跳过下载管理器初始化**，进主场景后对空管理器虚调用 → unityplayer `call [rax+0x48]` **崩溃**。

弹窗压制由 #4 独立完成，两者必须解耦。

## 四、运行时调用通道：共享内存信箱

### 4.1 为什么不能直接远程线程调用

il2cpp 的托管函数必须在**附着了 il2cpp 运行时的线程**上调用，否则内部要拿线程锁会失败。而 `CreateRemoteThread` 起的线程没有附着。

### 4.2 做法：让游戏主线程替我们调用

1. 找一处**每帧必调**的托管方法：`MonoClientPacketConsumer.Update`。
2. 在它的入口写 14 字节跳板（`FF 25 00000000` + 绝对地址），跳到自建 stub。
3. stub 逻辑：
   ```
   保存易失寄存器
   读信箱：[target][arg0..arg3][seq]
   seq 变化且 target 非空 → 按 Win64 调用约定布置 rax=target, rcx/rdx/r8/r9=args, call
   写回 [ret] 与 [done]
   恢复寄存器，执行被覆盖的原指令，跳回原函数
   ```
4. Python 侧：`WriteProcessMemory` 填信箱 → 轮询 `done` → 读 `ret`。

### 4.3 参数上限与扩展

信箱直通 **4 个寄存器参数**（rcx/rdx/r8/r9）。需要更多参数时要另外在栈上布置（工程里有 5~8 参的调用封装）。

### 4.4 坑

* **超时 = 游戏线程大概率已炸**（例如我们传了失效的对象指针），必须先查进程再判断。
* **il2cpp 包装层（如 `Mesh.SetVertices` 0x3498500）不能从信箱调**：它内部要拿 il2cpp 线程锁，而主线程正卡在 Update 钩子里 → **自死锁**（不崩但不返回）。只有不碰运行时锁的纯读函数（如 `get_vertexCount`）可以随便调。

## 五、内存原语

| 原语 | 用途 | 实测 |
|---|---|---|
| `OpenProcess(0x0410\|0x0020\|0x0008\|0x0010)` | 拿句柄 | ✅ |
| `VirtualQueryEx` 枚举区域 | 扫堆 | ✅ |
| `ReadProcessMemory` | 读任意内存 | ✅ |
| `WriteProcessMemory` + `VirtualProtectEx` | **写只读页** | ✅ 改保护后可写、回读一致 |
| `VirtualAllocEx` | 在目标进程分配大缓冲 | ✅ 分配 1MB 可写 |

### 关键约定

* **读堆必须分块**（16 MB）。一次性 `read_mem` 整块会让本进程申请同等内存，把系统提交打爆 → 游戏 OOM 崩在 `RVA 0x445d7d`。
* 大块数据（如 22 万字节的顶点数组）走 `VirtualAllocEx` 分配，不用 scratch 页（scratch 只有几 KB）。

## 六、定位托管对象：按 klass 扫堆

### 6.1 流程

```
1. 从字符串命中反查 klass（rt_class.py --name Xxx）
   —— 用「字符串 → 指向它的指针 → 该指针所在结构 +0xA8 是类名」的链
2. 用 klass 值在全部可读内存里搜 8 字节匹配
3. 每个命中点当作"对象起始"，做以下校验：
   a. 地址 > 0x100000000（低区是元数据/类表，不是 GC 堆）
   b. [obj+0x08] == 0（monitor 为空）
   c. [obj+0x10] >= 0x10000 且可读（m_CachedPtr）
   d. [native+0x38] >= 0x10000 且可读（如 Mesh 的 blk）
4. 全部通过才允许调方法
```

### 6.2 ★ 假实例会崩游戏

klass 结构里存在 `[klass+0x98] == klass` 这类自指针，会造成大量**假实例**。对假实例调 `get_name`，Unity 会把类名字符串当 native 指针解引用：

```
Read from location ffffffff  → Access Violation
```

**今天踩了两次**（`RBX=0x5075cf40`）。所以第 3 步的 native 链校验是**强制项**，不是可选项。

### 6.3 klass 地址每次进程都会变

klass = 「元数据基址 + 固定偏移」，基址随 ASLR 变。例如某进程 `0x9615490`，下一进程 `0x8c15490`。

**正确做法**：每次都从「已知对象的 `+0`」或字符串链重新求，**严禁复用上次的常量**。

## 七、手写托管对象

### 7.1 il2cpp String 布局

```
+0x00  klass     (String 的类指针)
+0x08  monitor   (0)
+0x10  length    (int32)
+0x14  chars[]   (UTF-16LE)
```

用途：给 il2cpp 函数传字符串参数，例如 `AssetBundle.LoadAsset(bundle, "assets/.../xxx.fbx")`。

### 7.2 il2cpp 数组布局

```
+0x00  klass
+0x08  monitor
+0x10  bounds        (0 表示一维无边界表)
+0x18  max_length    (int64)
+0x20  元素数据…
```

用途：
* 构造 `Matrix4x4[]`（补齐 bindpose 时用过，228 × 64 B）
* 构造 `Vector3[]`（顶点数组）

### 7.3 klass 从哪来

**不要另找**：从同类型现成对象取 `+0` 即可。
* String klass：任意活字符串（如 `get_name` 的返回值）
* Matrix4x4[] klass：`Mesh.get_bindposes` 返回数组的 `+0`

## 九、动态加载外部资源的完整链路

### 9.1 为什么需要重新打包

`AssetBundle.LoadFromFile` 是 **Unity 自己的加载器**，它只认标准 `UnityFS`。而 BH3 的 `.wmv` / 单元是**私有头**（前 54 字节被替换，version 字段是乱码）→ 直接加载必然返回 0。

处理链：

```
.wmv（私有头，可能含 mr0k 加密块）
  → wmvkit 解析私有头 + 解块
  → mkvfs.build_bundle 重建标准 UnityFS
     （version=6，flags=0x843，LZ4HC 分块）
  → LoadFromFile 成功
```

**格式细节**（实测有效组合）：

| 项 | 必须值 | 说明 |
|---|---|---|
| version | **6** | 2017.4 不认 v7（用 repack_plain 默认 v7 会返回 0） |
| flags | **0x843** | 0x800 + 块合并 0x40 + LZ4HC 0x3；0xc0 组合不行 |
| 块压缩 | LZ4HC | ci < ui 才被接受 |

### 9.2 类型哈希必须改写

`enable_type_tree = 0` 时，Unity 拿 bundle 里的 `oldTypeHash` 与引擎内置类定义比对，不一致会报
`contains run-time classes 'X' of incompatible version` 并**整包拒收**。

所以重建时要把 16 字节哈希改成目标客户端的值（`_ext\clsmap70.json`）。

MonoBehaviour（classID 114）不改：那 16 字节是脚本 GUID，改了也没用。

### 9.3 ★ 同一内容每进程只能加载一次

实测：同一份内容换个文件名再 `LoadFromFile`，**仍然返回 0**。
Unity 按 **bundle 内部身份**（AssetBundle 对象名 + 内部 CAB 列表）去重，**不是按磁盘路径**。

⇒ 正确做法是**复用已加载的 bundle 句柄**（`LoadAsset` 可以对同一个 VA 反复调）。

## 十、渲染侧

### 10.1 裸写顶点缓冲不管用

`Mesh` 的 native 结构：

```
mesh+0x10 → native
native+0x38 → blk
blk+0x60  → 顶点缓冲指针
blk+0x6c  → 顶点容量
```

直接 `WriteProcessMemory` 到 `blk+0x60` 指向的缓冲，**`get_vertices` 立刻能读到新值，但画面不变** —— 只改了 CPU 副本，没有提交 GPU。

### 10.2 走函数通道才生效

```
unityplayer!0x7EBBB0(native, data, len)
```

它内部：写数据 → 置脏标志 → 调 `0x7ec800` 提交。`ret == 0` 表示成功。

* `len` 必须等于当前顶点数（`blk+0x6c`），否则触发索引校验返回 1
* `len > 当前数` 走合法扩容
* 数据缓冲要 `VirtualAllocEx` 分配（22 万字节放不进 scratch 页）

## 十一、已证否 / 已知限制

| 结论 | 证据 |
|---|---|
| **换 `SMR.sharedMesh` 对皮肤网格无效** | 连 7.0 原生皮肤网格换上去都会乱/崩；游戏用**自研骨骼矩阵**渲染，Unity 的 `bones`/`bindposes` 只是形式挂载点 |
| `get_vertices` 对皮肤网格返回 0 是**正常现象** | 7.0 自己的皮肤网格同样返回 0（顶点数据在 `.resS`，CPU 侧读不到但 GPU 正常） |
| 顶点数/通道表读对 ≠ 能渲染 | 网格要真正上屏还受骨骼绑定、材质、SMR 装配影响 |
| 内存耗尽会让 `UserAssembly.dll` AV | `Write to location 00000000` + 页面文件剩 5 MB；不是补丁问题 |

## 十三、最小可用配方

```
1. 复制 version.dll + libraries.txt + bh3bypass.dll 到游戏根目录
2. 启动游戏，确认 bh3bypass.log 里 6 条 OK
3. 进到大厅（日志出现 PreloadUIViews）
4. python tools\icall.py install          # 装信箱
5. python tools\test_inject_all.py        # 12 项体检
6. 按需调用具体能力脚本
```
