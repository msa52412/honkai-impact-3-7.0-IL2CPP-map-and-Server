# 德丽莎 C7 第二套皮肤（04_01）注入 — 离线分析报告

> 日期：2026-11-02
> 目标：给《崩坏3》7.0 私人服务端客户端（`D:\BH3\7.0`）显示德丽莎 C7「月下誓约·予爱以心」的第二套皮肤 `dress_theresa_c7_04_01`
> 硬约束：**不修改任何客户端文件**（清单、缓存、`.wmv`、`asb.dat` 一律不动），只能运行时动态加载

---

## 0. 一句话结论

**04_01 是一条「纯换件」路线**：8 个分件 Mesh（Body / Face / Hair / Veil / EyeShape / Eyebrow / weapon01 / weapon03）+ 4 个材质 + 7 张贴图 + 1 个武器 prefab，**不带骨架、不带身体 prefab**。

它必须挂到 7.0 客户端里**已有的 C7 默认模型骨架**上。技术上可行，且比 04_02 简单；但最后一公里（骨架 bone 顺序、shader 解析）只能在游戏内验证。

#### ⚠ 扫描坑（踩过）

BH3 的资源清单是 FlatBuffers，字符串做了**前缀去重**。同一路径在文件里长这样：

```
assets/asbres/entities/avatar/theresa_c7_bw/dress_   ← 单独一段
04_01                                                 ← 单独一段
/theresa_weapontype/low                               ← 单独一段
/low_dress01.prefab
```

所以**扫整串 `dress_theresa_c7_04_01` 永远 0 命中**，会误判成「客户端没有这个资源」。正确做法是扫 `theresa_c7_bw/dress_` 或更独特的尾段（`low_dress01`）。

## 2. 三个硬事实（推翻/修正了旧笔记）

### 2.1 `m_Container` 的键不是对象名，而是 **fbx 路径**，且同一路径有 9 条

`01273761` 的容器表实测：

```
[0] .../dress_theresa_c7_04_01/_dependencies/model/avatar_theresa_c7_04_01_model.fbx  preload=0/1 -> Mesh:Body
[1] 同上                                                                              preload=1/1 -> Mesh:Eyebrow
[2] 同上                                                                              preload=2/1 -> Mesh:EyeShape
[3] 同上                                                                              preload=3/1 -> Mesh:Face
[4] 同上                                                                              preload=4/1 -> Mesh:Hair
[5] 同上                                                                              preload=5/1 -> Mesh:Veil
[6] 同上                                                                              preload=6/1 -> Mesh:weapon01
[7] 同上                                                                              preload=7/1 -> Mesh:weapon03
[8] 同上                                                                              preload=8/1 -> CharacterController
```

**9 条键完全相同**，靠 `preloadIndex` 区分。这就是当初 `LoadAsset("Body")` 返回 0 的真正原因——键里根本没有 `Body`。

→ 要拿单个 Mesh：`LoadAsset(fbx路径)` 只会拿到 `Body`（preloadIndex 0）；**要拿全部 8 个必须用 `LoadAllAssets()`**。

### 2.2 04_01 Body 绑 202 根骨，04_02 Body 只绑 92 根

- 04_02 的 SMR 实测 `m_Bones` = **92**，其 Body Mesh 的 `m_BindPose` 也正好 = **92** → 自洽。
- 04_01 的 Body Mesh `m_BindPose` = **202**。

→ **04_02 是 LOD 减骨版，不能当 04_01 的载体**。04_01 必须用基础模型那份完整骨架（≈202 骨）。

### 2.3 基础 C7 战斗模型在三个客户端里都是「加密变体」，离线读不出

| 客户端 | 单元 | 大小 | 状态 |
|---|---|---|---|
| 7.0 | `f95c59e5a19243bb_000C0274` | 1 928 934 B | 42 字节改写头 |
| 7.6 | `2d5855eb83c53bb4_00119369` | 1 928 866 B | 同上 |
| 9.1 | `88fcb9e4d8e56353_0011A5CA` | 1 928 866 B | 同上 |

三家发的是**同一个被保护的文件**。文件头是 `UnityFS\0` + 42 字节被改写区（`version` 读出来 `0xCE4EEE1E`），之后从 `0x32` 起是 `mr0k`。**没有 blocksInfo 就无法定块边界**，离线解不开。

→ 这份模型的 Mesh 名、SMR 列表、bone 顺序，**只能在游戏运行时读**。

## 3. 三条注入路线

### 路线 A：整模型替换（用 04_02）

- **做法**：外部加载 `00260C8E`（`avatar_lod.prefab`）+ 4 材质 + 2 贴图，实例化后替换当前 C7 的模型节点。
- **优点**：04_02 自足（自带骨架 + prefab + body 材质），不依赖基础模型内部结构；`LoadFromFile` + `LoadAsset` 已在 7.0 客户端实测成功。
- **缺点**：**显示的是 04_02，不是用户要的 04_01**。
- **价值**：作为**技术验证台阶** —— 先跑通「外部 prefab 实例化 + 替换模型节点」这条链，再换成 04_01 的换件。

### 路线 B：网格热替换（用 04_01）★ 推荐

- **做法**：载体用 7.0 现成的 C7 默认模型（骨架已在内存里），把 8 个 SMR 的 `sharedMesh` 换成 04_01 的 8 个 Mesh（按名字对应），再把材质换成 04_01 的 4 个 mat + 7 张贴图。
- **优点**：显示的是真正的 04_01；改动面最小（只换 Mesh 引用，不动骨架/Animator）；`LoadAllAssets()` 一次拿全 8 个 Mesh。
- **风险**：
  1. **bone 顺序**必须一致（04_01 Mesh 的 bindpose 顺序 vs 基础模型 SMR 的 `m_Bones` 顺序）——这是唯一可能致命的一点，只能运行时验证。
  2. 04_01 的 mat 依赖的 shader 在 7.0 里是否存在。
  3. `..._texture_body_color` 的容器路径前缀是 **`assets/deleted/res/`**（路径迁移残留），按路径加载可能被拒 → 改用 `LoadAllAssets` 规避。

### 路线 C：改 DressData 让客户端自己去加载

- **阻塞**：`patch_dress_record.py` 的「共享签名」是**堆指针**（每次启动都变：0x0E7EB1C0 / 0x0E0DB1C0 / 0x0d5db1c0…），硬编码候选表已失效。已加 `derive_sig()` 从立绘字符串反推，能稳定拿到 296 条记录。
- 但即使改成功，7.0 客户端里**没有 04_01 的资源**，客户端照样加载不到 → 这条路单独走不通，只能配合路线 B 的运行时资源注入。

## 4. 已验证 / 未验证

### 已离线验证 ✓

- `m_Container` 真实语义（键 = fbx 路径 × preloadIndex）
- 04_01 / 04_02 全部单元的清单、大小、容器键、对象组成
- 04_01 的 8 个 Mesh 名字、子网格数、bindpose 数
- 04_02 的 prefab 层级（108 GO / 92 骨 / 1 个 Body SMR）
- 两套皮肤共用骨架（04_02 prefab 里含 04_01 的头发骨骼）
- 7.0 客户端确实没有 04_01/04_02 资源
- 基础 C7 模型是加密变体（三家一致）

### 已在游戏内验证（前几轮）✓

- **7.6 的 04_01 主模型单元在 7.0 客户端里 `LoadFromFile` + `LoadAsset` 双双成功**
- asb 入口 `0x2FA9570` 是**安全调用点**（QPC 里调 `LoadAsset` 会 AV 崩溃），且大厅日常活动会自动触发，无需手动进页面

### 未验证 ✗（必须进游戏）

1. 7.0 基础 C7 模型的 SMR 列表与 bone 顺序，是否与 04_01 各 Mesh 的 bindpose 顺序一致 ← **最关键**
2. 04_01 材质依赖的 shader 在 7.0 里能否解析
3. `assets/deleted/res/...` 路径的 body color 贴图是否被引擎接受
4. 换完 Mesh 后 Animator 是否正常驱动（蒙皮矩阵由 SMR + bone 决定，理论上不受影响）

## 5. 工具缺口

| 缺口 | 影响 | 严重度 |
|---|---|---|
| **第二种 mr0k 编码**未解 | `00336C7B`(04_02)、`011FF180` b3、`0163E526`(anim) | 低——都不在关键路径上 |
| **42 字节改写头**未解 | 三家的基础 C7 战斗模型 | 中——只能运行时读，不影响方案 |
| 资源路径 64 位哈希未校准 | 无法离线「路径 → 单元」反查 | 低——已改用 `preloadIndex` 方案 |

> mr0k 解码器本身是对的：与 `wmvkit.lz4_decode` 在全部 40 个普通 LZ4 块上**逐字节一致**。失败的块是另一种编码，不是 bug。

## 6. 建议下一步

1. **先跑路线 A 当台阶**：外部加载 04_02 的 `avatar_lod.prefab`，实例化并替换当前 C7 模型。这一步能一次性验证「外部 prefab → 场景实例 → 替换模型节点」全链路。
2. 同时**在游戏里 dump 基础 C7 模型的 SMR 结构**（每个 SMR 的 `sharedMesh.name` + `m_Bones.Length` + 前几个 bone 的 GameObject 名）。拿到这份数据就能离线判定路线 B 的 bone 顺序是否匹配。
3. 若 bone 顺序匹配 → 直接上路线 B（换 8 个 Mesh）。
4. 若不匹配 → 退回路线 A，改用 04_02 的骨架当载体，把 04_01 的 Mesh 重定向（工作量显著上升）。
