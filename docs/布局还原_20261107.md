# 布局还原：把「有名字没偏移」的元数据表补成可用布局（2026-11-07）

> 接 `docs/离线分析能力_20261107.md`。那一轮用代码反推字段偏移，覆盖 27,995 类、
> 但**只有 9.3% 的偏移能配上名字**。这一轮把缺口补掉：**36,465 类 / 595,240 个字段全部带名字 + 偏移**。

## 1. 先纠正上一轮的两个误判

| 上一轮的说法 | 实际情况 |
|---|---|
| 「`bh3_layout5b.tsv` 只有 36,464 个类型，`LevelActor` 这类主力类恰好没有」 | **错**。表里类型名带命名空间（`MoleMole.LevelActor`），当时用 `\tLevelActor\t` 查漏了。实际有 176 行 |
| 「`bh3_types_parents.txt` 有 57,488 行继承信息」 | **是个空壳**：`parent` 列整列为空，只有表头。真正可用的在 **`bh3_types_full.txt`**，`parentIdx` + `parent` 齐全，覆盖率 **98.4%** |

`bh3_types_full.txt` 格式：

```
index  namespace  type  token  methodStart  methodCount  nestedCount  parentIdx  parent
31142            LevelScoreDLCPlugin  020079AE  ...                     202814     MoleMole.LevelScorePlugin
```

顺带验证了上一轮从 `_ctor` 反汇编推出的继承关系：`LevelScoreDLCPlugin::_ctor` 内部调
`LevelScorePlugin::_ctor`，表里 `parent = MoleMole.LevelScorePlugin`，两者一致。
`LevelScoreDLCPluginV2` 也是同一个父类。

## 2. 真正的缺口：offset 列全是 0

四份布局表的列都是 `typeIdx / typeName / fieldIdx / fieldName / fieldType / size / isStatic / offset / conf / nProbe`，
**名字、类型、大小都有，`offset` 整列为 0**。所以不能直接读，必须重算。

好在 il2cpp 的实例布局是确定的：

```
offset(field_i) = B + delta(i)
B       = 父类 instance_size（无父类时 sizeof(Il2CppObject) = 16）
delta   = 按声明顺序逐个 AlignUp(对齐) 后累加
```

两条关键事实（都是实测出来的，不是假设）：

1. **字段列表已经是「祖先在前」的扁平链**。`InLevelMainPageContext` 的 161 行开头就是
   父类 `BasePageContext` 的 21 个字段；`SoftBodyCable` 的第一行直接是
   `m_CachedPtr`（`UnityEngine.Object` 的字段）。所以这类**从 16 起算**，不能再叠父类大小。
   32.7% 的类型是这种情况（`flat`，17,232 个）。
2. **父类在类型表里但没有任何字段行 = 零实例字段**，基址沿用父类的基址，不能当成「父类未知」。
   这类占 50.7%（`zero-field-parent`，17,706 个）——`LevelScorePlugin` 就是这种，
   所以它的 `_levelActor` 落在 `+0x10` 是对的。

## 3. 对齐规则：不能按 size 硬套

第一版用 `align = min(size, 8)`，结果只到 89.5%。原因是 Unity 的结构体：
`Vector2` 是 8 字节但**对齐 4**，`Vector4`/`Color` 是 16 字节但**对齐 4**。
按 size 硬套会把后面的字段全部推偏。

改成按字段类型递归求对齐：

```
基元        -> 自身大小（封顶 8）
枚举        -> 底层类型大小
结构体      -> 成员对齐的最大值（递归进它的字段表）
引用/数组/泛型 -> 8
```

值类型判定不用猜 size，用父类链：`parent` 走到 `System.ValueType` / `System.Enum` 就是值类型
（共 11,215 个），这条路子干净且通用。

## 4. 校验：拿代码反推的偏移当真值

用 26,414 个同时有「表」和「代码观测」的类对撞：

```
偏移总条数            164,660
完全落在字段起点      153,059
落在结构体字段内部      5,343   <- 也是对的，见下
未命中                11,601
命中率（按条数）        93.0%
命中率（按访问次数加权） 96.2%
Assembly-CSharp        94.5%
MetaData               99.9%
mscorlib               91.0%
```

**那 5,343 条「落在结构体内部」不是错，是我一开始的校验写错了**。例如
`LaserSwordTrail.Sword2WorldMatrix` 是 64 字节的 `Matrix4x4`，代码里访问
`[this+0x30] / [this+0x40] / [this+0x50] / [this+0x60]`，那是矩阵的四行——
编译器把 `Sword2WorldMatrix.m10` 这类成员访问折叠成了 `this + 0x40`。
`SoftBodyCable.swingScale`（12 字节 Vector3）内的 `0x34`/`0x38` 同理。
把「落在值类型字段区间内」也计为命中后，命中率从 90.9% 升到 94.5%。

三处独立真值复核：

```
InLevelMainPageContext +0x20  = <view>k__BackingField (GameObject)
   反汇编 SetOWEndlessLevelScoreVisible:  mov rcx,[rsi+0x20] → GameObject::get_transform()
LevelScoreDLCPlugin    +0x38  = <active>k__BackingField (bool)
   反汇编 LevelScoreDLCPlugin::SetActive:  mov byte ptr [rbx+0x38], dil
LevelScorePlugin       +0x1c  = <score>k__BackingField (float)
   = 0x10(_levelActor,8) + 0x18(totalScore,4) + 0x1c(score)
```

## 5. 还没解决的：字段表漏项导致的整体漂移

`LevelActor` 是反例：表里 176 行、算出 size=`0x648`，但代码在 `+0x3e8` / `+0x3f0`
各有一个 **8 字节指针**（`cmp qword ptr [rbx+0x3e8], 0`），表里 `+0x3e8` 却是
4 字节的 `_swapTimerState`。说明表在 `0x048` 和 `0x3e8` 之间漏了字段，后面整段推偏。

试过用代码观测的偏移做锚点「补空位」（`LF_SNAP=1` 打开），逐类按匹配分择优：
**只有 238 条命中被选中，且这部分的实际命中率只有 83.2%，比自然版差**。
触发条件（`观测偏移越过本字段且与该字段对齐一致`）误判太多，已默认关掉，代码留着当实验开关。

结论：**表漏字段这件事靠布局推算补不回来**，只能靠更完整的字段表。
不过这类漂移集中在少数巨型类（`LevelActor` 这种 0x648 字节、上百字段的），
绝大多数类（`Assembly-CSharp` 94.5%）是准的。

## 7. 顺带修正一条 HUD 结论

上一轮说 `InLevelMainPageContext::SetOWEndlessLevelScoreVisible` 里有 `ctx[+0x209] = notify[+1]`。
**这条是错的**。把整个函数（`pdata` 长度 `0xba`）完整反汇编，`this`（`rsi`）只被访问一次：

```
mov  rcx, qword ptr [rsi + 0x20]        ; ctx.view (GameObject)
call UnityEngine.GameObject::get_transform
mov  rdx, qword ptr [rip + 0x79183e1]   ; 静态引用槽 -> 面板名
call UnityEngine.Transform::FindChild(string)
movzx ebx, byte ptr [rsp + 0x40]        ; = notify payload[+0]
...  tail -> GameObject::SetActive(bool)
```

即：**它只读 `ctx+0x20` 拿 view、只按一个静态名字 FindChild、只 SetActive 那一个面板**，
全程没有写 `ctx+0x209`。所以 NotifyType `0x2F7` 确实只控制一个面板，这一点上一轮的结论站得住，
但「`ctx[+0x209]=notify[+1]`」这个细节要删掉。`+0x209` 在布局表里落在
`_monoInLevelPracticeCmpt`（8 字节引用）内部，本身就不可能是个 bool 字段 ——
布局表在这里帮我们否掉了一个错误结论。
