# 元数据解密 · 进展报告（2026-11-07）

> ⚠️ **11:40 修订**：本文"必须挂 guard page"的结论已过时。
> `rea\_rea\bh3_symtab.tsv` 里已经有 398,316 条「类::方法 → RVA」（86.9% 精确落在 `.pdata` 函数起点），
> 方法级的解密需求不需要再做了。详见 **《元数据_符号表与远端通道_20261107.md》**。
> 本文保留，用于记录「为什么整文件解密这条路走不通」以及内存里那 14.9 万条 Profiler marker 的来源。

> 目标：解开 `BH3_Data\Managed\Metadata\global-metadata.dat`（56,440,956 B）
> 结论先行：**文件只有 0x110 字节（272 B）的头部是真正被加密的，其余是「分段加密 + 明文」混合；
> 但正是这 272 字节决定了整份文件的用法，而它用 AES 级加密且无跨版本复用，静态拿不到。
> 内存里也没有整份明文（已用 2.39 GB 快照证伪）。**

## 1. 文件结构实测

| 项 | 值 |
|---|---|
| 大小 | 56,440,956 B（53.83 MB） |
| 头 8 字节 | `4d 48 59 00` `71 4d 2f 65`（`MHY\0` + 4 字节 tag） |
| 标准 IL2CPP magic `AF 1B B1 FA` | **全文件 0 次** |
| **加密区间** | **仅 `0x000000 .. 0x000110`**（272 B = 17 × AES 块） |
| 0x110 起 | 立刻是明文 u32 数组（`39 ee 02 00` = 0x2EE39 = 192,057，反复出现） |
| 4 KB 块统计 | 13779 块，熵均值 **7.298**，>7.5 占 **83.7%**，<5.0 占 15.8% |
| 可读 ASCII 串占比 | **0.8%**（108 / 13779 块） |

### 1.1 明文 / 密文跨度（4 KB 粒度，节选）

```
pln       0..81      0x00000000..0x00052000     328 KB   ← 头部 0x110 之后全是明文表
ENC      82..1379    0x00052000..0x00564000    5192 KB
pln    1380..2752    0x00564000..0x00AC1000    5492 KB
ENC    2753..3782    0x00AC1000..0x00EC7000    4120 KB   ← 注意 0xAC1000 处又是明文（0x6000xxxx 递增值）
pln    3783..4008    0x00EC7000..0x00FA9000     904 KB
ENC    4009..7211    0x00FA9000..0x01C2C000   12812 KB
pln    7545..7878    0x01D79000..0x01EC7000    1260 KB   ← 含 0x1DEDBAE 的长度前缀字符串表
ENC    7879..9261    0x01EC7000..0x0242E000    5532 KB
pln    9262..9386    0x0242E000..0x024AB000     500 KB
... 之后是 64~400 KB 的小段交替
```

说明：加密不是「整文件流密码」，而是**按段加密**，段边界 4 KB 对齐。
每段内部看起来是真正的分组密码（见第 2 节），明文段则是原样数据。

### 1.2 明文段里能直接读到什么（样例）

- `0x1DEDBEE`：`09 00 00 00 "MoleMole." 13 00 00 00 "MonsterAIController" ...`
  长度前缀字符串表，含 `UI/InLevelUI/FuncBtnUp`、`SKL_ULTRA` 等资源路径与枚举名
- `0x00AC1000`：`f8 07 00 60  fa 07 00 60  f9 07 00 60 ...`，整段是 `0x6000_0000 | 递增序号`
- `0x0242E000`：`(0x5F2,4) (0x5F2,4) (0x332D7,4) (0x332D6,4) ...`，`(index, count)` 对

## 2. 为什么静态解不开头部

| 检验 | 结果 | 含义 |
|---|---|---|
| UA 内 AES S-box / Te0 / Td0 | **0 命中** | 不是标准 AES 查表实现（可能 AES-NI 或自研） |
| UA 内 ChaCha sigma / SM4 S-box | 0 命中 | — |
| UA 内 TEA/XXTEA delta `0x9E3779B9` | 密集命中 `0x6553151..` | 是 XXTEA 变体（`(a<<6)+b+((a>>2)+delta) ^ a`），但作用对象未知，**不是元数据头** |
| 头部 xor 自相关（周期 1/2/4/8/12/16/17/20/24/32/34/48/64/68/108/136） | 各周期熵均 ≈7.0–7.2 | **不是重复密钥 XOR** |
| 7.0 ↔ 7.6 ↔ 7.9 ↔ 9.0 同偏移 XOR | 熵 7.90 / 7.90 / 7.86 | **无跨版本密钥流复用** |
| 同偏移 4 KB 块直方图 L1 距离 | 均值 0.473（随机基线 0.277） | 不是字节置换/洗牌 |
| **同一文件内 5 个加密段两两 XOR**（首 4 KB） | 熵 7.948–7.961 | **段间不复用密钥流**（否则会塌到 3–5） |
| 段内相邻 4 KB XOR | 熵 7.92–7.95 | 不是 4 KB 周期的固定填充 |
| `.rdata` 里 `global-metadata.dat` / `metadata version(%d) is not match` 字符串 | 存在（`0x81A0C78` / `0x81A0C244`） | 加载器确实在这里 |
| 上述字符串的 RIP 相对 xref | **0 处**（扫描器已在 2 MB 样本上验证可正常工作，267 处命中其它目标） | 加载器代码被混淆 / 在 `.tvm0` 里 |
| 文件头 tag `71 4d 2f 65` 在 UA 内 | 唯一命中 `0x81975F4`，后接 152 B 随机块 | 疑似每版本 tag 表，但后续字节与文件不一致 |
| 各版本 tag | 7.0 `71 4d 2f 65`；7.6 `71 0f 73 66`；7.9/9.0 `00 00 00 00` | 7.x 早期带 tag，后期置 0 |

**结论**：头部 272 B 是真正的分组密码产物（17 块，且 7.6/7.9/9.0 连 0x110 之后也继续加密），
静态路线必须拿到密钥，而密钥在混淆过的加载器里，没有可用的 xref 锚点。

## 3. 运行时实测（用 11-06 的 2.39 GB 快照 `hud\_mem\mem2.bin`）

### 3.1 内存里是密文，不是明文

| 检查 | 结果 |
|---|---|
| 快照里 `AF 1B B1 FA` | **0 处**（2.39 GB 全扫） |
| 快照里 `MHY\0` | 2 处 → 其一是**整份文件的密文副本** |
| 文件副本位置 | VA `0x208C7000`，区域 53.83 MB，`MEM_PRIVATE / RW`，与磁盘文件**逐字节一致** |
| 明文常量 `09 00 00 00 "MoleMole."` | 只有 1 处（= 文件副本内 0x1DEDBAE），**没有第二份明文副本** |

> 关键推论：如果存在整份解密副本，那么文件里本来就明文的 `0x1DEDBAE` 段会在内存里出现**两次**。
> 实测只有一次 ⇒ **不存在整份解密镜像**。

### 3.2 但内存里确实有大量明文元数据内容

- `IsAvatartDoNotShow`、`MonoInLevelOWEndlessMonsterGroupInfo` 等类名/方法名
  **在文件里 0 命中，在内存里命中**（例如 VA `0x181D9FB1`）
- 这批明文的规模：**149,637 条唯一 Profiler marker、14,754 个类名**
- 分布：VA `0x13400000` 起成 1.4–1.6 MB 的块，块间夹 1 MB 左右的堆结构
  ⇒ 解密是**按段、按需**做的，解出来的段留在堆上，但没有拼回一份完整文件

## 4. 意外收获：现成的符号表

il2cpp 的 Profiler marker 是 `命名空间-类-方法` 形式，在 7.0 的 `.rdata` 里确实一条都没有
（《技术路线》文档的结论没错），但**在运行时内存里是明文常驻**。

已导出：

| 文件 | 内容 |
|---|---|
| `hud\_out\profiler_markers.txt` | 149,637 条 marker + 14,754 个类名 |
| `hud\_out\names_from_mem.txt` | 2,099 个命令/协议名（`RequestOWEndlessBattleBegin`、`KCPSend_*` 等） |

与当前 HUD 相关的样例：

```
MoleMole-BaseInLevelContextPlugin-SetLevelScoreView0
MoleMole-Config-AddLevelScore-Call0
MoleMole-Config-AddLevelScore-get_MuteAuthority0
MoleMole-ActorAbilityPlugin-ByLevelScoreValueHandler0
MoleMole-LevelDesignManager-QuestHUDSetTimerShow0
MoleMole-KingdomsWarMainPageContext-SetHUDActive0
```

**这份表本身就是「类 + 方法」的全量名单**，虽然不带方法指针，但足以：
1. 枚举任意类有哪些方法（写 hook 前先确认该做什么）
2. 结合「marker 字符串被哪个函数用 `lea` 引用」反查函数地址 —— 见 5.3

## 5. 下一步（三选一，按性价比排序）

### 5.1 早期 hook 抓头部（推荐，1–2 天）

思路：272 B 的头部一定在 il2cpp 初始化时被解出来过一次。
利用现成的注入链（`version.dll` → `bh3bypass.dll`，启动早期即运行）：

```
1. 轮询等 global-metadata.dat 被读进内存（CreateFileW/ReadFile hook 或直接扫 MEM_PRIVATE 找 53.83MB + MHY 头）
2. 对该缓冲区第一页 VirtualProtect(PAGE_GUARD)
3. 捕获 STATUS_GUARD_PAGE_VIOLATION，记录 faulting RIP ← 解密函数地址
4. 两种收获任一：
   a. 直接读它解出来的 272 B 明文头部 → 后面所有段都能靠偏移解析
   b. 反汇编该函数拿密钥 → 离线解任意版本（含 7.9）
```

风险：gurad page 单次触发，若解密发生在缓冲区创建之前则抓不到（需换成 hook 分配点）。

### 5.2 纯运行时「按段捞」（0.5 天，收益有限）

既然解密后的段留在堆上，可以写工具扫全进程，把所有「看起来像元数据段」的块 dump 出来拼回去。
问题：**段与段之间无法确定顺序和偏移**（头部没解，没有 offset 表），拼不出合法文件，
只能拿到一堆可读字符串/数组。

### 5.3 符号恢复：marker → 函数地址（0.5 天，和元数据解耦）

不依赖头部，直接把 14.9 万条 marker 变成「函数 RVA → 类.方法」的映射：

```
1. 在快照里搜 marker 字符串地址的 8 字节指针
2. 指针落在 UA 模块的 .data / il2cpp 段 → 得到 ProfilerMarker 静态对象 RVA
3. 在 UA 代码里搜引用该 RVA 的 lea → 所在函数 = 该 marker 对应的方法
4. 产出 symbols_70.txt：RVA, Namespace.Class::Method
```

这条路的直接价值：**《技术路线》里说的「L3 能、但要一个个定位」会变成批量定位**，
也正好补上 HUD 那边「找不到 SetOWEndlessLevelScoreMode 之外的方法」的缺口。

## 7. 一句话给下一个人

> 7.0 的元数据不是「加密了整个文件」，而是「**只加密了 272 B 的头部 + 若干敏感段**」；
> 头部是 17 个 AES 块的产物，没有跨版本复用、没有 xref 锚点，静态无解。
> 想拿到它，唯一便宜的路是**在游戏启动早期给文件缓冲区挂 guard page，抓解密函数**。
> 而在那之前，**149,637 条 Profiler marker 已经把「有哪些类和方法」白送了**。
