## 0. 一句话结论

符号表给了 `类::方法 → RVA`，但真正干活缺四样：**字段偏移、调用者、枚举语义、字符串**。
本轮把前三个全自动化了，第四个（面板名）从 11-06 的内存快照里白捡到明文。
顺手纠正了 HUD 那条链路的一个错结论：**`isExtra` 不是面板开关**。

### 1.1 字段偏移：核心难点和三个坑

原理很朴素：getter 是 `mov eax,[rcx+0x38]`，setter 是 `mov [rcx+0x38],dil`，
setter 的写入位置和 getter 的返回值来源就是字段名与偏移的绑定。

踩到的三个坑，都已修：

1. **别名污染**：`mov rbx,rcx` 之后 rbx 也是 this，但 `mov rbx,[rcx+0x28]` 之后 rbx
   已经变成子对象了。不处理会让子对象的字段全算到 this 头上（实测 `+0x136` 被
   46 次写入、16 个方法命中，纯噪声）。修法：寄存器被非 this 来源改写就移出集合。
2. **pdata 边界偏小**：`get_rankScorePercentage` 的 pdata 只标 23 字节，真实有 40+，
   硬截断会漏掉 `movss xmm6,[rbx+0x3c]`。修法：窗口取 `max(pdata, 0x120)`，再回退到
   「最后一个 ret」收口。
3. **名字乱撒**：一个 getter 会路过好几个偏移（基类字段、临时对象）。修法：名字只落到
   「最后一条 load」（返回值来源）/「最后一条 store」，其余偏移只登记不命名。

### 1.2 验证（拿已知真值对撞）

| 真值来源 | 期望 | 实测 |
|---|---|---|
| `LevelScoreDLCPlugin::SetActive` 的 `mov byte [rbx+0x38],dil` | `+0x38` bool | ✅ `+0x38 w=1 store=2` |
| `LevelActor::HasLevelScorePlugin` 的 `cmp [rbx+0x3e8],0` | `+0x3e8` 指针 | ✅ `+0x3e8 w=8 load=3` |
| 同上第二分支 `cmp [rbx+0x3f0],0` | `+0x3f0` 指针 | ✅ `+0x3f0 w=8 load=5` |
| `LevelActor` 里 DK 伤害插件 | 应该叫 damagePlugin | ✅ 自动得出 `+0x378 damagePlugin` |

`LevelScorePlugin` 的整张表按声明顺序完整还原，可信度最高：

```
+0x1c score      +0x20 ratio     +0x24 extraRatio   +0x28 rank
+0x2c baseScore  +0x30 teamUltraSkillGauge          +0x38 active
```

`+0x38 active` 同时出现在 `LevelScorePlugin` 和 `LevelScoreDLCPlugin`，
正好对上 `HasLevelScorePlugin` 里那句 `cmp byte [rax+0x38],0` —— 两个 plugin 同基类。

## 2. 枚举语义：0x2F7 到底是什么

```bash
python _analysis/enum_recover.py 0x13FB4A0 --arg 2   # NotifyManager::FireNotify(NotifyTypes, object)
```

`FireNotify` 有 2258 个 call 候选，过滤后解出 **458 种取值**。`type` 落 `edx`，
回看最近的 `mov edx,imm`，再用 pdata 反查该调用点属于哪个方法，方法名即语义。

```
0x2f (47)   102 处   SetStatusBar / ShowStatusWidget / HideStatusWidget …
0x17 (23)     3 处   MonoLevelCgDownloadProcessView::OnAudioDownload*
0x19 (25)     4 处   MonoUploadProcessView::OnUpload*
0x2f7 (759)   1 处   LevelDesignManager::SetOWEndlessLevelScoreMode   ← 唯一生产者
```

**0x2F7 全库只有 1 个生产者**，与之前的链路分析完全对上，交叉验证通过。

## 3. HUD 结论修正

### 3.1 之前错的

> 「面板选择点在 NotifyType 0x2F7 的监听者，改 isExtra 就能点亮 Extra 面板。」

现在看来不对。`InLevelMainPageContext::SetOWEndlessLevelScoreVisible` 的实际行为是：

```
mov  rcx,[rsi+0x20]          ; this+0x20 = 内层 UI 根 GameObject（全类 45 次访问 / 34 个方法）
call GameObject::get_transform()
mov  rdx,[rip+0x79183e1]     ; 面板名 —— 静态引用槽，运行时才填
call Transform::FindChild(string)
...
call SetActive(ntf[+0x1])
```

**只有一处 `FindChild`，名字是单个静态引用槽** ⇒ 0x2F7 这个事件只控制**一个**面板。
另一个面板不归它管，所以改 `isExtra` 怎么试都不会亮。

### 3.2 正确的拓扑

面板由 **plugin 是否存在**决定，两个 plugin 两条独立入口。
用 `callers.py who` 反查，继承关系也一并清楚了：

```
LevelScorePlugin                                   (基类, +0x38 active)
  ├─ LevelScoreDLCPlugin                           _ctor(actor) @0xd78bf0
  │     └─ 内部调 LevelScorePlugin::_ctor()  ← 证明是子类
  └─ LevelScoreDLCPluginV2                         _ctor @0x2510660

Lua ─→ LevelDesignManager::InitBattleScorePlugin(float,float,int)  @0x3668590
         └─→ LevelScorePlugin::Init(score,ratio,rank)  @0x2a9af00
               └─→ LevelScorePanel

Lua ─→ LevelDesignManager::EnableLevelScoreDLCPlugin(bool)         @0x364b1a0
         └─→ LevelActor::SetupLevelScoreDLCPlugin()               @0x906300
               └─→ new LevelScoreDLCPlugin(actor)                 @0xd78bf0
                     └─→ SetupUI()  （IFix 接管）
                           └─→ ExtraLevelScorePanel

Lua ─→ LevelDesignManager::EnableLevelScoreDLCPluginV2(
          bool active, LuaFunction enterFever, LuaFunction exitFever,
          LuaFunction enterClimax, LuaFunction exitClimax,
          bool autoFever, bool enableClimax)                       @0x364afd0
```

V2 的签名是决定性的：**带 4 个 `LuaFunction` 参数 + `enableClimax`**。
这说明 DLC/Extra 面板是 Lua 侧驱动的（狂热/高潮玩法），也解释了为什么
`EnableLevelScoreDLCPlugin` / `InitBattleScorePlugin` / `LevelScoreDLCPlugin::_ctor`
用 `callers.py who` 查全是「无静态调用者」—— 它们从 Lua 进来，不经过 C# 的 call 指令。

而 `LevelScoreDLCPlugin::SetupUI` 反汇编只剩 `WrappersManagerImpl::IsPatched`，
真实实现被 **IFix 热更新**接管（走 `GetPatch` + `ILFixDynamicMethodWrapper::Gen_Wrap_*`），
静态看不到挂载逻辑。这也解释了 `LevelDesignManager` 为什么有 2984 个方法、
`ILFixDynamicMethodWrapper` 有 13612 个 —— 整个热更层都在这里。

### 3.3 面板名从哪来（不用开游戏了）

11-06 的 `hud/_mem/mem2.bin`（2.4 GB 堆快照）里两个名字都是**明文**：

```
VA 0x62A418F8  "LevelScorePanel"         引用 1 处 @ 0x62896968
VA 0x62A3EF48  "ExtraLevelScorePanel"    引用 1 处 @ 0x628992A8
VA 0x0482C2F8  "LevelScorePlugin"        ← 类名池（0x4708000 区域，与 Assembly-CSharp.dll 交替）
VA 0x04884038  "LevelScoreManager"
```

两个引用点在同一 4 MB 区域（0x62707000）内相距 0x2900，是**同一 UI 页面的两个相邻节点**，
与 11-06 prefab 分析的「两套面板都在场景里、active 都是 0」完全一致。

## 4. 已知缺口与下一步

> **2026-11-07 12:xx 更新**：下面第 1、2 条的缺口已经解决，见 `docs/布局还原_20261107.md`。
> 结论摘要：继承链在 `bh3_types_full.txt` 里（`parentIdx`/`parent`，覆盖 98.4%），
> 元数据布局表的 `offset` 列全为 0 但名字/类型/大小齐全，按「祖先在前 + 声明顺序 + 递归对齐」
> 重算后得到 **36,465 类 / 595,240 字段** 的完整布局（`rea/_rea/bh3_layout_resolved.tsv`），
> 用代码反推的偏移对撞，命中率 **93.0%（按访问次数加权 96.2%，Assembly-CSharp 94.5%）**。
> 上一轮说「`bh3_layout5b.tsv` 缺 `LevelActor`」是 grep 漏了命名空间前缀，属误判。

1. ~~**继承链没合并**~~：已解决，走元数据而不是「偏移集合超集」反推。
2. ~~**有名率 9.3%**~~：已解决，名字来自元数据表而不是靠 getter 命名。
   剩余问题是**表本身漏字段**（`LevelActor` 在 `0x048..0x3e8` 之间缺项，导致整段漂移）。
3. **`[rip+0x79183e1]` 的面板名**：静态读不到（il2cpp metadata usage 槽，运行时填）。
   要确认就开一次游戏读 `base+0xB3A4E0`；不开游戏也能从「0x2F7 名字里带 OW」推断是
   `LevelScorePanel`。
4. **加个 `--class-only` 提速**：全量重跑现在要 17 分钟（扩窗后解码量变大近 4 倍）。
   可以对 pdata 长度 ≥ 0x120 的函数直接用 pdata、只对短函数扩窗，估计能回到 5 分钟。
   注：有了 `layout_fix.py` 之后，`field_layout.py` 主要退化为「校验器 / 未覆盖类的兜底」。
