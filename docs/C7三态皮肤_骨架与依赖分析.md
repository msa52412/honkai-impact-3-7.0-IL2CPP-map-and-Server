# C7 三态皮肤（原模型 / 04_01 / 04_02）骨架与依赖分析

> 目标：德丽莎 C7「月下誓约·予爱以心」的**原模型 + 04_01 + 04_02 三套外观都能在游戏内使用**，
> 且不改任何客户端文件（只做运行时动态加载）。

数据来源：7.0 客户端本地资源、7.6 客户端（`D:\BH3\BH3_v7.6.0_b6f1709c3910`）、
9.1 官方客户端（`D:\BH3\miHoYo Launcher\games\Honkai Impact 3rd Game`）。

## 一、结论摘要

| 项 | 原模型（BW 默认） | 04_01 | 04_02 |
|---|---|---|---|
| 资源在 7.0 本地 | ✅ 有（加密变体，客户端自己能读） | ❌ 无（7.6/9.1 才有） | ❌ 无（仅 9.1 有） |

## 二、骨架真相（本轮最重要）

### 2.1 04_01 的 8 个分件是 100% 同源

拿每个分件的 bindpose 去和 Body 的 202 个比对，**全部 100% 命中、残差 0.00e+00**：

| 分件 | bindpose | 在 Body 202 里命中 | 最大残差 |
|---|---|---|---|
| Hair | 37 | 37 / 37 | 0.00e+00 |
| Veil | 26 | 26 / 26 | 0.00e+00 |
| Eyebrow | 33 | 33 / 33 | 0.00e+00 |
| weapon01 | 1 | 1 / 1 | 0.00e+00 |
| weapon03 | 2 | 2 / 2 | 0.00e+00 |

说明 8 个 Mesh 是在**同一副 202 骨骨架上烘焙出来的不同子集**，不是各做一套骨架。

### 2.2 04_02 的 92 骨是 04_01 的子集

- 04_02 Body 的 92 个 bindpose 中，**51 个在 04_01 的 202 个里精确命中**（最大残差 2.38e-07）。
- 映射索引**连续递增**：04_02 的 130..180 → 04_01 的 40..90。
- 04_01 的 Hair（37 骨）有 17 根落在 04_02 的 92 骨里。
- **04_01 的 Veil（26 骨）在 04_02 里 0 命中** —— 04_02 没有面纱骨。

### 2.3 骨骼顺序是「名字的字母序」，不是层级顺序

用 `SMR.m_Bones`（`@0x9C`，count=92，前缀 count 自洽）逐项对齐，**82/92 精确匹配（残差 1e-06）**，
顺序如下：

```
[ 0..15]  Avatar_BW_C7_04_01_Hair_BL_A01..A05 / BL_B01..B03 / BR_A01..A05 / BR_B01..B03
[17..23]  Avatar_BW_C7_04_02_Hair_BL_A01..A05 / BL_B01..B02
[28]      Avatar_BW_C7_04_02_Hair_BL_Root
[34..39]  Avatar_BW_C7_04_02_Hair_BR_B01..B03 / BR_C01..C03
[40]      Bip001 Head
[41]      Bip001 L Calf
[42]      Bip001 L Clavicle
[43..57]  Bip001 L Finger1 / 11 / 12 / 2 / 21 / 22 / 3 / 31 / 32 / 4 / 41 / 42 / 5 / 51 / 52
[58..63]  Bip001 L Foot / Forearm / Hand / Thigh / Toe0 / UpperArm
[64]      Bip001 Neck
[65..81]  Bip001 R Finger* / Foot / Forearm / Hand / Thigh / Toe0 / UpperArm
[88..90]  Bip001 Spine / Spine1 / Spine2
[91]      Bone_PelvisTwist
```

**这是实现层面的关键**：字母序意味着「子集 ⊂ 超集」时相对顺序必然不变，
所以 04_01 的 202 个 bindpose 与基础模型的 `m_Bones` 顺序天然一致，
换件时**直接赋值 `sharedMesh` 即可，不需要重排骨骼数组**。

### 2.4 04_02 的 Body Mesh 是「两套皮肤通用」的合并网格

前 16 个 bindpose 全是 `04_01_Hair_*`，紧接着是 `04_02_Hair_*`，
然后才是 Bip001 身体骨。也就是说这个合并网格**同时挂了两套头发的骨骼**，
是给「不区分皮肤的 LOD 预览」用的通用模型，不是 04_02 独占。

## 三、结构对比：为什么必须分两条路线

### 3.1 04_01 是「纯换件」

模型单元 `01273761` 只有：

```
Mesh × 8 + AssetBundle × 1 + CharacterController × 1
```

**零个 GameObject、零个 Transform、零个 SkinnedMeshRenderer。** 它必须挂在别人的骨架上。

8 个 Mesh：`Body`(3 子网格/202 骨) / `Face` / `Hair`(37) / `Veil`(26) /
`Eyebrow`(33) / `EyeShape` / `weapon01`(1) / `weapon03`(2)。

### 3.2 04_02 是「自足整模型」

`00260C8E` 有 223 个对象：GameObject ×108 / Transform ×108 / Mesh ×1 /
SkinnedMeshRenderer ×1 / Animator ×1 / MonoBehaviour(AfterImage) ×1 / CharacterController ×1。

骨架树是标准 Bip001：

```
Avatar_LOD  [Animator, AfterImage]
  Bip001
    Bip001 Pelvis
      L/R Thigh → Calf → Foot → Toe0
      Bip001 Spine → Spine1 → Spine2
        L/R Clavicle → UpperArm → Forearm → Hand → Finger1..5 (各 3 节)
        Bip001 Neck → Bip001 Head
          Avatar_BW_C7_04_01_Hair_B_Root → ...   (04_01 头发骨)
          Avatar_BW_C7_04_02_Hair_BL_Root → ...  (04_02 头发骨)
          Avatar_BW_C7_04_02_Hair_BR_Root → ...
    Bone_PelvisTwist
Body  [Transform, SkinnedMeshRenderer]
```

### 3.3 材质槽对不上

| 材质槽 | 7.0 基础 C7 | 04_01 | 04_02 |
|---|---|---|---|
| body | `material_body_duelface` | `_material_body` | `_material_body` |
| hair | `material_hair` | 无（复用基础） | 无（复用基础） |
| veil | `material_veil` | `_material_veil_alpha` | **无** |
| skirt | **无** | `_material_skirt_alpha` | 无 |
| weapon_01 | `material_weapon_01` | `_material_weapon_01` | 无 |
| weapon_ex | `material_weapon_ex` | 无 | `_material_weapon_ex` |
| dualface | 同上 body | 无 | `_material_dualface` |
| body_effect | 无 | 无 | `_material_body_effect` |

**04_01 有裙摆（skirt）材质而基础模型没有** —— 这是换件唯一的槽位缺口，
裙摆应该合并在 Body 的 3 个子网格里，需要 Body 的 SMR 至少 3 个材质槽。

## 四、依赖分析

### 4.1 好消息：Mesh 与贴图零依赖

| 单元 | 外部依赖 |
|---|---|
| `01273761`（8 个 Mesh） | **0** |
| `01424B16` / `014DF0E1` / `01508FDA` / `01599118`（贴图） | **0** |
| `010278AD`（裙摆 anim） | **0** |

所以「只换 Mesh + 贴图属性，材质复用 7.0 原生」这条最简路线**完全不需要跨版本依赖**。

### 4.2 材质会牵出一串 shader

04_01 的材质单元各带 3~6 个外部 bundle，其中 4 个是它自己的贴图单元：

| 外部 CAB | 实际是 |
|---|---|
| `3af36e0a` | `014DF0E1` skirt_lightmap |
| `a126221c` | `01424B16` alpha_diss |
| `c8147ea5` | `01508FDA` veil_alpha_diss |
| `7025e060` | `01599118` veil_lightmap |
| `d3c1e1e4` | `0119B6EC` weapon_01 材质 |
| `65630798` / `dab1fdbe` | 7.0 本地已有 |
| `87151cf0` / `93b60edb` / `e7e02c42` / `ebd77c2f` / `f9be2373` / `ce9a387c` | 未知（shader / 公共贴图） |
| `c233ae09` | 基础 C7 公共资源（7.6/9.1 都有，7.0 无） |
| `c41844e3` | weapon shader（7.6/9.1 用；**7.0 用的是 `aca86bb5`**） |

### 4.3 版本分叉：bundle 命名规则不同

| 客户端 | `AssetBundle.m_Name` | externals 里的路径 |
|---|---|---|
| 7.0 | `7235902776606527566.unity3d`（数字） | `archive:/cab-xxx/cab-xxx` |
| 7.6 | `13061789817064023001.unity3d`（数字） | `archive:/cab-xxx/cab-xxx` |
| 9.1 | `CAB-e54ad8992da77103b190a95c08771d49` | `archive:/cab-xxx/cab-xxx` |

**7.6 与 9.1 的 04_01 材质 externals 完全一致**（`3af36e0a, 87151cf0, a126221c, e7e02c42, ebd77c2f`），
说明是同一份资源、只是打包方式不同。**7.6 的 04_01 更适合 7.0**（同一命名体系）。

### 4.4 04_02 prefab 的 3 个外部依赖

| fileID | CAB | 是什么 |
|---|---|---|
| 1 | `366d2782` | 未定位（9.1 全量包里） |
| 2 | `590e3d79` | ✅ `avatar_theresa_c7_material_lod.mat`（**基础 C7 公共材质**） |
| 3 | `d8adf828` | **RuntimeAnimatorController**（未定位） |

`590e3d79` 已在本批单元里找到（`007C4B87`），另有 `007C4EC3` =
`avatar_theresa_c7_common_model.fbx` —— 都是**基础 C7 的公共资源**。

**这说明 04_02 不是自足的，它复用基础角色的材质与公共模型。**
`d8adf828` 这个 Animator controller 是 04_02 能否「动起来」的唯一硬依赖。

## 五、实现方案

### 5.1 路线 B：04_01 网格热替换（推荐先做）

**前提**：基础 C7 模型的 `Body` SMR 绑 202 骨（由「04_01 是它的官方皮肤」推定）。

```
1. 运行时 LoadFromFile 04_01 的 6 个零依赖单元（模型 + 4 贴图 + 裙摆 anim）
2. LoadAllAssets(bundle) 取全部 8 个 Mesh —— 容器键只有 1 条（fbx 路径），
   靠 preloadIndex 0..8 区分，LoadAsset(路径) 只能拿到 1 个
3. 遍历角色的 SkinnedMeshRenderer，读 sharedMesh.name 匹配 Body/Face/Hair/Veil/...
4. 逐个 smr.sharedMesh = 04_01 对应 Mesh
5. 材质：优先复用 7.0 原生材质，只把 _MainTex / _LightMap 等槽位换成 04_01 贴图
6. 裙摆：Body 有 3 个子网格，需要 3 个材质槽（body / skirt_alpha / ?）
```

**优点**：零跨版本依赖，改动面最小，骨架已在内存。
**风险**：基础模型的 SMR 数量/名字未知，裙摆槽位可能不够。

### 5.2 路线 A：04_02 整体实例化

```
1. LoadFromFile 04_02 的 prefab 单元 + material_lod + common_model
2. Instantiate(avatar_lod.prefab)
3. 挂到角色根节点下，隐藏原模型
4. Animator.runtimeAnimatorController 换成 7.0 基础 C7 的
   （骨骼是标准 Bip001 命名，名字能对上）
5. 材质用 04_02 自己的 4 个（需解决 c41844e3 shader 缺失）
```

**优点**：自足、骨架自带、无槽位问题。
**风险**：Animator controller 缺失会 T-pose；shader 版本分叉可能粉材质。

### 5.3 三态切换

原模型必须保住，所以切换是「替换」而不是「破坏」：

| 目标态 | 操作 |
|---|---|
| 原模型 | 恢复原始 sharedMesh + 原始材质引用（启动时先备份） |
| 04_01 | 路线 B 换件 |
| 04_02 | 路线 A 实例化 + 隐藏原模型 |

**关键：启动时必须先备份原模型的 8 个 SMR 的 `sharedMesh` 与 `sharedMaterials`**，
否则切到 04_01 后回不去。

## 七、工具

本轮新增/修正：

| 工具 | 作用 |
|---|---|
| `tools/sf_ext_cabs.py` | 提取 SerializedFile 的 externals CAB 名（顺序即 fileID-1） |
| `tools/bundle_index.py` | 建「bundle 名 → 文件 + 容器键」索引，支持 `--find` 反查 |
| `tools/prefab_deps.py` | 列出一个单元的所有 PPtr，区分内部引用与外部依赖 |
| `tools/bindpose_match.py` | 比对两个 Mesh 的 bindpose 集合，判断是否共用骨架 |
| `tools/bone_map2.py` | 用 `SMR.m_Bones` 顺序把 bindpose[i] 反推成骨骼名（可导 CSV） |

修正的坑：

- **bindpose 是 row-major 存储**（平移在 index 3/7/11，第 4 行恒为 `0,0,0,1`），
  按 column-major 读会把平移读成 0。
- **`SMR.m_Bones` 不在固定偏移**：BH3 的 SMR 头部布局与标准 Unity 不同，
  要用「连续 12 字节步长、pathID 命中本文件 Transform」自动定位（本文件在 `@0x9C`）。
- **定位骨骼数组时 pid 集合必须包含解析失败的 Transform**，否则连续性会断在它们身上
  （04_02 有 3 个 Transform 数据异常，`bad child count`）。
