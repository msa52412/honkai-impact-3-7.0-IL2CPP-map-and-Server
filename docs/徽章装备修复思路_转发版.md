# BH3 7.0 徽章装备修复思路（可转发）

整理日期：2026-11-08。适用于本文所述本地服务器源码结构，供其他开发者按自己的项目移植。此问题通过服务端协议和持久化修复，不需要客户端运行时注入。

## 一、根因

“有徽章列表”和“能够佩戴徽章”是两条不同流程。原服务端虽然可以返回徽章收藏列表，但缺少MedalOpReq（451）的装备操作处理器，且GetMainDataRsp.OnMedalId固定下发0。结果是装备请求不能完成；即使只临时改界面或回一个成功包，重新取主数据仍会恢复成未佩戴。

完整修复必须同时完成：接收装备/卸下操作、保存每个账号的选择、在主数据中持续返回相同选择。

## 二、协议及字段

| 请求/响应 | 编号 | 用途 |
| --- | --- | --- |
| GetMedalDataReq / GetMedalDataRsp | 449 / 450 | 返回拥有的徽章列表及到期时间 |
| MedalOpReq / MedalOpRsp | 451 / 452 | 佩戴、替换、卸下 |

MedalOpReq字段：tag1 op，tag2 on_id，tag3 off_id。op=1为MEDAL_WEAR，op=2为MEDAL_OFF。

MedalOpRsp字段：tag1 retcode，tag2 op，tag3 on_id，tag4 off_id。返回码为SUCC=0、FAIL=1、NO_OWN=2、EXPIRED=3、OFF_ID_ERROR=4。移植到其他版本时应核对其实际Proto定义，不只看字段名。

## 三、装备逻辑

以服务端会话UID确定账号，不信任客户端提供的账号。

1. 读出当前有效佩戴ID，默认0。
2. 拒绝未知操作。请求off_id非0时，必须等于当前佩戴ID，否则返回OFF_ID_ERROR，保持原选择。
3. 佩戴时验证on_id存在、账号拥有且未到期；失败分别返回NO_OWN或EXPIRED。
4. 成功佩戴：on_id返回新ID；off_id返回被替换的旧ID，同一枚重复佩戴时返回0。
5. 成功卸下：on_id返回0，off_id返回原佩戴ID。
6. 成功结果先提交持久化并回读验证，再发送452响应；成功后补发最新主数据，使界面与存档一致。失败不覆盖原选择。

示例：当前A，装备B，请求wear/on=B/off=A，成功返回on=B/off=A；卸下B则返回on=0/off=B。

## 四、持久化与登录同步

新增SQLite表MedalEquipment，以owner_uid作唯一账号索引。核心数据为OwnerUid、OnMedalId、LimitedEndTime；项目IRow还包含Id、CreatedAt。

选用独立表，而不是只给在线User对象加字段，可避免旧User缓存或序列化路径把佩戴选择覆盖。读写通过项目Global.Table/SqlTable封装，提交后回读确认。并发修改以服务内锁串行化。

主数据处理器中把原来固定0改成：

```csharp
getMainDataRsp.OnMedalId = MedalService.Current(user.Uid);
```

Current需要检查徽章仍有效；不存在或过期时对客户端返回0。GetMedalDataRsp的列表应与此处的拥有/到期规则一致。只改451/452而不改主数据，仍会在刷新或重新登录时显示未佩戴；只改主数据则不能正常替换/卸下。

## 五、本地服额外策略，可按需取舍

本项目原本采用“表中徽章全部拥有”的本地服策略，因此IsOwned检查有效MedalData编号即可；这不是装备协议必须要求。其他服务器如果有真实领取记录，应改为检查该账号的实际拥有数据。

本地表共130枚，105枚永久、25枚限时。永久徽章EndTime=0；限时判定取原始MedalData.json的timeType=2或3。限时徽章在账号首次取数时生成并持久保存一个999天截止时间，之后读取、切换徽章和重启不续期。999天与所有限时徽章共用截止时间是本地服选定策略，不应当成官方通用规则或修复装备功能的必要条件。

## 六、移植文件

按本项目根目录的相对路径：

- 新增server-v2/Server/GameServer/MedalService.cs
- 新增server-v2/Server/Handlers/MedalOpReqHandler.cs
- 修改server-v2/Server/Handlers/GetMedalDataReqHandler.cs：使用统一服务返回列表/到期时间
- 修改server-v2/Server/Handlers/GetMainDataReqHandler.cs：OnMedalId读取持久化选择

依赖现有Common.Resources.Proto中的MedalOpReq、MedalOpRsp、MedalOpType，及Global.Table、SqlTable、MedalData读取器。Handler通过PacketCmdId属性交给现有包工厂注册；移植项目采用手动注册时须补上451映射。不要把空方法的客户端rea导出类当作服务端处理器。

移植这些逻辑并重新编译对方自己的Server项目即可。当前整包Server.dll还含家园、深渊等其他修改，不建议只为徽章修复直接替换他人的整包DLL。

## 七、验证方法和已有边界

至少验证：首次无佩戴、装备A、替换B、重复佩戴、卸下；不存在编号、错误旧ID、未知操作、过期徽章拒绝；两个账号互不影响；主数据与数据库一致；重新连接数据库、重启服务端和重新登录后仍保存；限时截止时间不会重置。

原修复在真实130条徽章数据上进行协议序列化、保存/回读、非法输入、账号隔离及999天测试，共405项通过。用户已确认徽章可装备。证据与测试源码位于_launch/medal_overload_fix/test.log、MedalFixTests.cs。

这确认的是装备、显示和保存流程。舰桥读取到徽章属性和技能配置，并不等于已经测量所有战斗Buff的实际加成；如要声明战斗效果正确，应另进关卡核对挂载和伤害。

本文所说徽章是Medal装备系统，与家园3900/3901协议中的badge字段无关。本次整理说明未修改游戏、数据库或服务端运行状态。
