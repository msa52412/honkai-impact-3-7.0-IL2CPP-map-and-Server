# BH3 7.0 技术路线总览（AI 交接文档）

> 用途：把 7.0 这套已经跑通的方案完整交给另一个 AI / 另一个自己，避免重复试错。
> 所有数字、偏移、字节序列均为**本机实测值**，核对时间 2026-11-07。
> 只讲手法与机制，不含游戏资源再分发。

---

## 0. 三十秒摘要

7.0 是一个**开放的实验台**：

- 客户端是 Unity **2017.4.18f1** + 米哈游定制引擎，反作弊 ACE 在 7.0 上是停止状态
- 通过 `version.dll` 侧加载把自写 DLL 塞进 `BH3.exe`，**通道已验证可用，ACE 不拦**
- 两条改逻辑的通道：**启动早期静态补丁**（改字节）＋ **运行中共享内存信箱**（让游戏主线程替我们调函数）
- 服务端 `server-v2`（.NET 8 + SQLite）源码在手，协议定义 `SeaRelWin8.4.0.proto` 全量在手（4277 message / 720 enum）
- 资源是标准 `UnityFS` 加一层私有头，可解包、可重建、可用 `AssetBundle.LoadFromFile` 动态加载
- **元数据（`global-metadata.dat`）没解开，但 7.0 不需要它**——函数序言完整（13.2 万个），静态就能定位任意函数

一句话定位：**7.0 能改逻辑、改数值、跳校验、换资源、画 Overlay，唯独不能换模型/加新动作（引擎渲染层限制）。**

## 2. 总体架构：两条通道

```
┌──────────────────────────────────────────────────────────────┐
│ 游戏进程 BH3.exe                                              │
│                                                              │
│  BH3.exe 启动                                                 │
│      │ 系统按名加载 version.dll（同目录优先于 System32）        │
│      ▼                                                        │
│  version.dll  ← 侧加载垫片，17 个导出全部转发给 system32         │
│      │ 读 libraries.txt（一行一个 DLL）                        │
│      ▼                                                        │
│  bh3bypass.dll ← 注入载荷                                     │
│      │ DllMain 只起线程（加载器锁内不能 LoadLibrary）           │
│      │ 轮询等 UserAssembly.dll 就绪 → 核对原始字节 → 写补丁      │
│      ▼                                                        │
│  [通道A 静态补丁] 资源校验恒假 / 弹窗压制 / 校验结果恒真         │
│                                                              │
│  ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ←   │
│      ↑ 共享内存信箱（Python 工具 → 游戏主线程）                 │
│      │ {target, args[4], ret, seq, done}                       │
│  MonoClientPacketConsumer.Update 钩子（每帧取走执行）           │
└──────────────────────────────────────────────────────────────┘
              ▲
              │ ReadProcessMemory / WriteProcessMemory
              │ VirtualAllocEx / VirtualProtectEx
┌─────────────┴────────────────────────────────────────────────┐
│ 外部工具进程（Python）：app\tools\*.py                        │
└──────────────────────────────────────────────────────────────┘
```

| 通道 | 时机 | 能做 | 不能做 |
|---|---|---|---|
| **A 静态补丁** | 启动早期，UA 刚映射 | 拦住校验、压制弹窗（必须先于游戏逻辑） | 只能等长字节改写 |
| **B 运行时信箱** | 游戏运行中 | 调任意 il2cpp / 引擎函数、构造对象、读写字段 | 依赖主循环在跑；碰运行时锁会死锁 |

**为什么不能 `CreateRemoteThread` 直接调托管函数**：il2cpp 托管函数必须在附着了 il2cpp 运行时的线程上执行，远程线程没附着，拿线程锁会失败。所以必须借游戏主线程。


产物是 `x86_64` DLL，导入 `api-ms-win-crt-*`（Win10+ 自带，无需额外运行时）。

### 3.4 四个必踩的坑

1. **`DllMain` 里 `UnityPlayer.dll` 还没进模块表**（日志实测 `UnityPlayer = 0x0`）。因为 `version.dll` 是 `UnityPlayer.dll` 的依赖，在它加载过程中就被拉起来了 → 想 hook UnityPlayer 导出必须起线程轮询 `GetModuleHandleA`。
2. **`BH3Base.dll` 在 `DllMain` 时已就位**（ACE 集成模块）。目前不拦，但每次改载荷都要重新验"能否进到登录界面"。
3. **导出签名必须全对**：mingw 的 `winver.h` 把 `VerFindFileA/W` 声明成非 const `LPSTR`，`VerInstallFileA/W` 是 8 参数。照 MSDN 抄会编不过。
4. **加载器锁内不能 `LoadLibrary`**，所有实活必须放到新线程。

## 4. 通道 A：静态补丁（7 处，全部实测落地）

所有目标都在 `UserAssembly.dll`，用**文件内 RVA**定位，运行时加模块基址：

```c
BYTE *ua = (BYTE*)GetModuleHandleW(L"UserAssembly.dll");
BYTE *fn = ua + RVA_XXX;
```

### 4.1 补丁表

| # | RVA | 函数 | 原始字节（实测） | 写入 | 作用 |
|---|---|---|---|---|---|
| 1 | `0x02FAD6D0` | NeedRefreshMemoryMappedData | `48 89 5c 24 18 55 48 8d 6c 24 a9 48 81 ec 90...` | `33 C0 C3` | 永不重建 asb.dat |
| 2 | `0x02FADA80` | NeedToVerifyBlocks | `40 53 48 83 ec 20 48 8b d9 33 c0 b9...` | `33 C0 C3` | 跳过块校验 |
| 3 | `0x02FAD520` | NeedDownloadPatchX | `40 57 48 83 ec 20 48 8b f9 b9 3c 19...` | `33 C0 C3` | 补丁块不触发下载 |
| 4 | `0x02753570` | NeedShowDownloadResourceDialog | `40 57 48 83 ec 20 48 8b f9 b9 17 b6...` | `33 C0 C3` | **压掉"要求下载"弹窗** |
| 5 | `0x02FAD470` | NeedDownloadAsbX | `40 53 48 83 ec 20 48 8b d9 b9 84 19...` | `33 C0 C3` | ASB 不触发下载 |
| 6 | `0x01F1A600` | OnCheckStreamingAssetBundleComplete | `48 89 5c 24 08 57 48 83 ec 30 48 8b d9 0f b6 fa` | `FF 25 00 00 00 00` + 8 字节指针 | 校验结果恒真 |
| 7 | `0x0302A4F0` | UIUtil.IsAvatartDoNotShow | `40 53 48 83 ec 20 48 8b d9 b9 7c f3 00 00 e8...` | `FF 25 00 00 00 00` + stub | 放行隐藏角色（见第 11 节） |

1–5 是同构的"恒返回 false" = `xor eax,eax; ret`（bool 返回 0）。
6 不能这么改（返回值被当"成功"走后续逻辑），所以 jmp 到自建 stub：`B2 01`（`mov dl,1`）+ `B0 01` + `C3`。
7 需要按参数判断，走入口跳板 + 代码洞。

### 4.2 工程要点

- **幂等**：写之前先读，已是目标字节就跳过（防重复注入 / 热重载破坏）
- **改保护**：`.text` 是 `PAGE_EXECUTE_READ` → `VirtualProtect` 成 `RWX` → 写 → 改回 → `FlushInstructionCache`
- **字节核对强制**：不匹配就拒绝写入并记日志，绝不"盲写"
- **只改进程内存**，磁盘上的 `UserAssembly.dll` 一个字节都不动
- **每条补丁落地都写日志**：`app\bh3bypass.log`（当前 88 KB，含每次启动的核对结果）

日志样例（`bh3bypass.v8.log`，说明 6 处全部命中并写入）：


### 4.3 ★ 绝对不能补的函数

**`GetDownloadBlockSize`（RVA `0x02753210`）——禁止打补丁。**

恒返回 0 会让 `DownloadResources` 走 `==0` 分支**跳过下载管理器初始化**，进主场景后对空管理器虚调用 → `unityplayer call [rax+0x48]` **崩溃**。
弹窗压制由 #4 独立完成，两者必须解耦。

## 5. 通道 B：共享内存信箱（运行时调用）

### 5.1 钩点

找一处**每帧必调**的托管方法：`MonoClientPacketConsumer.Update`。
入口写 14 字节跳板 `FF 25 00 00 00 00` + 绝对地址 → 跳到自建 stub。

### 5.2 stub 逻辑

```
保存易失寄存器
读信箱：[target][arg0..arg3][seq][done][ret]
seq 变化且 target 非空
  → 布置 rax=target, rcx/rdx/r8/r9=args，call
  → 写回 [ret]，置 done
恢复寄存器
执行被覆盖的原指令，跳回原函数
```

Python 侧：`WriteProcessMemory` 填信箱 → 轮询 `done` → 读 `ret`。

### 5.3 限制

- **只直通 4 个寄存器参数**（rcx/rdx/r8/r9）。5–8 参需要另在栈上布置（工程里有封装）
- **超时基本等于游戏线程已炸**（例如传了失效对象指针）。先查进程状态再判断
- **★ il2cpp 包装层不能从信箱调**：例如 `Mesh.SetVertices`（RVA `0x3498500`），它内部要拿 il2cpp 线程锁，而主线程正卡在 Update 钩子里 → **自死锁**（不崩、不返回）。只有不碰运行时锁的纯读函数（如 `get_vertexCount`）可以随便调

## 6. 内存原语（实测全部可用）

| 原语 | 参数 / 用法 |
|---|---|
| `OpenProcess` | `0x0410 \| 0x0020 \| 0x0008 \| 0x0010` |
| `VirtualQueryEx` | 枚举区域、扫堆 |
| `ReadProcessMemory` | 任意读取 |
| `WriteProcessMemory` + `VirtualProtectEx` | **写只读页**：改保护后可写、回读一致 |
| `VirtualAllocEx` | 在目标进程分配大缓冲（实测 1 MB 可写） |

### 两条硬约定

1. **读堆必须分块（16 MB）**。一次性读整块会让本进程申请等量内存，把系统提交打爆 → 游戏 OOM 崩在 `RVA 0x445D7D`。
2. 大块数据（如 22 万字节顶点数组）走 `VirtualAllocEx` 分配，不用 scratch 页（scratch 只有几 KB）。

## 7. 定位托管对象：按 klass 扫堆

### 7.1 流程

```
1. 从字符串命中反查 klass（tools\rt_class.py --name Xxx）
   链路：字符串 → 指向它的指针 → 该指针所在结构 +0xA8 是类名
2. 用 klass 值在全部可读内存里搜 8 字节匹配
3. 每个命中点当"对象起始"，逐条校验：
   a. 地址 > 0x100000000        （低区是元数据/类表，不是 GC 堆）
   b. [obj+0x08] == 0           （monitor 为空）
   c. [obj+0x10] >= 0x10000 且可读（m_CachedPtr）
   d. [native+0x38] >= 0x10000 且可读（如 Mesh 的 blk）
4. 全部通过才允许调方法
```

### 7.2 ★ 假实例会崩游戏

klass 结构里存在 `[klass+0x98] == klass` 这类自指针，会产生大量**假实例**。
对假实例调 `get_name`，Unity 会把类名字符串当 native 指针解引用：

```
Read from location ffffffff  → Access Violation
```

**已踩过两次**（`RBX=0x5075cf40`）。第 3 步的 native 链校验是**强制项**，不是可选项。

### 7.3 klass 地址每进程都变

klass = 元数据基址 + 固定偏移，基址随 ASLR 变。实测某进程 `0x9615490`，下一进程 `0x8c15490`。

**正确做法**：每次都从"已知对象的 `+0`"或字符串链重新求，**严禁复用上次的常量**。

## 8. 手写托管对象（给 il2cpp 函数传参用）

### 8.1 String

```
+0x00  klass      (String 的类指针)
+0x08  monitor    (0)
+0x10  length     (int32)
+0x14  chars[]    (UTF-16LE)
```

### 8.2 数组

```
+0x00  klass
+0x08  monitor
+0x10  bounds       (0 表示一维无边界表)
+0x18  max_length   (int64)
+0x20  元素数据…
```

用处：构造 `Matrix4x4[]`（补齐 bindpose，228 × 64 B）、`Vector3[]`（顶点数组）。

### 8.3 klass 从哪来

**不要另找**，从同类型现成对象取 `+0`：
- String klass ← 任意活字符串（如 `get_name` 返回值）
- `Matrix4x4[]` klass ← `Mesh.get_bindposes` 返回数组的 `+0`

实测状态：手写 String 被引擎正常接受；手写数组用于顶点/bindpose 成功。

## 9. 资源：解析、重建、动态加载

### 9.1 格式现实

`.wmv` / 单元是**私有头**：标准 `UnityFS\0` 之后的前 54 字节被替换，version 字段是乱码，可能含加密块。
→ `AssetBundle.LoadFromFile` 直接吃必然返回 0。

头 64 字节实测（7.0 与 7.9 **同构**，同一套 `ce 4e ee 1e ...` 加密标志，没有所谓 `mr0k` 私有块）：

```
55 6e 69 74 79 46 53 00 ...  ce 4e ee 1e ...
```

### 9.2 处理链

```
.wmv（私有头）
  → wmvkit 解析私有头 + 解块
  → mkvfs.build_bundle 重建标准 UnityFS
  → AssetBundle.LoadFromFile 成功
```

**实测有效参数组合**：

| 项 | 必须值 | 说明 |
|---|---|---|
| version | **6** | 2017.4 不认 v7（`repack_plain` 默认 v7 会返回 0） |
| flags | **0x843** | `0x800` + 块合并 `0x40` + LZ4HC `0x3`；`0xc0` 组合不行 |
| 块压缩 | LZ4HC | `ci < ui` 才被接受 |

### 9.3 类型哈希必须改写

`enable_type_tree = 0` 时，Unity 拿 bundle 里的 `oldTypeHash` 与引擎内置类定义比对，不一致直接报
`contains run-time classes 'X' of incompatible version` 并**整包拒收**。

→ 重建时把 16 字节哈希改成目标客户端值（映射表 `_ext\clsmap70.json`）。
MonoBehaviour（classID 114）不改——那 16 字节是脚本 GUID，改了没用。

### 9.4 ★ 同一内容每进程只能加载一次

实测：同一份内容换个文件名再 `LoadFromFile`，**仍然返回 0**。
Unity 按 **bundle 内部身份**（AssetBundle 对象名 + 内部 CAB 列表）去重，**不是按磁盘路径**。

→ 正确做法是复用已加载的 bundle 句柄（`LoadAsset` 可对同一个 VA 反复调）。

## 10. 渲染侧

### 10.1 裸写顶点缓冲不管用

```
mesh+0x10  → native
native+0x38 → blk
blk+0x60   → 顶点缓冲指针
blk+0x6c   → 顶点容量
```

直接 `WriteProcessMemory` 到 `blk+0x60` 指向的缓冲：`get_vertices` 立刻能读到新值，**但画面不变**——只改了 CPU 副本，没提交 GPU。

### 10.2 必须走函数通道

```
unityplayer!0x7EBBB0(native, data, len)
```

调用后画面刷新。这是"改渲染数据"的唯一有效路径。

## 11. 实战范例：放行被隐藏的角色（完整可复用模板）

`app\tools\keqing_visible.py` 是**最完整的通道 B 范例**，也是最好的补丁模板。

### 11.1 反汇编实证（UserAssembly.dll）

```
UIUtil.IsAvatartDoNotShow(AvatarDataItem) @ 0x18302A4F0     （RVA 0x302A4F0）
    40 53                 push rbx
    48 83 EC 20           sub  rsp,0x20
    48 8B D9              mov  rbx,rcx            ; rcx = AvatarDataItem
    B9 7C F3 00 00        mov  ecx,0xf37c         ; 方法初始化探针 token
    E8 ..                 call 0x1835D7F80
    ...
    48 8B 70 20           mov  rsi,[rax+0x20]     ; AvatarClassDoNotShow
    E8 ..                 call get_ClassId
    E8 ..                 call List<int>.Contains
    75 1D                 jne  → mov al,1; ret     ; ★ 按 classID 隐藏
    8B 53 1C              mov  edx,[rbx+0x1C]     ; avatar.avatarID
    E8 ..                 call List<int>.Contains
    74 12                 je   → 0x18302A590
    B0 01                 mov  al,1                ; ★ 按 avatarID 隐藏
    E9 ..                 jmp  0x18302A600         ; ★ 尾调用协作角色判断

UIUtil.IsCollaborationAvatarDoNotShow(...) @ 0x18302A600

```

**关键结构**：`IsAvatartDoNotShow` 尾部是 `jmp 0x18302A600`（尾调用）。
所以只要在它入口对 `avatarID == 2001` 提前 `return false`，"按 classID 隐藏"、"按 avatarID 隐藏"、"协作角色隐藏"三条判据**一次全绕过**。

### 11.2 补丁形态

入口 14 字节（正好到 `call 0x1835D7F80` 之前）改为绝对跳转：`FF 25 00 00 00 00 <stub_va>`

代码洞（`VirtualAllocEx` 分配，双向都用绝对跳转，不依赖 ±2GB 距离）：

```
00  48 85 C9              test rcx,rcx
03  74 0C                 jz   orig            ; avatar == null → 走原逻辑
05  8B 41 1C              mov  eax,[rcx+0x1C]  ; avatarID
08  3D D1 07 00 00        cmp  eax,2001
0D  75 02                 jne  orig
0F  EB 1C                 jmp  false_ret
11  <原始 14 字节>
1F  FF 25 00 00 00 00     jmp  qword [rip+0]
25  <resume_va = 0x18302A4FE>
2D  31 C0 C3              xor eax,eax ; ret
```

作用面：**只有 avatarID == 2001 被放行**，其它角色（含 316 / 901 等联动角色）行为完全不变。

### 11.3 用法

```bash
python keqing_visible.py status      # 进程、模块基址、当前入口字节
python keqing_visible.py apply       # 打补丁
python keqing_visible.py revert      # 还原入口字节
python keqing_visible.py wait 600    # 等游戏起来后自动打
python keqing_visible.py apply --avatar 2001
```

状态文件 `app\tools\.keqing.json`（有成功记录：pid 3720、stub 0x3BF02000）。
入口字节当前实测仍匹配，补丁对当前客户端**依然有效**。

### 11.4 这个模板能推广成什么

同一手法可以套到任何"按 ID 过滤"的函数上：`mov reg,[rcx+偏移]` + `cmp reg,常量` + 条件跳转到 `xor eax,eax; ret`。
找出过滤函数的方法：在 `.text` / `il2cpp` 段搜 `B9 imm32` + `E8 rel32` + 紧跟 `84 C0 0F 8x`（方法初始化 + `test al,al` + `jne`），7.0 的候选非常少。

## 12. 元数据现状（7.0 的难度量化）

7.0 的 `global-metadata.dat` **没解开，但也不需要解开**。实测：

| 指标 | 7.0 | 7.9 |
|---|---:|---:|
| 大小 | 56.4 MB | 68.5 MB |
| 头 8 字节 | `MHY\0 71 4D 2F 65` | `MHY\0 00 00 00 00` |
| 标准 sanity `AF 1B B1 FA` | ❌ 无 | ❌ 无 |
| 尾部 `-0x4008` 自引用（老 miHoYo 格式判据） | ❌ 不成立 | ❌ 不成立 |
| **4 KB 块体平均熵** | **6.28** | **7.17** |
| 高熵块（>7.5）占比 | **58.2%** | 76.1% |
| 明文 1 KB 窗口 | 1.62% | 0.93% |
| 明文区可读标识符 | 7,636 | 9,316 |
| `UIUtil` / `AvatarDataItem` / `IsAvatartDoNotShow` | 均**不在**明文 | 均**不在**明文 |
| UnityPlayer.dll 内 `global-metadata.dat` 字符串 | 0 次（已混淆） | 0 次 |

**两个可用线索**：

1. **分块加密，粒度 4 KB**。明文区间全部按 4 KB 对齐，说明部分块根本没加密。
2. **保留了标准 IL2CPP 字符串表片段**，两版字节完全一致：

   ```
   09 00 00 00 "MoleMole."  13 00 00 00 "MonsterAIController"  11 00 00 00 ...
   ```

   7.0 在文件偏移 `0x1DEDBF2`，7.9 在 `0xBB25B2`。

**结论**：7.0 静态解算法是"中等，1–2 周"；但正确解法是**运行时 dump 内存**（"低，1–3 天"），因为 7.0 的外部读写没有拦截（ACE 服务 Stopped），而 IL2CPP 运行时不可能每次访问都解密，内存里通常明文常驻。

**验证成本极低的第一步**（2 小时）：起 7.0，扫内存找 `AF 1B B1 FA`。
找到 = 内存明文 = 直接 dump 喂 Il2CppDumper；找不到 = 字段级加密，立刻转指纹迁移路线。

> ⚠️ 7.9 上同样思路**无效**：Morax 框架下每个字段单独加密、内存里也是密文，dump 出来还是密文。7.0 是否同样，上述实验可判定。

## 14. 与 7.9 的差异（迁移视角）

| 指标 | 7.0 | 7.9 |
|---|---:|---:|
| UserAssembly | 182 MB | 249 MB |
| `il2cpp` 段 | 103.2 MB | 227.6 MB |
| `40 53` 函数序言 | **131,894** | **468** |
| `CC CC CC CC` 填充 | **732,447** | 12,750 |
| `.tvm0` 段 | 11.3 MB | 7.7 MB |
| TVM 入口跳板（`E9 rel32` + `CC`） | — | **71 个**（占 0.03%） |
| 外部进程读写 | ✅ 可用 | ❌ ACE 拦死（err=5） |
| 元数据头 | `MHY\0 71 4D 2F 65` | `MHY\0 00 00 00 00` |

**7.0 的核心价值是"名字"**：

1. 13.2 万完整函数序言 → 可完整反汇编、切成独立函数单元 → 能建"函数指纹库"
2. 两版 `.rdata` 可读字符串交集 **92.8%**（8406 / 9058）→ 同源证据，跨版本匹配可行
3. 现成的补丁框架 + 行为验证台（改完立刻看效果，随时 revert）

**7.9 的核心价值是"内容"**：新角色、新活动、新资源只存在于 7.9。

**转移路线**：用 7.0 建指纹（调用图 + 常量 + 指令 n-gram，**不要用字节哈希**，重编译全变），拿 7.9 的 228 MB 明文段匹配。
7.9 独有情报：`.rdata` 里有 **1,638 个 `类名_方法名` 形式的 Profiler marker**，其中 32 个与 Avatar/UI 相关（如 `AvatarFilterAndSort_RefreshShowList`），7.0 一个都没有——这些在运行时内存里是真实对象，可作校准点。

### ⚠️ 迁移时别踩的两个坑（7.9 实测）

1. **字符串反查对业务层无效**。两版都是 `lea` 引用率约 29%（7.0 30.0% / 7.9 28.7%），但**含 `Avatar` / `UIUtil` / `MoleMole` 的命中数是 0**。游戏 C# 业务字符串全在加密的 metadata 字符串表里，不在 `.rdata`。
2. **字符串是后缀合并存储**。`lea` 常指向字符串**中间**（如瞄 `lua_setmetatable` 实际落在 `ua_setmetatable`）。匹配必须按"落在区间内"判断，不能按"等于起点"——否则会得到 0% 的错误结论。

## 16. 操作规程（给接手的 AI）

### 必做

1. **改字节前先读、先比对、再写**。不匹配就放弃并记日志。
2. **所有日志追加写**，包含"当前字节"，便于事后确认到底改没改上（`bh3bypass.log` 就是这个格式）。
3. **改完立刻能 revert**。`keqing_visible.py` 的 status/apply/revert 三件套是标准形态。
4. **只在进程内存里改**，不碰磁盘上的 `UserAssembly.dll` / `BH3_Data`。
5. **每次改载荷后重新验"能否进到登录界面"**——ACE 目前不拦，不代表以后不拦。
6. **读堆分块（16 MB）**。
7. **对象指针用前必过 native 链校验**。
8. **klass / 模块基址每进程重算**，不复用常量。

### 严禁

| 禁止项 | 原因（实测后果） |
|---|---|
| 补 `GetDownloadBlockSize` @ `0x02753210` | 下载管理器不初始化 → 主场景虚调用空指针 → **崩溃** |
| 对假实例调方法 | Unity 把类名字符串当指针解引用 → `Read from ffffffff` **AV 崩溃** |
| 一次读整块堆内存 | 本进程 OOM，**游戏崩在 `RVA 0x445D7D`** |
| 从信箱调 `Mesh.SetVertices` 等 il2cpp 包装层 | 抢 il2cpp 线程锁 → **自死锁**（不崩不返回） |
| 无参调 `il2cpp_get_api_table` | 7.9 实测是写入式初始化（`mov [rcx+rax*8], rdx`），RAX=0 时写无效地址 → **AV** |
| 在 `DllMain` 里做事 / `LoadLibrary` | 加载器锁死锁 |
| 改磁盘上的 UA / 客户端文件 | 签名校验，且不可逆 |

### 排障顺序

```
1. app\verhook.log        → 载荷有没有被加载进去
2. app\bh3bypass.log      → 每处补丁的"当前字节"对不对（99% 的问题在这里）
3. 崩溃 → %LOCALAPPDATA%Low\miHoYo\Honkai Impact 3rd\Crashes\<时间戳>\error.log
4. 进不去登录界面 → 先移除 libraries.txt 里的载荷，确认是载荷问题还是客户端问题
```
