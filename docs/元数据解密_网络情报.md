# 元数据解密 · 网络情报与路线修正

> 时间：2026-11-07 11:00
> 背景：本地静态分析全部碰壁（无 AES 表、无密钥复用、内存无明文镜像、xref=0）。
> 上网核对后，四个"碰壁"全部有了物理解释。

## 0. 一句话结论

**7.0 的 `global-metadata.dat` 用的不是"整文件加密再解出来"，而是米哈游自研的
字段级混淆（Morax 血统）+ 腾讯 TVM 虚拟化的加载器。**
"解出明文文件"这条路在本 build 上结构性地不成立；正路是**运行时用游戏自己的
il2cpp API 枚举**，而这张 API 表就在 `UserAssembly.dll` 里，有 1203 项。

## 2. 崩坏3 元数据到底被做了什么（DJ Katy 实测，4.3 版）

不是"加个密"，是**五层数据混淆**：

1. **第一层整文件加密** —— 文件里每隔 `0x353C0` 出现 `0x40` 字节高熵块，嵌在合法表内
2. **头部重排** —— 标准 `Il2CppGlobalMetadataHeader` 是 `0x110` 字节，崩坏3 是 `0x158`，
   字段顺序被打乱，还多塞了 `0x48` 字节未知数据（人工剪切粘贴的痕迹，成组保序）
3. **字符串表整块移除** —— 文件里**没有字符串字面量表**，访问改成了外部函数调用
   （例如本该是 `s_ImagesTable[i].name = &v2[offset + *idx]`，变成 `pGetImage(...)`）
4. **表结构体字段互换** —— `Il2CppFieldDefinition` 的 `nameIndex` 与
   `customAttributeIndex` 对调；`Il2CppTypeDefinition` / `Il2CppMethodDefinition` /
   `Il2CppPropertyDefinition` 同样被改
5. **头部之后一大块整体加密**（就是字符串字面量区）

### 他们怎么解开的（关键）

**不破算法，直接调用 `UnityPlayer.dll` 里的解密函数。**

```csharp
[DllImport("kernel32.dll")] static extern IntPtr LoadLibrary(string path);
[UnmanagedFunctionPointer(CallingConvention.Cdecl)]
delegate IntPtr DecryptMetadata(byte[] bytes, int length);

var h = LoadLibrary("UnityPlayer.dll");
var baseAddr = Process.GetCurrentProcess().Modules
                 .First(m => m.ModuleName == "UnityPlayer.dll").BaseAddress;
var fn = (DecryptMetadata)Marshal.GetDelegateForFunctionPointer(
             baseAddr + 0x42110, typeof(DecryptMetadata));   // 4.3 的偏移
var p = fn(File.ReadAllBytes("global-metadata.dat"), len);
// Marshal.Copy 出来 → global-metadata-decrypted.dat
```

**这个函数是怎么找到的**（比函数本身更重要）：

1. ProcMon 只过滤 `BH3.exe` 对 `global-metadata.dat` 的访问
2. 发现**游戏先读文件末尾**（偏移 55,791,616，长度 30,684）——正常 IL2CPP 是从头读
   ⇒ 末尾那块是解密要用的东西
3. 双击读偏移 0 的事件 → **Stack 标签** → 用户态最顶帧在 `UnityPlayer.dll`
4. 往上追：`UserAssembly.dll` 里通过一个**运行时初始化的函数指针**调用它，
   再往上是 `il2cpp::vm::MetadataLoader::LoadMetadataFile`

附带情报：
- `UserAssembly.dll` 就是**改名后的 `GameAssembly.dll`**
- miHoYo 在 `LoadMetadataFile` 里加了个 `else` 分支，用解密返回值替换原返回值
- **安卓版算法相同**，PC 的 dat 拿安卓 lib 也能解
- 4.3 往回至 3.8 流程一致

## 3. Morax：米哈游自研的 IL2CPP 混淆框架

`IL2CPP_ENABLE_MORAX_SOLIDIFY` 开启。**在 C++ 元数据层动手，让二进制里根本不存在明文元数据**。

| 手法 | 机制 |
|---|---|
| 字段级加密 | `Il2CppTypeDefinition` / `MethodDefinition` / `FieldDefinition` / `CodeRegistration` / `MetadataRegistration` 的**每一个字段**单独用编译期随机的 `MoraxXor` 或 `MoraxAdd` 加密 |
| 运行时解密 | `MoraxField<T, Cipher>` 包住每个字段，**读时解密、写时加密**，密钥常数烧在模板里 |
| 字符串加密 | `Il2CppStringChar` / `StringLiteralChar` 用计数器模式流加密（`MoraxCtrDecryptor`），逐字符 XOR/MUL 链；**字符串表在 blob 里全密** |
| 头部打散 | `Il2CppGlobalMetadataHeader` **不作为结构体存在**，每个字段偏移编成 `#define` 常量 —— 内存里没有这个头 |

**Morax key 是每次构建随机生成的 88 位值，用于 codegen 时派生所有字段密钥，
它不存在于编译产物里。**

变体：

| 变体 | 文件 | 附加 |
|---|---|---|
| MHY0 | `startup-metadata.dat` + `global-metadata.dat` | 加密更多 |
| MHY1 | 只有 `global-metadata.dat` | Morax + xxHash3 字符串哈希 + BeeByte |

### 这条解释了此前全部四个"碰壁"

| 我此前的实测 | Morax 给出的解释 |
|---|---|
| UA 里没有任何 AES S-box / ChaCha / SM4 | 根本不是分组密码，是逐字段 XOR/ADD |
| 分段/跨版本 XOR 熵恒 7.9 | 没有密钥流可复用，常数是逐字段独立的 |
| 全盘扫 2.39GB 内存，`AF 1B B1 FA` 0 处，明文常量只出现 1 次（在密文副本里） | **因为解密是"访问时逐字段"发生的，从不存在一份解密后的完整文件** |
| `.rdata` 有 `global-metadata.dat` 字符串但 RIP 相对 xref = 0 | 引用它的代码在 `.tvm0` 里，是 TVM 字节码不是 x86 |

**本机版本归属**（已核对磁盘）：

```
7.0/app/.../Metadata/  →  global-metadata.dat                    ← 只有这个，MHY1 形态
7.9/app/.../Metadata/  →  global-metadata.dat + startup-metadata.dat  ← MHY0 形态
9.0/.../Metadata/      →  global-metadata.dat + startup-metadata.dat  ← MHY0 形态
7.6/.../Metadata/      →  global-metadata.dat                    ← MHY1 形态
```

## 4. `.tvm0` = 腾讯 TVM 虚拟化（ACE 那一套）

两个 DLL 都有：

```
UserAssembly.dll   .tvm0  VA=0x0ACD9000  vsize=0x00B4DD8A (11.3 MB)  ent=7.289  可执行
UnityPlayer.dll    .tvm0  VA=0x01A1E000  vsize=0x0019A000 ( 1.7 MB)  ent=6.888  可执行
```

熵 7.289 接近随机 ⇒ 不是普通代码段，是 VM handler + 字节码。
**这就是我 RIP 相对 xref 扫出 0 的原因**——调用方那段不是 x86 指令。

`tvm-recover`（Python 3.13 + capstone，配套 llvmlite）能把 `.tvm0` 提到 guest 级
listing / LLVM IR，官方给的 ACE 模块还原率 73%–95%。但这是研究级工作量。

## 5. 我这次查到的"plan B"，比解密更划算

### `UserAssembly.dll` 只有一个功能导出，正好是我们要的

```
exports (共 3 个):
   DllCanUnloadNow            RVA=0x00456360
   DllGetActivationFactory    RVA=0x00456370
   il2cpp_get_api_table       RVA=0x00466C50   ← 这个
```

反汇编 `il2cpp_get_api_table`（`0x180466C50`）：

```asm
mov  [rsp+8], rcx            ; rcx = 调用者给的输出缓冲区
mov  eax, 0x11118            ; 先要 69912 字节栈
call __chkstk
sub  rsp, rax
movabs rax, 0x410ece9923532841   ; 混淆基值
mov  [rsp+0x28], rax
mov  rax, [rsp+0x11120]      ; 取回 rcx 备份
mov  [rsp+0x30], rax         ; 输出缓冲区指针
...
cmp  rax, 0x4b3              ; ★ 循环上限 = 1203
jae  ...
lea  rcx, [rip - 0x466cc3]
mov  eax, [rcx + rax*4 + 0x4d64f0]   ; 跳转表
add  rax, rcx
jmp  rax                     ; 1203 路 switch
```

每一路都在做同一件事：

```asm
; 以 index=0x42a 分支为例
rcx = 0x410ece9923532841 + i
rax = rcx + 0x61c3ce6447701bcc
rdx = rax; rcx = &tmp
call 0x18045f890             ; 变换
call 0x180432d70             ; 解析出真实函数指针
[rsp+0x48] = rax
rax = 0x5daf71de49a8d059 + rax
out[i*8] = rax               ; ★ 写回调用者缓冲区
```

**结论：`il2cpp_get_api_table` 是一张 1203 项 × 8 字节的函数指针表**，
地址被 `base + index` 混淆常数派生（防止静态 dump）。调用一次就拿到**整个 il2cpp API
的实际地址**，包含 `il2cpp_domain_get` / `il2cpp_domain_get_assemblies` /
`il2cpp_class_from_name` / `il2cpp_class_get_methods` / `il2cpp_field_get_offset` 等等。

拿到它之后，运行时枚举 `domain → assemblies → images → classes → methods → methodPointer`
就是标准的 Perfare 流程，**产出等价于 `dump.cs` 的东西，而且带真实地址**。
Perfare 原话：*"因为是运行时修改，也能绕过大部分壳，目前大多数游戏厂商都没有对 api 做保护。"*

## 6. 另一个结构观察（本机实测 + 资料交叉验证）

本机 7.0 文件头：

```
0000  4d 48 59 00  71 4d 2f 65   "MHY\0" + 4 字节版本标签
0008  ...高熵...                    ← 从这里开始
0118  39 EE 02 00  DF 42 03 00      ← 明文 u32 表从这里开始
```

`0x08 + 0x110 = 0x118`。**`0x110` 正是标准 `Il2CppGlobalMetadataHeader` 的长度。**

也就是说 7.0 的布局是：

```
[0x00, 0x08)  "MHY\0" + 版本标签     8 字节容器头
[0x08, 0x118) 标准长度 0x110 的头部   加密
[0x118, EOF)  数据区                  部分分段加密
```

**7.0 没有 4.3 那多出来的 `0x48` 字节**，头部长度是标准的 ⇒ 7.0 的变体比 4.3 简单，
只要那一层加密解开，头部就是标准结构，不用做 djkaty 那种痛苦的重排推断。

（三个版本的 4 字节标签各不相同，像是 per-build 的种子：
7.0 `714d2f65`、7.6 `710f7366`、7.9/9.0 `00000000`。）

## 7. 路线修正

### P1 · 先做 · 半天 · 不需要开游戏也无所谓

**把 1203 项 API 表打出来。** 两种打法：

- **离线**：写个小 host，`LoadLibrary` 两个 DLL，`GetProcAddress("il2cpp_get_api_table")`，
  传一个 `1203*8` 缓冲；它内部只是算术 + 调两个 helper，可能不需要 il2cpp 初始化就能跑通
- **在线**（更稳）：在已有的 `bh3bypass.dll` 注入链里调一次，把表 dump 成
  `api_table.bin` + 按 `il2cpp-api-functions.h` 顺序对号入座

验证方式：`table[il2cpp_domain_get_idx]()` 返回非空，`domain_get_assemblies` 能数出
程序集数量（应该接近 100+）。通了就直接走枚举，**整个"解密"需求就绕过去了**。

### P2 · 备用 · 1 天 · 需要开游戏配合

**照抄 djkaty**：ProcMon 过滤 `BH3.exe` 读 `global-metadata.dat` → 看 Stack →
拿到 `UnityPlayer.dll` 里的偏移 → `LoadLibrary` + 函数指针调用 → 出明文 → 喂
**Il2CppInspector + miHoYo 插件**（`Loaders/miHoYo/MappedTypes.cs` 已有崩坏3 头部映射）。

风险：7.0 若是"逐字段按需解密"，这个函数可能不复存在，调用会拿到半成品。
一小时就能证伪，值得试。

### P3 · 兜底 · 数天 · 研究级

`tvm-recover` 还原 `.tvm0`，把加载器从 TVM 里捞出来。
只有在 P1、P2 都失败时才考虑。

### 明确放弃

- ❌ 静态破算法：Morax 的 88 位 key 不在二进制里，逐字段常数上千个
- ❌ dump 内存拼文件：`mem2.bin` 已证伪，且 Morax 机制决定它不可能存在
