## 一、五层防护模型

米哈游的资源保护不是一个算法，而是五层独立机制叠加。**破解任何一层都不等于能改资源**，这是理解这套体系的关键。

| 层 | 机制 | 防的是什么 | 强度 |
|---|---|---|---|
| L1 传输层 | HTTPS + 自签 CA + mitm 拦截成本 | 抓包改响应 | 弱（本地代理即可破） |
| L2 清单层 | FlatBuffers 清单 + 内容 hash | 改包后让客户端找不到 | **中**（能改，但会触发重新下载） |
| L3 包体层 | 自定义加密 / XOR / ArchiveStorage | 离线解包 | **强**（自研，无公开算法） |
| L4 运行时层 | 自研蒙皮缓冲、私有资源通道 | 内存注入替换资源 | **最强**（无公开绕过） |
| L5 代码层 | ACE 反作弊 + `.tvm0` 虚拟化 + metadata 加密 | 静态逆向、hook | 强 |

**结论先行**：L1/L2 是可破的，L3 部分可破（看具体游戏），L4 在 BH3 上是死路，L5 只是提高成本。

## 三、UnityCN（团结引擎）ArchiveStorage —— 官方方案

这是 Unity 中国版的官方 AB 加密，**米哈游没有用它**（见第四节实测），但它是理解整套体系的基准，且很多国产游戏在用。

### 3.1 文件结构

```
+0x00  u32  unknown_1
+0x04  16B  data
+0x14  16B  key
+0x24  1B   (跳过)
+0x25  16B  data_sig     ← 密文
+0x35  16B  key_sig      ← 密文
+0x45  1B   (跳过)
+0x46  ...  数据区（分块）
```

签名常量：`#$unity3dchina!@`（16 字节）

### 3.2 密钥派生

```python
# 用户提供的 16 字节 key（AssetBundle.SetAssetBundleDecryptKey）
derived = AES_ECB_encrypt(key=user_key, plaintext=key_sig)   # 16 字节
assert data_sig XOR derived == b"#$unity3dchina!@"           # 校验
data_plain = key XOR AES_ECB_encrypt(user_key, key)          # 得 16 字节种子
```

种子展开成 nibble 流：

```python
nibbles = [n for b in data_plain for n in (b >> 4, b & 0xF)]   # 32 → 64
index     = nibbles[:16]                                        # 半字节替换表
substitute = nibbles[16:] 按 4x4 转置                           # 差分表
```

### 3.3 块解密（关键：数据体不加密）

```python
def decrypt_byte(view, offset, index):
    b = (substitute[((index >> 2) & 3) + 4]
       + substitute[index & 3]
       + substitute[((index >> 4) & 3) + 8]
       + substitute[((index % 256) >> 6) + 12])
    view[offset] = (((index_table[view[offset] & 0xF] - b) & 0xF)
                    | (0x10 * (index_table[view[offset] >> 4] - b))) % 256
    return view[offset], offset + 1, index + 1

def decrypt(data, index, remaining):
    cur, off, index = decrypt_byte(data, 0, index)
    high, low = cur >> 4, cur & 0xF
    if high == 0xF:                       # 扩展长度
        while True:
            b, off, index = decrypt_byte(data, off, index)
            high += b
            if b != 0xFF: break
    off += high                           # ★ 跳过 high 个字节，原样不动
    if off < remaining:
        decrypt_byte(...)                 # 2 个字节
        decrypt_byte(...)
        if low == 0xF:
            while ...: decrypt_byte(...)
    return off
```

**核心洞察**：只有「块长度字节」被加密，`high` 个字节的**数据体原样保留**。所以解出来的文件里，LZ4 压缩块是完整可读的。

### 3.4 密钥获取

**[外部]** UnityPy 提供爆破接口：

```python
UnityPy.helpers.ArchiveStorageManager.brute_force_key(
    fp        = "global-metadata.dat 或内存 dump",
    key_sig   = <从文件头读>,
    data_sig  = <从文件头读>,
)
# 内部用正则 \w{16} 扫候选，逐个 AES-ECB 验证签名
```

密钥通常硬编码在 `global-metadata.dat` 或 `libil2cpp.so` 的字符串常量里。

## 四、BH3 7.0 实测对照

这一节全部是**[实测]**，和上面的通用方案对照。

### 4.1 资源包 `.wmv`：完全明文

| 项 | 结果 |
|---|---|
| 数量/体积 | 440 个 / 16.13 GB |
| 文件头 | 首 7 字节全是 `UnityFS` —— **没有加密** |
| 加密 | 无。不需要任何 key |
| 异常 | 0x32 处有 `mr0k` 变体（C7 主模型单元），现有 LZ4 解码器解不了 |

**所以 BH3 的资源包本身不设防**，防护全在清单层和校验层。

### 4.2 清单 `Blocks.xmf`：FlatBuffers，明文

```
37B 头 + N 包记录 + 4B 尾
头 = MD5_1(8B BE) | MD5_2(8B BE) | u32 type | u32 ver=7 | u32 0 | u32 0 | u8 0 | u32BE 包数
记录 = 16B md5(文件) | FileTag | DownloadTag | BlockID | Length | u32 单元数
      | 单元0(u8 Y=0 + u8 名长 + 名)
      | 单元k(u32 单元k-1偏移 + u8 Y + u8 名长 + 名)
      | u32 单元n-1偏移
```

- 16B hash **就是文件 MD5**，文件名也等于 MD5（440/440）
- 单元名 = `<Name十进制>_<Hash十进制>.unity3d`
- 唯一例外：`asbresversion.unity3d`
- 7.0 明文；**7.6 / 9.1 加密**（头分别 `26 49 5b 42…` / `f9 11 c7 8e…`）

### 4.3 为什么改包是死路

| 硬事实 | 证据 |
|---|---|
| 客户端只读 `Blocks.xmf` | `Blocks_7_0.xmf` 是死文件，改名藏起来照样正常 |
| `Blocks_7_0.xmf` 和任何 `.wmv` **从未被 HTTP 请求过** | nginx 80 + Server 443 全查 |
| 校验基准来自 HTTP 下发的 `BlockMeta` | 每次启动 `GET .../HD/asb/BlockMeta_7_0.xmf` |
| 改内容 → 弹「下载 51MB」；改 MD5 → 触发下载 → 失败 → `missing asb` | 多组对照实验 |

`BlockMeta` 记录 = `16B hash + u32 f1 + u32 f2 + u32 f3 + u32 size`（**size 在索引 4**）。

### 4.4 配置表通道：完全不同的一条路

这是本次新查清的部分，和 `.wmv` 的 ASB 通道**互不相干**。

**请求方式**：
```
GET /asset_bundle/overseas01/1.1/data/editor_compressed/data/<数字>_<SHA1>
Range 请求（206 Partial Content）
```

**清单 `DataVersion.unity3d`：整体 XOR 0xA5**

```python
raw = open("DataVersion.unity3d","rb").read()
dec = bytes(b ^ 0xA5 for b in raw)      # → 标准 UnityFS，version=6，2017.4.18f1
```

解出来是 LZ4HC 压缩的 UnityFS，内含**明文 JSON 清单**，415 条：

```json
{"N":"data/1577722382","CS":"4728354","CRC":"2389B3BE…","ULM":"0","DLM":"1",
 "BT":"0","R":"false","RD":"data","V":"2","APS":[],"PN":[]}
```

- `N` = 单元名，`CS` = 字节数，`CRC` = 40 位 hash
- **文件名 = `N 的数字部分` + `_` + `CRC`**
- 另有 `data/excel_output`（TextMap）、`data/bh`（BakeHead）、`data/sv`（SVNVersion）

**表本体：自研加密**

| 检测项 | 结果 | 推论 |
|---|---|---|
| 熵 | 7.76 ~ 7.99 | 强加密或压缩 |
| 长度 mod 16 | 均匀分布（0~15 都有） | **不是块密码**（CBC/ECB 会补齐到 16） |
| 同表两版本字节相同率 | 0.40% | 每文件 key/IV 不同 |
| zlib / lzma / lz4 / gzip | 全部失败 | 不是标准压缩 |
| **UnityCN ArchiveStorage 验证** | **47 万候选 key 全未命中** | **不是 UnityCN** |

**内存里的线索**（2.8 GB 进程 dump）：

```
_ExcelOutputAsset/CombinedBytes        ← 全部 1762 张表的合集入口
HKEV1                                   ← 自研容器 magic
bZIRSH~USeKEgKcn)qfv5C~oXI)            ← 28 字符 UTF-16 密钥串（紧邻上述路径）
_ExcelOutputAsset/<表名> × 1762          ← 完整表名清单
```

**缓存与重下行为**：

- 本地缓存 `%LocalLow%\miHoYo\Honkai Impact 3\Data\data\` 有 421 个文件，415 条清单**大小全部对得上**
- 但每次启动**仍会重下 `1577722382`（4.7 MB，唯一一个）**，带 `206 1024` 探测
- 该文件是全表里最大的，极可能就是 `CombinedBytes`

**CRC 不等于内容 SHA1**：明文文件与加密文件全部不匹配。说明 CRC 只是版本标签，**客户端不拿它校验文件内容**。

### 4.5 运行时层：BH3 的真正壁垒

- 客户端有**自研蒙皮通道**：预渲染 pass 把顶点+权重送 VS 蒙皮，SO 写入私有骨骼矩阵缓冲；主 pass 读该缓冲
- Unity 的 `SkinnedMeshRenderer.bones` / `bindposes` 设得再准也影响不到最终画面
- 实测：骨骼世界变换、mesh 顶点、法线、bindposes 全部精确匹配，画面依然错

**这是结构性壁垒**，不是参数问题。

## 五、代码与运行时保护

| 手段 | 说明 |
|---|---|
| **ACE**（AntiCheatExpert） | 腾讯的反作弊，非米哈游自研。`CreateRemoteThread` 被拦，需走入口绝对跳转 `FF 25` |
| **`.tvm0` 段** | 虚拟机保护，代码被编译成自定义字节码。BH3 的 `il2cpp` 段 RVA `0x52E000`，size `0x6727B2A` |
| **metadata 加密** | `global-metadata.dat` 被加密，Il2CppDumper 直接读会失败 |
| **字符串 XOR** | 运行时才解出明文字符串 |
| **符号混淆** | Beebyte 等商业混淆器 |
| **内容级校验** | 资源加载后比对 hash（BH3 的 `BlockMeta` 机制） |

**[外部]** `Il2CppInspectorRedux` 号称能自动破解 XOR 字符串、Beebyte 混淆、miHoYo 系 metadata 加密。

## 七、对本项目的可行动结论

### 通的路

| 路线 | 可行性 | 依据 |
|---|---|---|
| 解 `.wmv` 拿资源 | **完全可行** | 明文 UnityFS，不需要 key |
| 改配置表清单 `DataVersion` | **完全可行** | XOR 0xA5 + 明文 JSON，能解能重打包 |
| 拦截单个表请求 | **架构可行** | nginx 精确 location 即可；客户端本就在重下 `1577722382` |
| 运行时改 DressData 文本 | **已验证** | `patch_dress_record.py` 两次实测生效 |

### 死的路

| 路线 | 原因 |
|---|---|
| 改 `.wmv` 内容 | `BlockMeta` 内容级校验，改内容/改 MD5 都是死循环 |
| 跨版本移植 Mesh | 7.0 与 9.1 类型哈希不同，顶点数据读成垃圾，实测崩 3 次 |
| 替换蒙皮骨骼 | 自研私有缓冲，Unity 层改不动 |
| 重加密配置表 | 自研流密码，算法未定位，**唯一未攻克的关卡** |

### 下一步的技术赌注

如果要把配置表这条路走通，唯一要解决的是「重加密」。三个候选方向：

1. **keystream 差分** —— 拿一份明文 P，`K = C ⊕ P`，`C' = P' ⊕ K`。前提是 keystream 只依赖偏移
2. **明文直投** —— 同类有 17 个明文 UnityFS 文件（`bh_/sv_/lua*/excel_output_`），说明加载器先看文件头。若成立，伪造文件根本不用加密
3. **hook 解密出口** —— 在客户端解密函数返回处取明文，顺便反推算法

其中 **2 的成本最低**：改一个 `lua*` 明文文件的一个字节，启动看是否报错，一次就能定生死。
