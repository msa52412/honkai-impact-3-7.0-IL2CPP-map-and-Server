# 主界面展示角色：读取与更换

日期：2026-11-07　目标进程：`BH3.exe` PID 15056，`UserAssembly.dll` 基址 `0x7ffa397d0000`

## 结论

主界面角色的读取**零调用**（纯 `ReadProcessMemory` 走五跳链），更换走游戏自己的
`GalTouchModule::ChangeMainPageAvatar` → `NetworkManager::RequestSetWarshipAvatar`，
即**发服务器请求**，回包后由游戏自己重建 `GalTouchInfo` 并刷新显示。

实测两次切换全部成功：

| 操作 | `CanChange` 预检 | 请求返回 | 回包后 ID | `_mainPageGalTouchInfo` |
|---|---|---|---|---|
| 507 → 101 | `True` | `1` | **101** | `0x700a66d3ed0` → `0x700a94c1f90` |
| 101 → 301 | `True` | `1` | **301** | → `0x700a7f0f8d0` |
| 507 → 507（对照） | **`False`** | 未发 | — | — |

info 对象每次都换成新地址，说明是服务器回包后游戏重建了缓存 —— **不是我们硬改内存**，
所以改动会被服务器持久化。

## manager 单例的通用取法

反汇编 `GalTouchModule::get_galTouchModule` @`0x3082E20` 与
`NewbieDialogContext::ReplaceGalTouchAvatar` @`0x11BABD0`，发现两者拿 manager 的形状完全相同：

```
G0   = *(base + g_rva)        ; .data 段里每个 manager 一个全局槽
k1   = *(G0)                  ; klass；+0x136 是 class-init 标志，为 0 时要先 call Init
B    = *(k1 + 0x90); k2 = *(B)
inst = *(*(k2 + 0x28))
```

`get_galTouchModule` 的主执行路径**完全不使用 `this`** —— 它就是个静态单例访问器，
所以拿模块不需要任何对象、不需要反射、不需要 `GetComponent`。

已知全局槽：

| RVA | 模块 | 来源 |
|---|---|---|
| `0x9AA3488` | `GalTouchModule` | `get_galTouchModule` 的 `rip+0x6a2064a`；按钮里的 `rip+0x88e880f` 也是它 |
| `0x9A988C8` | `AvatarModule` | `ReplaceGalTouchAvatar` 的 `rip+0x88ddcd0` |

这条模板可以直接套到其他 manager 上：在任意方法里看到
`mov rax,[rip+X]` → `mov rbx,[rax]` → `cmp byte [rbx+0x136],0` → `mov rax,[rbx+0x90]`
→ `mov rbx,[rax]` → `mov rax,[rbx+0x28]` → `mov rcx,[rax]`，那 `X` 就是该模块的全局槽。

## 校验链

`GalTouchModule::CanChangeMainPageAvatar(int avatarID, GalTouchType type)` @`0x14A3530`：

```
info = GetTouchInfoByTypeAndID(type, avatarID)
if (!info) return false
if (![this+0x80]) return false
return info.CompareTo([this+0x80]) != 0     ; 与当前相同则拒
```

纯本地校验：不发网络、不分配、不抛异常。**可以拿它低成本试探合法 ID。**
实测 `CanChange(507,0)=False`（当前就是它）、`CanChange(101,0)=True`，语义完全对上。

## 更换链路

`GalTouchModule::ChangeMainPageAvatar` @`0x14A35E0`：

```
if (!CanChangeMainPageAvatar(id, type)) return
[this+0x60] = isSwitchTwins
info = GetTouchInfoByTypeAndID(type, id)
NetworkManager::RequestSetWarshipAvatar(info.mainAvatarID, info.secondAvatarID)
```

调用方 `NewbieDialogContext::ReplaceGalTouchAvatar` @`0x11BABD0`（就是"对话结束弹更换按钮"那条）：

```
AvatarModule::GetAvatarByID(id) → cmp byte [item+0x69], 0    ; 校验已拥有
[预览对象+0x10] = id
GalTouchModule::ChangeMainPageAvatar(id, 0, false)           ; r8d/r9d 都 xor 成 0
```

⇒ `touchType = 0` 是从 `xor r8d,r8d` 直接读出来的，不是猜的。

## 这一轮踩到的四个坑

1. **布局表整体偏 8 字节**。`bh3_layout_resolved.tsv` 把 `_mainPageGalTouchInfo` 记在
   `+0x88`，`get_MainPageGalTouchInfo` 实读 `[rcx+0x80]`。被混淆过的类要一律以反汇编为准。

2. **符号表 RVA 可能是 COMDAT 折叠的共享桩**。`get_UserAvatarList` 的 RVA 与
   `AssemblyName::get_Version`、`FileInfo::get_Name` 等 5 个方法相同，因为方法体都是
   `mov rax,[rcx+0x60]; ret`，链接器把它们合并了。**RVA 不唯一 ⇒ 不能当入口地址用**
   （好在护栏会拦住非入口）。反过来这个折叠信息本身有价值：它直接告诉你字段偏移。

3. **il2cpp 的 bool 返回只保证 `al` 有效**。`CanChange` 返回 `True` 时 `rax` 是
   `0xFFFFFF01`（高位脏），按整数判真假会得到 4294967041。必须 `v & 0xFF`。

4. **`List<T>` 不是 `+0x18/+0x20`，是 `+0x10/+0x18`**。第一版按 Unity 习惯读，把
   `_items` 指针当成 size 读出 86，size 读成 0，遍历结果为空。

## 复现所需前提

- 游戏已进主界面（此时 `MainCanvas/Pages/MainPage(Clone)` 激活，全局槽已初始化）
- 插件信箱已安装（只有 `--can` / `--set` 需要；只读完全不需要）
- 读取状态零调用 ⇒ 即使崩溃也不会破坏状态
