# 04_01 换装：运行时 Mesh 替换方案

> 结论：**可行且已跑通**。崩坏3 7.0 的角色网格可以在运行时原地替换成 9.1 的 04_01 数据，
> 由引擎自己蒙皮 —— **会跟着动作变形**。不需要 3DMigoto、不需要动 mr0k 加密。

## 一、为什么这条路能成（架构）

崩坏3 是 **Stream-Output 蒙皮**：

```
预渲染 pass:  Draw(N) 读 vb0(位置) + vb1(权重 32B) → VS 蒙皮 → SO 写入蒙皮缓冲
主渲染 pass:  DrawIndexed 读那个已蒙皮的缓冲
```

引擎是**读 mesh 自己的顶点和 BoneWeight** 来算蒙皮的。所以只要把 mesh 的
顶点/法线/UV/BoneWeight/索引**原地改掉**，引擎就会继续用它的管线蒙皮。

（3DMigoto 路线失败的原因：它是「draw 提交前换资源」，覆盖 SO pass 必定卡死，
且无法改变非索引 Draw 的顶点数 —— 所以做不出动画。）

## 二、数据来源（必须同源！）

| 流 | 来源 draw（9.1 dump） | 说明 |
|---|---|---|
| 位置 / 法线 / BoneWeight | **预渲染 pass `000004`** | 模型空间、Y 向上、跨度 1.94 |
| 索引 / UV | **主渲染 `000014`** | 与预渲染的顶点顺序一致 |

- **不要混用**：主渲染的位置流是另一个空间（中位模长 0.287 vs 1.101，
  逐顶点相关系数仅 0.05/0.50/-0.17），混用会「错位成一团」。
- **不要缩放**：9.1 与 7.0 的 bindpose 空间一致（62 条精确匹配 at s=1）。
  ×1.6 只适用于主渲染那个空间，用在这里会错。

## 三、生成资产

```powershell
python tools\build_mesh_assets.py `
  --dump "<9.1 dump 目录>" `
  --pos-draw 000004 --blend-draw 000004 --uv-draw 000014 --ib-draw 000014 `
  --map "_ext\tmp\map_body202.txt" --out "_ext\mesh\c7_04_01_v2" --scale 1.0
```

产出：`pos.bin`(12B/顶点) `nrm.bin` `uv.bin`(8B) `bw.bin`(32B) `tri.bin`(int32)。
校验项：索引不越界、权重和=1、无零长法线、骨骼索引 ≤227。

## 四、施加（每次游戏重启都要重做，地址随进程变）

```powershell
python rea\_rea\icall.py install                          # 装信箱（每进程一次）
python tools\rt_class.py --name Mesh --probe               # 取 Mesh klass（低 12 位恒 0x490）
python tools\rt_meshes.py --klass <klass>                  # 找 name=Body 且 bindposes=228
python tools\rt_mesh_replace.py --mesh <addr> --apply _ext\mesh\c7_04_01_v2
```

⚠ **场景里必须已加载 C7**（角色页/编队），否则找不到 228 根骨的 Body。

## 五、三个致命坑（都踩过）

1. **补位不能补零**
   网格 17658 顶点，而 7.0 的数组是 19129 → 补 1471 条。
   补零 ⇒ 权重和 0 + 法线零长 ⇒ 蒙皮除零 ⇒ NaN ⇒ **进程退出**。
   ✅ 正解：复制第 0 条记录 + 末尾调 `RecalculateBounds`。

2. **顶点色必须重设**
   只换顶点/法线/UV/权重/索引，**颜色通道还是原网格的** ⇒ 与索引错配 ⇒ 大片深色。
   ✅ `get_colors32` → 全部写白 → `set_colors32`。

3. **地址换算**
   `icall.py call <RVA>` 命令行**会自己加基址**；`rt_load.do_call` **不会**（要传 `base+RVA`）。
   `do_call` 的 args 必须是整数，hex 字符串会 TypeError。

## 六、贴图

几何由运行时提供，贴图由 3DMigoto 覆盖（两条链路不冲突）。

替换后 IB 哈希会变，需要用新哈希匹配：

```ini
[TextureOverrideC7BodyTex]
hash = 1c91d0b5          ; 替换后的新 IB 哈希
ps-t0 = ResourceBodyDiffuse
ps-t1 = ResourceBodyShade
ps-t3 = ResourceBodyRamp

[ResourceBodyDiffuse]
filename = body_t2.dds
```

- 新哈希的拿法：把 `analyse_options` 改成 **`dump_ib buf`**（只导 IB），
  按 F8 就不会卡死（原配置会导巨型顶点缓冲 + 渲染目标，改完 mesh 后必挂）。
  哈希在文件名里：`000038-ib=1c91d0b5-...`
- 9.1 的槽位与 7.0 不同（9.1 在 t1 插了个共享 ramp），按规格配对：
  `t0 ← 9.1 t2`（漫反射，裙子变白 ✓）、`t1 ← 9.1 t4`（纹路正确）、`t3 ← 9.1 t3`（ramp）
- ⚠ `[ShaderOverride]` 在这版 3DMigoto 里**不能**赋值 `ps-t0`（实测无效），必须用 `[TextureOverride]` + draw 哈希

## 九、★ 重要发现：米哈游的角色贴图不是彩色漫反射

把 dump 里的贴图转成 PNG 后看颜色统计与画面：

| 贴图 | 尺寸 | 平均 RGB | 饱和度 | 判定 |
|---|---|---|---|---|
| 7.0 原版 body `t0` (c90ed2ed) | 1024² | (0.00, **0.22**, 0.00) | 0.219 | 绿色遮罩（纯绿分区 + 黑线稿） |
| 9.1 04_01 body `t0` (1921d92f) | 1024² | (0.00, **0.37**, 0.00) | 0.373 | 同性质 |
| 9.1 body `t2` (f95f34b0) | 1024² | (0.97,0.97,0.97) | 0.002 | 纯白遮罩 |
| 9.1 body `t4` (e7d61b55) | 1024² | (0.02,0.02,0.02) | 0.000 | 纯黑遮罩 |
| 9.1 body `t3` (27a5bcf1) | 512² | (0.48) 灰 | 0.005 | 灰 ramp |

⇒ **颜色 = 遮罩 × ramp 渐变**，在着色器里算出来；没有任何一张是「彩色漫反射」。
⇒ 顶点色也不是配色载体（写入 dump 里的真实顶点色 → 画面「一团乱」，已回退为涂白）。
⇒ 要精确还原 04_01 的配色，必须找到它对应的 **ramp 色带**（ramp 是多角色共享的一张图，
04_01 的色带只占其中一小块），这已经属于「改材质参数」而不是「换资源」。

### 已试过的贴图组合（供以后参考）
- `t0 ← 9.1 t2`（白）→ 裙子变白，纹路对
- `t1 ← 9.1 t4` → 纹路正确，整体偏暗
- `t3 ← 9.1 t3` → 无变化
- `t0 ← 9.1 t0`（绿遮罩）→ 全身绿（因为它是遮罩不是颜色）

## 十、★ 贴图槽位的真实对应（人工对照确定，11-03 09:39）

把两边 body draw 的全部贴图导出成 PNG（`_ext\himi\tex_compare\`，文件名 `版本_槽位_哈希.png`），
人工比对后确认：

| 7.0 槽位 | 用途 | 对应 9.1 | 哈希 |
|---|---|---|---|
| `t0` | 遮罩 | `t0` | 7.0 `c90ed2ed` ↔ 9.1 `1921d92f` |
| **`t1`** | **漫反射** | **`t2`** | 7.0 `0a627347` ↔ 9.1 `f95f34b0` |
| `t3` | 阴影 | `t4` | 7.0 `1e1d5dab` ↔ 9.1 `e7d61b55` |
| — | — | `t3` `27a5bcf1`（512² 灰） | 用途不明，7.0 无对应 |

**★ 关键：7.0 的漫反射在 `t1`，不是 `t0`！** 9.1 的在 `t2`。
之前按「槽位号一一对应」去换，必然错。

正确的 mod：
```ini
[TextureOverrideC7BodyTex]
hash = 1c91d0b5
ps-t0 = ResourceMask      ; 9.1 t0
ps-t1 = ResourceDiffuse   ; 9.1 t2  ← 漫反射
ps-t3 = ResourceShadow    ; 9.1 t4
```

## 十一、✗ UV 仍是未解的硬骨头

试过的全部组合（都失败）：

| 方案 | 结果 |
|---|---|
| float UV（`vb1` 偏移 4，U∈0~2 / V∈0~1）→ 通道 0 与 1 | 用纯白贴图时「白裙 + 纹路正确」；**换成真实贴图后「一团乱」** |
| 打包 UV（`vb0` 偏移 24/26） | 更乱 |
| 打包 UV（`vb0` 偏移 32/34） | 更乱 |
| 通道 0 float + 通道 1 打包 | 乱 |
| float UV 的 U 压缩一半（`--uv-scale 0.5,1`） | 无变化 |

**结论**：之前「白裙 + 纹路正确」是**纯白贴图掩盖了 UV 错乱**。真实贴图一上就暴露。
UV 数据本身是合理的（三组打包 UV 都是 0~1 / 256 唯一值；float UV 的 U 到 1.995 说明图集可能横向两格），
但**没有一组能和这张 1024² 的贴图对上**。

**下一步只能做**：在 Blender 里把 9.1 的 mesh UV 展开图导出来，与贴图的实际绘制区域逐区对照，
确定「UV 属于哪一组 / 图集是不是 2048 宽 / 需不需要翻转」。这是需要坐下来细做的工作。

### 可用参数（供继续调）
`build_mesh_assets.py` 支持：
- `--uv-packed` + `--uv-packed-offset 24|28|32`（用 vb0 的打包 UV）
- `--uv-scale u,v` / `--uv-offset u,v`（UV 校正）
- `--bp-a` / `--bp-b`（**重新绑定**：把顶点从 9.1 的 bindpose 空间搬到 7.0 的，公式见下）

## 十二、★★★ 关键突破口：`il2cpp_get_api_table` 是导出函数

```
UserAssembly.dll 导出表里只有 3 个函数，其中：
  il2cpp_get_api_table   RVA = 0x466c50
```

**这意味着「在游戏堆里创建托管对象」是可行的** —— 通过 API 表可以拿到：
- `il2cpp_object_new(klass)` → 分配任意托管对象（GameObject / Transform / Mesh / Texture2D…）
- `il2cpp_array_new(klass, len)` → 分配数组（不再需要「复用 get_* 返回的数组」这种绕法）
- `il2cpp_class_from_name(image, ns, name)` → 按名字取 klass
- `il2cpp_alloc` / `il2cpp_free`

### 为什么这是根本解法
当前所有失真的根源是**骨架不匹配**：04_01 有 202 根骨、C7 有 228 根，
`bindpose` 只有 87 根能精确对上，其余靠「挂到最近的身体骨」近似 ⇒ 局部拉伸、比例失真。

有了 `object_new` 就能：
1. 按 9.1 的 bindpose（`_ext\tmp\bp202.csv`）建 202 个 `Transform`
2. 按 9.1 的层级摆好（层级需另取，或由 bindpose 反推父子关系）
3. 把 SMR 的 `bones` 换成这 202 个 Transform
4. 顶点直接用 9.1 的原始数据、骨索引用 0..201 原样
⇒ **蒙皮完全精确，零失真**，不再需要任何映射近似。

### 下一步实施步骤（未做）
1. 调 `il2cpp_get_api_table` 拿到表指针（需要游戏主线程可响应）
2. 按 `il2cpp-api-functions.h` 的顺序定位 `class_from_name` / `object_new` / `array_new`
   （**验证办法**：`class_from_name("UnityEngine","Mesh")` 应返回已知的 Mesh klass，低 12 位恒 `0x490`）
3. 用 `object_new(Transform klass)` 批量建骨，设 localPosition/localRotation（从 bindpose 反算）
4. 组装 SMR

### 重新绑定公式（已实现但效果不佳，留档）
```
v' = Σ wᵢ · ( B7[bᵢ] · B9[i]⁻¹ ) · v
```
实测 9890/17658 顶点被变换，但画面更乱 ⇒ **近似映射 + 重绑定会放大误差**，
根本解法仍是「建真实骨架」而不是「在错误的骨架上做数学补偿」。

## 十四、✗ 设置骨骼变换这条路被 XMM 卡住

`Transform.set_position(Vector3)` / `set_rotation(Quaternion)` 的参数是**结构体按值**，
走 **xmm0**，而 icall 信箱只写 rcx/rdx/r8/r9。

试过的方案与结果：

| 方案 | 结果 |
|---|---|
| 直接调 `set_position`（不给 xmm） | 崩：`mov [rcx],rax` / 读空指针 |
| `VirtualAllocEx` RWX 页 + shellcode 填 xmm0，直接调该页 | 崩：信箱校验「target 不在 UserAssembly.dll 里」 |
| 在模块 `.text` 找 CC 代码洞写 `jmp <page>`，再调洞地址 | 第一次：进到 Unity 内部后崩（`Read from location 0`）<br>第二次：主线程直接停摆 |
| 改用已挂接的 transform 再试 | 同样停摆 |

⚠ 改 `.text` 还有**反作弊完整性校验**风险。

### 剩下的干净方案（未做）
**直接写原生 Transform 的字段**（不执行任何代码，不碰 .text）：
`Transform` 的托管对象 `+0x10` 是 `m_CachedPtr` → 原生结构里存着 localPosition / localRotation。
只要能定位这两个字段的偏移，就能用 `write_mem` 直接改 —— 完全绕开 XMM 与反作弊。

定位办法：拿一个**已知位置**的 transform（例如把某个物体放到已知坐标），
在原生结构里搜那三个 float，再用另一个已知坐标交叉验证。

### 另一条路（未做）
`il2cpp_get_api_table`（RVA `0x466c50`）**不是无参函数** —— 它需要一块 1203×8 的输出缓冲区，
反汇编确认它会往 `arg0 + i*8` 写 1203 项。但**内容是 XOR 混淆的**（密钥常量 `0x410ece9923532841`），
拿到 `il2cpp_object_new` 需要先逆出这个混淆算法。
