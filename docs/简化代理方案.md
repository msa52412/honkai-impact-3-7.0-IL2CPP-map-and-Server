# 简化代理方案：用注入关掉证书校验，去掉 mitmproxy 与 CA

> 日期：2026-11-04
> 目标：客户端仍然走 `https://`，但**不再要求代理证书**——本地一张自签证书（甚至 Kestrel 现成那张 CN=bh3-local）就能过，从而丢掉 mitmproxy、SNI 现签和「把 CA 装进受信任根」。
> 现状对照：`docs\启动链对照_ys5.4天机端.md` 里写过——天机端是「DLL 劫持 + hook」，我们因为 BH3 走 HTTPS 被迫用中间人。本方案就是把这一课补上。

---

## 一、现在的链路与代价

```
BH3.exe
  └─ 系统代理 127.0.0.1:8891 (mitmdump)
       ├─ 按 SNI 现签 leaf 证书 ──► 客户端校验「签发者是否受信任」──► 需要 mitmproxy CA 进 Root
       └─ 改写目标到 127.0.0.1:443 (Kestrel, run\cert\server.pfx)
```

代价都在 `_launch\launch_all.py` 的 `check_cert()` 里写着：

* 必须 `certutil -addstore -f Root`（要管理员）；
* 证书按域名现签，**IP 目标没有 SNI** 时 CN 对不上 → 握手失败（2026-10-24 那个坑，见 `runtime\proxy\proxy.py` 注释）；
* 换网段要重新探 Host；
* mitmproxy 同时接管了浏览器流量，得靠 `GAME_SUFFIXES` 白名单逐个放行。

**根因**：客户端在校验服务端证书。把它关掉，上面四条同时消失。

---

## 二、客户端到底在哪校验（有据）

| 层 | 证据 | 结论 |
|---|---|---|
| 引擎层（UnityWebRequest） | `UnityPlayer.dll` 的导入表含 `crypt32.dll!CertGetCertificateChain`、`CertVerifyCertificateChainPolicy`、`CertAddEncodedCertificateToStore`… | 引擎把链校验交给 **Windows CryptoAPI** |
| 业务层 | `MiHoYo.SDK.cs` 的 `PerformHttpRequest` 全部构造 `UnityWebRequest` | 登录 / SDK / 上报走的是上面那条 |
| 托管层（System.Net） | `UserAssembly.dll` 内有 `Mono.Unity.UnityTlsProvider`、`Mono.Net.Security.ChainValidationHelper` | 少数走 `SslStream` 的请求在这里校验 |

两个入口都是「布尔返回，false 就抛异常」——正好可以打成恒真。

## 三、补丁设计

### 3.1 主补丁：`crypt32!CertVerifyCertificateChainPolicy`

签名（x64）：

```c
BOOL CertVerifyCertificateChainPolicy(LPCSTR pszPolicyOID,        // rcx
                                      PCCERT_CHAIN_CONTEXT pChain, // rdx
                                      PCERT_CHAIN_POLICY_STATUS pStatus); // r8
```

入口写 14 字节 `FF 25 00 00 00 00` + 8 字节绝对地址，跳到我们 `VirtualAllocEx` 出来的 code cave：

```asm
test r8, r8                 ; 45 85 C0
jz   +8                     ; 74 08
mov  dword ptr [r8+4], 0    ; 41 C7 40 04 00000000   pStatus->dwError = 0
mov  eax, 1                 ; B8 01 00 00 00
ret                         ; C3
```

为什么不是简单的 `mov eax,1; ret`：调用方可能读 `pPolicyStatus->dwError` 决定提示文案，顺手清零更干净。
这一处同时放行 **链不受信 / 主机名不匹配 / 证书过期**，所以本地证书 CN 写什么都无所谓。

### 3.2 辅补丁：il2cpp 的 3 个 `ValidateCertificate`

入口写 `B0 01 C3`（`mov al,1; ret`）。RVA 相对 `UserAssembly.dll`（ImageBase `0x180000000`）：

| RVA | 符号 | 覆盖 |
|---|---|---|
| `0x6747880` | `ChainValidationHelper.ValidateCertificate(collection)` | `SslStream` 主路径 |
| `0x6747790` | `ChainValidationHelper.ValidateCertificate(leaf)` | 重载 |
| `0x6323C80` | `UnityTlsProvider.ValidateCertificate` | UnityTls 后端 |

> 这三处是否全部命中不影响结果，属于「多打一层保险」。

### 3.3 工具：`tools\cert_bypass.py`

```bat
python tools\cert_bypass.py --dry-run    :: 只读探测（默认）
python tools\cert_bypass.py --apply      :: 写入（游戏需在运行，最好同权限）
python tools\cert_bypass.py --restore    :: 按备份还原
```

* 幂等：已经是补丁字节就跳过；
* 写入前后都回读校验，`FlushInstructionCache`；
* 原字节备份到 `server-v2\run\cert_bypass_backup.json`；
* 只改内存，**重启游戏自动消失**。

在本机正在运行的 BH3（PID 96572）上 dry-run 的实际输出：

```
UserAssembly.dll  0x7FFDB53D0000
crypt32.dll       0x7FFEA9430000
[1] crypt32!CertVerifyCertificateChainPolicy  0x7FFEA9453C00  4c8bdc49895b0849896b104989731857
[2] ChainValidationHelper.ValidateCertificate(collection) 0x7FFDBBB17880
    ChainValidationHelper.ValidateCertificate(leaf)       0x7FFDBBB17790
    UnityTlsProvider.ValidateCertificate                  0x7FFDBB6F3C80
```

## 四、简化代理的两种形态

### 方案 A：直连（最简，推荐长期形态）

```
BH3.exe ── hosts: 游戏域名 → 127.0.0.1 ──► Kestrel 127.0.0.1:443 (server.pfx 自签即可)
```

* **不要**系统代理、**不要** mitmproxy、**不要**装 CA；
* 浏览器/其它软件完全不受影响（这是现在最大的痛点）；
* 证书就是 `server-v2\run\cert\server.pfx`（CN=bh3-local），客户端已经不看了。

代价：hosts 要列全。Windows hosts 不支持通配符，**别猜**——用方案 B 的 `--log-hosts` 跑一次登录，把真实域名抓出来再填。

### 方案 B：透明管道（不改 hosts，随时可切回）

```
BH3.exe ── 系统代理 127.0.0.1:8891 ──► simple_tls.py
                                        ├─ CONNECT 一律 200
                                        ├─ 用一张固定证书和客户端握手
                                        └─ 再 TLS 连 127.0.0.1:443，字节级双向转发
```

`runtime\proxy\simple_tls.py`，纯标准库、约 200 行：

```bat
python runtime\proxy\simple_tls.py
python runtime\proxy\simple_tls.py --log-hosts _launch\logs\game_hosts.txt
```

* 不解析 HTTP、不按 SNI 现签，全程一张证书；
* 明文 `http://` 请求改写绝对 URI 后转发 8081；
* 默认复用 `runtime\web\nginx\conf\ssl\127.0.0.1.pem`。

已用 curl 验证（本机 Kestrel）：

```
HTTPS 经代理 -> GET https://any.host.test/gm   200 (24034 B, GM 控制台页面)
HTTP  经代理 -> GET http://bh3.test/           404 (Kestrel 正常应答)
```

## 五、落地步骤（先 B 后 A）

1. 正常启动服务端（Kestrel 443 + 8081），客户端进到登录界面；
2. `python tools\cert_bypass.py --apply`；
3. 停掉 mitmdump，启动 `python runtime\proxy\simple_tls.py`（系统代理仍指 8891）；
4. 登录，观察：能进大厅即成功；
5. 想彻底去代理：用 `--log-hosts` 跑一次，把域名写进 hosts，然后关系统代理、直连 443。

判据（出问题按这个顺序看）：

| 现象 | 判断 | 处理 |
|---|---|---|
| 客户端立刻报「网络错误 / SSL」 | 补丁没命中 | 回读 crypt32 入口是否为 `ff 25`；是不是管理员权限 |
| 请求根本没到 Kestrel | hosts / 代理端口没生效 | `netstat -ano | findstr :443`；`--log-hosts` 看有没有 CONNECT |
| 部分接口 404/500，TLS 正常 | 只是路由问题，跟证书无关 | 看 Server 日志 |
| 只有某几个域名失败 | 那条链路没走上面两套栈 | 对那几个域名继续用 mitmproxy（混合模式） |

回退：

```bat
python tools\cert_bypass.py --restore
:: 系统代理切回 8891 + mitmdump，证书环境与现在完全一致
```

## 六、风险与边界

* **进程级副作用**：crypt32 补丁对该进程内所有证书校验生效（含更新器、外链）。对本用途可接受，但别在别的程序里复用这个脚本。
* **只在内存**：不落盘、不改 `UserAssembly.dll`，重启即还原；反作弊若做代码段 CRC，风险与现有 6 处静态补丁同级（目前未触发）。
* **不覆盖自建校验**：如果某条链路自己解析证书（不用 CryptoAPI、不用 Mono），补丁无效——用第五节的判据定位，必要时保留 mitmproxy 只接管那一条。
* **别同时开两套**：mitmdump 与 simple_tls 抢 8891 时，Windows 的 `SO_REUSEADDR` 会让两个进程都能 bind，实际由先启动的那个服务（本次调试就踩了：改完代码仍返回旧行为）。切换前先确认端口只剩一个监听者。

## 九、与 ys5.4 天机端的异同（2026-11-04 复核）

复核对象：`D:\ys5.4\5.4.0天机端\补丁\`（4 个文件）与 `D:\ys5.4\GenshinImpact_5.4.0\config.json`。

### 9.1 一句话

**他是「把 TLS 这层整个拆掉」，我们是「留着 TLS、只让它不认证书」。**
前者不需要证书也不需要代理进程；后者必须有一张证书 + 一个 443 端点。

### 9.2 证据

| 他的做法 | 证据 |
|---|---|
| 换掉 SDK 模块 | `补丁\mhypbase.dll` 139 KB / 导出仅 `Initialize` / 内含 `[AntiCheatEMU] Initialize`，替换原版 26 MB（导入 `WINTRUST`、`CRYPT32`） |
| 侧加载 | `version.dll` 17 个导出全转发到 system32，`DllMain` 读 `libraries.txt` = `hk4echeckbypass.dll` + `rsapatch.dll` |
| 改签名 | `rsapatch.dll` 内含 `<RSAKeyValue><Exponent>AQAB</Exponent><Modulus>…` 与日志串 `[*] SDK RSA: key replaced` |
| 改目标地址 | 同 DLL 内含 `serde` 结构 `HttpConfig { proxy_host, proxy_port }`、`http://`、`bal.yuanshen.com` 等域名表；读游戏目录 `config.json`（`127.0.0.1:521`） |
| 明文传输 | 521 是 LunaGC 的 Java HTTP 服务（`encryption.useEncryption=false`、无 keystore），本身不提供 TLS |
| hook 手法 | `iced-x86` + `ilhook` + `patternscan`（Rust），进程内 inline hook |

### 9.3 逐项对照

| 维度 | ys5.4 天机端 | 本项目（本方案） |
|---|---|---|
| 拦截层 | SDK 模块 + 应用层验签 + 传输协议 | 仅 TLS 证书链校验 |
| 传输 | 明文 `http://127.0.0.1:521` | 仍 `https://`，本地 443 |
| 证书 | **零** | 一张固定自签（CN 无关） |
| 代理进程 | 不需要（521 就是服务端） | 需要 443 端点：`simple_tls.py` 或 hosts 直连 |
| 客户端落盘改动 | 4 个 DLL + 替换 26 MB 模块 | 仅 `version.dll` + `bh3bypass.dll`（已有） |
| 补丁时机 | 加载期（DLL 内，早于 SDK 初始化） | 运行期（外部进程写入，晚于启动） |
| 覆盖范围 | 特定模块，范围窄 | 进程内所有 CryptoAPI 校验，范围宽 |
| 回退 | 启动器退出时复原文件 | 内存补丁重启即失效；`--restore` 兜底 |
| 依赖 | 目标游戏有可替换的 SDK 外壳 | 无此前提，只能改判定 |

### 9.4 为什么这套搬不过来

1. BH3 没有 `mhypbase` 这种可整体替换的 SDK 外壳——登录/资源清单都在 `UnityPlayer.dll` + il2cpp 里，换不掉。
2. 客户端的 SDK 基址是 `https://127.0.0.1`（见 9.5 的请求分布），scheme 写死在客户端，服务端改不到；把 URL 改成 http 需要改客户端。
3. 验签对象不同——他改的是 dispatch 响应的 RSA 公钥；BH3 的登录票据校验在服务端会话层，改客户端公钥没有对应收益。

### 9.5 复核（同日晚，按真实请求分布重估）

`_launch\logs\v2_mitmdump.log` 一次完整登录的请求分布：

| 目标 | 次数 | 说明 |
|---|---|---|
| `https://127.0.0.1/*` | **30112** | SDK / MDK / 日志上报 / APM / `query_dispatch` / `device-fp` / `combo` / `mi18n` |
| `http://192.168.0.103/*` | 1205 | nginx 静态（`asset_bundle`） |
| `https://192.168.0.103/com.miHoYo.bh3oversea/*` | **266** | 只有两组：`Audio/Windows/7_0/0/`（133）+ `StreamingAsb/7_0_0/pc`（133） |
| 其它公网 | 300+ | 系统/浏览器的 OCSP、Windows Update、遥测，属于全局代理的副作用 |

结论三条：

1. **证书不是为 80 静态资源服务的**。80 上的 `asset_bundle` 全是明文；TLS 的压力来自 `https://127.0.0.1` 这三万次 SDK/API 调用。
2. 但 127.0.0.1 是 **loopback**：没有 DNS、没有 SNI、不存在「域名/主机名对不上」，只剩「信不信这张证书」一件事——正好是 `cert_bypass` 解决的。
3. 唯一「https 到局域网 IP」的只有那 266 条清单请求，而它的 scheme 是**服务端可控**的（见 9.6）。

### 9.6 `ex_res_use_http`：把 266 条 https 请求变成明文

反汇编 `MoleMole.LAAEAFLEJGE` 的构造函数（`0x181BEE370`）可见：

```
rdx = "ext"                  ; JSON["ext"]
rdx = "ex_res_use_http"      ; JSON["ext"]["ex_res_use_http"]
call AsInt ; cmp eax, 1 ; sete cl
mov byte ptr [rax + 0xC8], cl      ; 存进网关数据类 +0xC8
```

`WwiseAudioManager.GetAudioServerUrl`（`0x1838A72D0`）随后按这个字节选字面量：

```
cmp byte ptr [rax + 0xC8], 0
mov  rdi, "https"        ; 默认
cmovne rdi, "http"       ; ext.ex_res_use_http == 1 → http
```

运行时实测（`tools\_probe_audiourl.py`）：两个槽分别是 `'https'` / `'http'`，格式串为
`{0}://{1}/Audio/{2}_{3}/{4}` 与 `{0}://{1}/Audio/{2}/{3}_{4}/{5}`，当前字节为 0。

⇒ 把 `query_gateway` 的 `ext.ex_res_use_http` 从 `"0"` 改成 `"1"`，音频 / StreamingAsb 清单就从
`https://192.168.0.103/...`（443，无 SNI）变成 `http://192.168.0.103/...`（80，nginx 直出，路径不变）。
连带收益：`StaticProxy`（443→80 反代）与「IP 目标没 SNI」这个历史坑一起消失。

### 9.7 值得借鉴的两点

1. **把证书补丁从「外部写内存」搬进 `bh3bypass.dll`**：与 `rsapatch` 同构——`DllMain` 起线程 → 等 `UserAssembly.dll` / `crypt32` 就绪 → 就地 `VirtualProtect` + 写 14 字节跳板。好处是时机早于任何握手、不需要跨进程句柄（`OpenProcess` / `WriteProcessMemory` 是 ACE 最容易看到的特征），也不要求 Python 与游戏同权限。
2. **配置驱动**：他读游戏目录 `config.json` 决定 `proxy_host/port`；我们的对应物是 `run\*.txt` 开关，思路一致，可把「补丁目标 / 是否启用」也放进 `run\cert_bypass.txt`，避免改代码。

### 9.8 改完之后的拓扑与落地

```
BH3.exe
 ├─ https://127.0.0.1:443        → Kestrel（server.pfx 自签，客户端不校验）   ~30k 次/登录
 ├─ http://<LAN>:8081            → Kestrel（query_dispatch / query_gateway / account / oaserver）
 └─ http://<LAN>:80              → nginx（asset_bundle + Audio + StreamingAsb 索引）
```

可以一并去掉：**mitmproxy、系统代理、`simple_tls.py`、hosts 探测、`StaticProxy`**。
它们的共同目的只是「让客户端接受一张它不认识的证书」，而 `cert_bypass` 已经把这件事从根上解决。

落地顺序：

1. 服务端：`DispatchController.GetExt()` 里 `ExResUseHttp = "0"` → `"1"`（建议配 `run\ex_res_http.txt` 开关，缺省 1、写 `0` 关闭）；重启服务端 + 重新登录。
2. 客户端：`python tools\cert_bypass.py --apply`。
3. 去掉系统代理（`HKCU\...\Internet Settings` 的 `ProxyEnable`），确认三方都通：
   * `netstat -ano | findstr :443` 只剩 Kestrel；
   * 登录日志不再出现 `https://192.168.0.103`；
   * `nginx` access.log 出现 `/com.miHoYo.bh3oversea/Audio/...`。

风险与判据：

| 现象 | 判断 | 处理 |
|---|---|---|
| 卡「下载活动资源失败」 | 音频清单仍走 443，或 nginx 未覆盖该路径 | 看 `--log-hosts`；确认 `ex_res_use_http` 已生效（可临时用信箱读 +0xC8） |
| 登录卡在 SDK 校验 | 某条 https 链路不走 crypt32（自建 TLS 栈） | 保留 mitm 只接管该域名（混合模式），其余直连 |
| 视频/字幕 404 | `ex_resource_url_list` 也吃这个开关，指向 `/tmp/...` | nginx 补 `location /tmp/`，或该列表保持不带 scheme 的原样 |

## 十、迁移实测（2026-11-04 19:20–19:40，已跑通）

### 10.1 结论：最终形态既不是代理，也不是内存补丁

按第九节的计划切到 `ex_res_use_http=1` 之后，静态资源已经全部走 80 明文，
但客户端仍然登不上。逐层排查后，真实链路是三件事叠加：

| 现象 | 真因 | 证据 |
|---|---|---|
| `Cannot resolve destination host` | Global Dispatch 域名 `global01.os.honkaiimpact3.com` 在公网已是 **NXDOMAIN** | `nslookup` 返回 Non-existent domain；DNS 探针抓到客户端在查它 |
| 改完 hosts 后弹出**官方**登录界面 | SDK 走的是 `*.hoyoverse.com` 一族（`bh3-sdk-os`、`sdk`、`api-account-os`、`account`、`webstatic`…），这些域名公网可解析，于是直连官方 | DNS 探针 19:33:50–19:34:03 的查询序列 |
| 客户端报 `Unknown Error` / `Request timeout`，服务端 443 一条日志都没有 | 校验由 **schannel 内部**完成，不走应用的 `crypt32!CertVerifyCertificateChainPolicy`，`cert_bypass` 的主补丁打不到 | 系统日志 Schannel **36882**（不受信任的 CA）、**36884**（证书不含预期的名称 `global01.os.honkaiimpact3.com`） |

第三条是关键：**UnityPlayer 导入了 `CertVerifyCertificateChainPolicy`，但实际握手路径没调用它**。
补丁写进去了、字节也验过（入口 `ff25` → code cave `4d85c9…c3`），照样握手失败。
这也顺带证伪了原方案里"关掉链校验就能免证书"的假设——对这条路径不成立。

## 十二、免登录 + 零外网收口（2026-11-04 20:20–20:40）

### 12.1 先纠正一个误判：登录框不是网页

启动后看到的 HoYoverse 登录框（账号/密码/「进入游戏」）是 **SDK 自己用 Unity 画的原生面板**，
不是 WebView。判据：

- 没有地址栏、没有滚动条、没有网页文字排版，弹窗直接叠在游戏场景上；
- 点击「进入游戏」时服务端日志是 `POST /bh3_os/mdk/shield/api/login`（本机接口），
  不是从 `account-pre.hoyoverse.com` 拉页面。

所以「缓存 WebView 到本地域名」对它无效 —— 没有页面可缓存。真正的闸门在 `verify` 接口。

### 12.2 闸门：`/mdk/shield/api/verify` 返回了 null

SDK 启动时拿本地缓存的 token 调 `verify`：

| 情况 | 服务端行为（改前） | SDK 表现 |
|---|---|---|
| token 在库里 | 返回账号 | 自动登录，直接进游戏 |
| token 不在库里 | `retcode=0` 但 `account=null` | 判定「未登录」→ 弹原生登录面板 |
| 本地没有缓存 token | 根本不调 `verify` | 直接弹面板 |

改动：`AccountController` 增加**宽容模式**——`verify` 认不出 token 就回落到
`server-v2\run\default_uid.txt` 指定的账号（缺省 `1002`），并带上库里该账号的真实 token。
`shield/api/login` 同理：面板里填任何用户名都落到这个账号（只查不建，避免顶掉主号数据）。

```bat
echo 1002 > server-v2\run\default_uid.txt   :: 指定回落账号
echo 0    > server-v2\run\default_uid.txt   :: 关闭宽容模式，恢复必须登录
```

日志里会有 `[SDK-LOGIN] 宽容登录：verify 未命中 token=…，回落 uid=1002`。

### 12.3 原先放过的那三类域名，现在也拦

### 12.5 登录态为什么要「快照 + 回灌」

实测：宽容模式只解决「SDK 调了 verify 但 token 不认」这一种情况。
如果本地压根没有缓存账号，SDK 启动时**根本不调 verify**，直接弹原生面板（日志里
只有 `loadConfig / getConfig / compareProtocolVersion`，没有 `verify`）。

登录态实际压在 Unity PlayerPrefs（`HKCU\Software\miHoYo\Honkai Impact 3`）的四类值上：

| 值 | 作用 |
|---|---|
| `MIHOYOSDK_ADL_PROD_OVERSEA_h…` | 已保存账号列表，DES 加密，**绑设备指纹** |
| `GENERAL_DATA_V2_Account_h…` | 当前账号 `{uid, token, …}` |
| `GENERAL_DATA_V2_LastLoginUserId_h…` | 上次登录 uid（DWord） |
| `MIHOYOSDK_DEVICE_FP_h…` | 设备指纹，ADL 的解密素材 |

坑在于 **ADL 和指纹必须配对**：SDK 每次登录都可能重写指纹（实测 `5369174356` → `6132610721`），
指纹一变，旧 ADL 就解不开 → 又变回"没登录" → 弹面板。加上服务端重启会让客户端掉线、
掉线后 SDK 会清账号，所以登录态经常"掉"。

做法：不解密、不伪造，只是把**同一台机器、同一指纹下的同一份密文**存下来再放回去。

```bat
python tools\sdk_login_state.py --save     :: 登录成功后拍快照（存 _launch\logs\sdk_login_state.json）
python tools\sdk_login_state.py --check    :: 对比当前值 vs 快照，看登录态有没有被清
python tools\sdk_login_state.py --apply    :: 回灌（要求游戏没在跑）
```

回灌已经接在两条链上，都是「游戏启动前」这个唯一有效的窗口：

- `启动服务端v2.bat` → `launch_v2.py start` → 起完 Server.exe 后自动 `--apply`
- `启动游戏.bat` → `launch_game.py` → 拉 BH3.exe 之前自动 `--apply`

`启动游戏.bat` 是新增的一键入口：按需起服务端（带 `--no-proxy --no-mitm`）→ 回灌登录态
→ 起客户端 → 等 `UserAssembly.dll` 加载后打刻晴补丁。

> 换号 / 重装后：手动登录一次，然后跑一次 `--save` 更新快照。

### 12.6 启动流程（最终版）

#### A. 日常启动 —— 只认一个入口：`启动游戏.bat`

```
双击 启动游戏.bat
  ① 服务端没在跑？→ 起 nginx + Server.exe（--no-proxy --no-mitm）；已在跑就跳过
  ② 回灌登录态 → 写回 PlayerPrefs 四件套（ADL 与设备指纹成对写入）
  ③ 拉起 BH3.exe
  ④ 等 UserAssembly.dll 加载 → 打刻晴内存补丁
→ 直接进舰桥，没有 HoYoverse 登录框
```

顺序不能反：**服务端先于客户端**。服务端中途重启会让客户端掉线，
掉线后 SDK 会清账号，下次启动就又弹面板。「已在跑就跳过」正是为了避开这点。

#### B. 为什么不能直接双击 BH3.exe

SDK 只在进程启动那一刻读 PlayerPrefs；游戏退出时又会把内存里的状态写回注册表。
所以回灌只能在「游戏没跑」的窗口做。`launch_game.py` 里 `game_running()` 为真时直接跳过回灌，
不会破坏正在跑的会话。

当前注册表本身是登录态时，直接点 BH3.exe 通常也能进；但一旦掉过账号就没有兜底，
所以统一走 bat。

#### C. 真正的「首次」（新机器 / 重装 / 删了注册表）

快照**不能跨机器复制**：ADL 用设备指纹派生密钥，换机解不开。首次必须手登一次。

```
1. 双击 启动服务端v2.bat               起 nginx + Server.exe
2. 直接双击 BH3.exe                    （没有快照，回灌会跳过并提示）
3. 弹出的 HoYoverse 面板里随便填账号密码
      服务端 shield/api/login 只查不建，落到 run\default_uid.txt 指定的账号（缺省 1002）
4. 进游戏后关掉（让 PlayerPrefs flush）
5. tools\python\python.exe tools\sdk_login_state.py --save
      → 生成 _launch\logs\sdk_login_state.json
6. 以后只用 启动游戏.bat
```

#### D. 故障对照

| 现象 | 判据 | 处理 |
|---|---|---|
| 又弹登录框 | `--check` 显示 Account/ADL 被清 | `--apply` 回灌；仍不行就重走 C |
| 登录框变成「本地模式」说明页 | 说明访问的是 `account-pre` 说明页 | 正常降级，不是错误 |
| 进游戏后掉线 | 服务端被重启过 | 关客户端，用 `启动游戏.bat` 重开 |

`RemoteAddress=Internet` 只含「非本地子网」，所以 `127.0.0.1:443`（SDK/游戏）和
`192.168.0.103`（LAN）不受影响；CEF 子进程也是 BH3.exe，同样受管。

删除该规则即恢复联网（`Get-NetFirewallRule <名字> | Remove-NetFirewallRule`）。

#### 顺带确认的登录语义

`shield/api/login` 是**只查不建**（`FirstOrDefault(d => d.Name == ...)`），
不用 `User.FromName`（它会为陌生名字现场建号，把主号顶成空白号）。
查不到就回落 `run\default_uid.txt`（缺省 1002）。所以：

- 输库里已有的名字（如 `1` 对应 1002）→ 直接用那个号；
- 输任意陌生名字 → 仍然进 1002；
- **不校验密码，不建新号，不生成新 token**（Users 表没有密码列）。

#### 12.7.1 两个后续发现（21:00）

**（1）回灌从来没生效过一次**

`启动游戏.bat` 打印 `[!] 登录态回灌失败` 并抛 Traceback，根因：

```python
_, have, _ = winreg.QueryValueEx(reg, name)
# QueryValueEx 只返回 (value, type) 两个值 -> ValueError: not enough values to unpack
```

改成 `have, _have_kind = ...` 后逻辑全通（回灌 ADL + 指纹两项）。

含义很重要：**此前「用 bat 启动就能免登录」是假象** —— 那些成功的启动靠的是注册表里
本来就有登录态，不是回灌的功劳。修复前 `--apply` 每次都在写第一项前就崩了。

**（2）防火墙规则建了，但 Private 配置文件整体关闭 -> 规则不参与匹配**

```
Get-NetConnectionProfile     以太网 -> Private
Get-NetFirewallProfile       Domain=True  Private=False  Public=True
```

规则本身是 `Outbound / Block / Enabled / Profile=Any`，但配置文件关着时任何规则都无效，
所以采样里仍漏出 `18.65.14.62`（CloudFront 同段）。

```text
Set-NetFirewallProfile -Profile Private -Enabled True
```

开启后连续 6 次采样：公网 0 条，只剩 `127.0.0.1`、`192.168.0.103`。

副作用：入站默认阻止。**本机访问不受影响**（loopback 不经过防火墙过滤），
但局域网内其他设备访问本机 80 端口会不通。需要时单独放行：

```text
New-NetFirewallRule -DisplayName 'BH3 nginx 80 LAN' -Direction Inbound -Action Allow `
  -Protocol TCP -LocalPort 80 -RemoteAddress LocalSubnet -Profile Private
```

#### 12.7.3 防火墙已还原（2026-11-04 21:30，按用户要求）

用户要求「还原我的防火墙」，已恢复成改动前的状态：

```
删除  BH3 block internet outbound   出站阻断规则
恢复  Private 配置文件 Enabled = False   （改动前就是关着的）
保留  Domain / Public = True            （原本如此，未动）
```

当前状态：

| 项 | 值 |
|---|---|
| Domain / Private / Public | True / **False** / True |
| BH3 相关规则 | 无 |

**这意味着「零公网」现在只靠 hosts 那一层。** 代价是明确的：

- hosts 是域名层拦截，对「运行时拼接的域名」和「直接走 IP」的请求无效；
- 之前实测就漏过 `18.65.14.62`（CloudFront，`sg-public-api.mihoyo.com` 解析结果）这种；
- 51 条域名清单覆盖的是已知集合，不保证穷尽。

如果之后发现又漏公网，两条路可选（都不改系统设置）：

1. 跑一次 `Get-DnsClientCache | ? Entry -match 'hoyoverse|mihoyo|honkai|bh3'`，
   看有没有解析到非 `127.*` 的，把域名补进 `tools/migrate_to_hosts.py`；
2. 重新加回那条出站规则（**只需要规则，不需要开 Private 开关**是行不通的 ——
   配置文件关着时规则不参与匹配，两者必须同时具备）。


## 十三、一键 vbs 链路更新（2026-11-04 21:20）

`一键启动.vbs` / `一键停止.vbs` 本身没改 —— 它们只负责 ShellExecute(runas) 提权，
再调 `_launch\launch_all.py start|stop`。变的是 launch_all.py 内部：
它还是 10/31 的 mitmproxy 版本，直接跑会把中间人和系统代理重新拉起来。

### 13.1 改了什么

| 位置 | 改前 | 改后 |
|---|---|---|
| `stack_args()` | `no_proxy=False` → 起 mitmdump、改系统代理 | `no_proxy=True, no_mitm=True` |
| 服务端端口判据 | 80 / 443 / 8081 / **8891** | 80 / 443 / 8081（8891 已废弃） |
| 第 6 步 | 等 mitmproxy 生成 CA 并装进 Root | `cert.pem` 存在 + `CN=bh3-local` 在受信任根 + hosts 标记块 |
| 第 7 步 | — | 新增「登录态回灌」：`sdk_login_state.py --apply` |
| 停止 | 按 `--keep-proxy` 决定是否恢复系统代理 | 恒 `keep_proxy=True`，**不动系统代理** |
| 收尾 | 永远 `input()` 等回车 | 成功 5 秒自动关，有 `[FAIL]/[WARN]` 才停住 |

`cert_trusted()` 也从「找 mitmproxy CA」改成「找 `CN=bh3-local`」，
`check_host()` 不再因为环回地址提示装 CA —— 环回现在是原生支持的。

### 13.2 启动时序（vbs → launch_all）

