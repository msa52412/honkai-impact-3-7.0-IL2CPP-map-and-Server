## 1. 层数问题

### 1.1 现象与证据

量子盘是 **20 场连打**（100031 的 splits 顺序）：

```
M10000 M10100 M10200 M10300 B10
M10400 M10500 M10600 M10700 B11
M10800 M10900 M11000 M11100 B12
M11200 M11300 M11400 M11500 B13   ← 第 20 场，最终 BOSS
```

两处失败：

- **第 6 场起不刷怪**：进关后地图空着，没有怪也没有门。
- **第 20 场不刷 BOSS**：地图、小怪都正常，唯独关底 BOSS 不出现。

客户端日志 `%LOCALAPPDATA%Low\miHoYo\Honkai Impact 3\output_log.txt` 里只有一条 Lua 异常，且只属于第 20 场：

```
QuantumEndlessCommon.lua.txt:283: invalid arguments to method:
  LevelDesignManager.StartAutoChangeLevelScoreByTime: 1477286120
  at loadMonster -> QuantumEndless.lua:72 Func -> do_wave -> do_waves -> section_process
```

第 6 场没有异常，是**静默**失败——难度索引越界后关卡没有对应配置，就不刷。

### 1.2 根因

反编译 `loadMonster.luac`（Lua 5.1）得到常量表，能直接看到写死的两个数：

```
17:'ChangeHardLevel'  18:15.0
41:'IsLastMonsterGroup'  42:1
```

- **第 6 场**：`MonsterGroupIndex` 是 1-based，第 5 场 `5+15=20` 刚好；**第 6 场 `6+15=21`**，难度只定义到 20，越界。
- **第 20 场**：`IsLastMonsterGroup == 1` 分支里调 `SetOWEndlessLevelScoreMode` 与 `StartAutoChangeLevelScoreByTime`。这两个是 **Lua 与 C# 版本错配**：Lua 按旧签名传参，C# 按新签名绑定，直接抛 `invalid arguments`。异常发生在 `section_process` 协程里，协程整个死掉 → 后面的刷怪步骤一个都不执行。

### 1.3 修法（客户端侧）

#### #1 层数越界：包一层 ChangeHardLevel

`_ext/tools/qt_watch.py` → `PATCH_HL`（第 120 行起）：

```lua
local i = tonumber(index)
if i and i > 20 then i = i - 15 end   -- 21→6, 22→7 … 35→20
if i and i > 20 then i = 20 end       -- 兜底
if not i or i < 1 then i = 1 end
return orig(i)
```

**为什么减 15 而不是直接钳到 20**：钳死会让第 6~20 场全部用同一套难度，血量/攻击都不对。减 15 才能让每场拿到各自独立的难度。

**作用域闸门（必做）**：迪拉克、主线也用 `ChangeHardLevel`，全局改会污染。所以包装里加两道：

```lua
if _G.QuantumEndlessPlugin == nil then return 'nordy' end   -- 不是量子场景，整组收工
local function inqt()
  local ok, i = pcall(debug.getinfo, 2, 'S')
  local s = ok and type(i) == 'table' and (i.source or '') or ''
  if s == '' or s == '=[C]' then return true end            -- 拿不到就当量子，宁可放过
  return string.find(s, 'QuantumEndless', 1, true) ~= nil
end
```

调用者不是 `QuantumEndless*` 就原样 `return orig(index)`。`PATCH_HL` 返回 `nordy` 时，`apply_patch()` **必须整组收工**，后面四段一段都别发——否则元表会被劫持到迪拉克上，13:05 的主线程卡死就是这么来的。

#### #2 第 20 场不刷 BOSS：劫持元表置空

`PATCH_BOSS1`（第 143 行起）。`LevelDesign` 在 Lua 里可能是 table 也可能是 userdata，两种都要处理：

```lua
local ld = _G.LevelDesign
if type(ld) == 'table' then ld.StartAutoChangeLevelScoreByTime = function() end return 'tbl' end
local meta = getmetatable(ld) or debug.getmetatable(ld)
local oldix = meta.__index
_G.__qt_boss_raw = function(key) ... end        -- 存下原始方法的取用入口

meta.__index = function(tbl, key)
  if tbl ~= ld then return oldix(tbl, key) end  -- ← 必须判，元表会被同类 userdata 共享
  if key == 'StartAutoChangeLevelScoreByTime' then return function(self, ...)
    local fn = _G.__qt_boss_raw(key)
    if fn ~= nil then pcall(fn, self, ...) end  -- pcall 吞掉 invalid arguments
    if _G.__qt_extra then pcall(_G.__qt_extra, self) end
  end end
  if key == 'QTEndlessUpdateBattle' and _G.__qt_upd ~= nil then return _G.__qt_upd end
  return oldix(tbl, key)
end
```

关键点：

- **不能直接置 `nil` 或 `function() end`**：这个方法还兼着「最后一层额外分 HUD」的显示职责，全砍掉额外分就永远不出现。正确做法是 `pcall` 调原函数（异常被吞），再跑我们自己的显示回调。
- **`tbl ~= ld` 必须判**：LuaInterface 的元表在多类型间共享，不判会拿 LevelDesign 的 self 去调别的 C# 对象 → 崩。

### 1.4 修法（服务端侧）：全通后停在最后一层

`OwEndlessState.Align()`（第 340 行起）原来写的是：

```csharp
if (SplitIndex > splits.Length) SplitIndex = splits.Length;
CurGroupId = SplitIndex < splits.Length ? ... : 0;   // 全通 → 0
```

全通后 `cur_monster_group=0`，配合 `BuildGroupList` 把 20 个组全标 `progress=10000`，客户端地图上一个可挑战节点都没有，表现为「最后一层不能反复打」。改成：

```csharp
if (SplitIndex >= splits.Length) SplitIndex = splits.Length - 1;   // 光标停在最后一场 BOSS
CurGroupId = OwEndlessConfig.ReportedGroupId(type, battleConfigId, splits[SplitIndex]);
```

`Advance()` 里同理，`nextGroup` 扫不到未完成组时回落到最后一组：

```csharp
if (nextGroup == 0u && splits.Length > 0)
    nextGroup = OwEndlessConfig.ReportedGroupId(type, battleConfigId, splits[splits.Length - 1]);
```

`BuildGroupList(..., bool forceCurrentPlayable = false)` 新增开关：

- `true` —— 只有 **3419**（`GetOpenworldEndlessDataReqHandler.cs:304`）传。当前组一律按 `cur` 下发，即使已在 `FinishedGroups` 里，这样最后一场 BOSS 一直可打。
- `false` —— **3425**（`FinishOpenworldEndlessMonsterGroupReqHandler.cs:113`）保持原逻辑。刚打完的组仍标 10000，否则客户端结算弹窗按 `progress>9999` 找不到刚完成的组会空转（历史坑，别改）。

另外 BOSS 场的占位 id（`split.GroupScoreId`）在 `forceCurrentPlayable` 且命中当前组时**不标记完成**，避免区域级 `allBattleFinished` 仍为 true。

### 1.5 改进度的坑

`OwEndlessState` 是「进程内 `ConcurrentDictionary` + 落盘」：

- `EnsureLoaded()` 有 `_loaded` 一次性开关，**手改 `abyss_state.json` 不会被重读**；
- `Reset()` 只删 Store 条目，下次 `Get()` 新建全 0 状态，**也不重读文件**。

所以想改进度必须**重启 Server.exe**：

```bash
app/tools/python/python.exe app/_launch/restart_server.py --only-stop
# 改 run/data/abyss_state.json（先备份 .bak-<时间>）
app/tools/python/python.exe app/_launch/restart_server.py --only-start
```

`CurGroupId` 是 `Align()` 由 `SplitIndex` 推出来的，**改 `SplitIndex` + `FinishedGroups` 就够，不用手填 CurGroupId**。

## 2. 计时器问题

### 2.1 两行 Lua 都错（版本错配）

`QuantumEndlessCommon.lua` 第 282~283 行：

| Lua 调用 | C# 实际签名 | 错在哪 |
|---|---|---|
| `SetOWEndlessLevelScoreMode(true, false, 'OWEndless_ExtraScoreText')` | `(bool show, bool playAnim, string textmap, bool isExtra)` | 少传 `isExtra` → 额外分显示模式没打开 |
| `StartAutoChangeLevelScoreByTime(1000, -1, 0.3, 0)` | `(long initScore, float durationTime, long finalScore)` | 多传 1 个 → `invalid arguments` |

额外分那条是另一个方法，签名正常：

```csharp
StartAutoChangeLevelExtraScoreByTime(long initScore, long finalScore, float durationTime)
```

### 2.2 为什么不能「只把实参改对」

实测本版 `StartAutoChangeLevelScoreByTime` 是**静态赋值，不是动画**：

```
StartAutoChangeLevelScoreByTime(1000, 4, 0)  →  3 秒后 GetLevelScore() 仍是 1000
```

也就是说它没有「按时间衰减、中途可读」的语义。把实参改对只会让结算面板永远显示 1000，并把这个 1000 当成额外分送给服务端——从「显示 0」变成「错报 1000」，更糟。

所以走**四段补丁**，逐层把分补出来。

### 2.3 四段补丁

| 段 | 名称 | 职责 |
|---|---|---|
| `PATCH_BOSS1` | 元表劫持 | 存 `__qt_boss_raw`；截获 `StartAutoChangeLevelScoreByTime` / `QTEndlessUpdateBattle` |
| `PATCH_BOSS2` | `__qt_extra` | 读 `_ext/tmp/qt_extra.cfg`（`off`/`down`/`up`），`down` = `StartAutoChangeLevelExtraScoreByTime(1000, 0, 300)`，HUD 从 1000 倒数 |
| `PATCH_BOSS3` | `__qt_upd` | 拦 `QTEndlessUpdateBattle(bi, prog, ex, ...)`——Lua 唯一把额外分交给 C# 的出口，原来恒传 0 |
| `PATCH_BOSS4` | `__qt_fixscore` | 结算面板补分（`GetLevelScore()` 为 0 才写），并在每场开局清 C# 侧残留 |

`__qt_upd` 的取值优先级：

```
入参 ex > GetLevelExtraScore() > 按 os.time() 本地推算(1000 * (1 - t/300)) > 保持原值
```

并写 `_ext/tmp/qt_finish.log`：

```
13:01:55 bi=20 prog=10000 in=0 out=942 src=cs lv=942
```

`src` 字段用来判断分从哪来（`in`/`cs`/`calc`），`lv` 是面板实际拿到的值——排障先看这一行。

### 2.4 三个必须记住的坑

#### 坑 1：C# 方法在 Lua 里是 userdata，不是 function

LuaInterface 把成员方法暴露成 `LuaFunction`（有 `__call`），`type(x) == 'function'` **恒为假**。所以下面这段以前一次都没执行过：

```lua
if type(ld.StartAutoChangeLevelScoreByTime) == 'function' then ... end   -- 永远不进
```

正确写法：

```lua
if x ~= nil then pcall(x, self, ...) end   -- pcall 支持 __call，userdata 可以直接 pcall
```

#### 坑 2：C# 侧的值不随 lua_State 重建清零

每场都是新的 `lua_State`，但 `GetLevelExtraScore()` / `GetLevelScore()` 是 C# 侧字段，**会带上一局的值**（实测空房间读到残留 871）。

后果：如果每场都无条件读它，**普通层也会白送一次残留额外分**。所以：

- `__qt_upd` 里读它必须加 `_G.__qt_t0 ~= nil` 守卫（只有 `__qt_extra` 真启动过计时器才读）；
- `PATCH_BOSS4` 在每场首次打补丁时 `SetLevelScore(0)` + `SetLevelExtraScore(0)`，用全局 `__qt_rst` 标记「本状态已清过」，防止重试补丁把战斗中途的分抹掉。

#### 坑 3：参数方向别猜

```
(1000, 0, 300)  → GetLevelExtraScore() = 1000 ✅
(0, 1000, 300)  → 返回成功，但恒为 0     ❌ 极具迷惑性
```

`initScore` 在前、`finalScore` 在后，`down` 模式就是 1000 起、300 秒衰减到 0。

## 3. 注入侧通用铁律

这几条不是量子专属，任何往游戏 Lua VM 里写东西的场景都适用。

### 3.1 绝不能 `lua_settop(L, 0)`

补丁在**游戏主线程**的信箱里执行。如果此刻主线程正在同一个 VM 里跑 `loadMonster` 协程，`settop(L, 0)` 会把 `top` 按回 `base`，**等于把游戏自己的调用栈整段清空**；之后游戏再压栈/补 nil，写入地址就跑到栈外。

崩溃特征（两次，13:31:55 / 13:35:15，不同进程同一偏移）：

```
ulua.dll + 0x26f8a4   0xc0000005
```

反汇编 `ulua.dll` 确认：`0x26f880 = lua_settop`，崩溃点 `0x26f8a4` 是 `mov dword [rax+8], 0`，`rax = [L+0x10] = L->top`——正是 `lua_settop` 里「把栈补到 base+idx」的补 nil 循环。结构偏移：`L+0x10 = top`，`L+0x18 = base`。

**修法**：

- 调用前不动栈（删掉 `settop(L, 0)`）；
- 调用后只 `settop(L, -2)`（负数走 `top += idx+1`，等价弹 1 个），只弹掉 `lua_dostring` 的返回值；
- 加 `L_sane(h, L)` 前置校验：读 `L+0x10/0x18`，要求 top/base 非空、16 字节对齐、`0 <= top-base <= 0x200000`。不自洽就一个字节都不写。

一句话：**补丁只能「压一个、弹一个」，绝不能改动游戏原有的栈高度。**

### 3.2 `I.S()` 传字符串必须自己补 NUL

`icall._mkstring` 把 `Il2CppString` 写进 scratch 时，只在 `0x14 + len*2` 不是 8 的倍数时补零。**正好 8 对齐时没有终止符**，而 `lua_dostring` 的入参按 C 字符串读（`strlen`），于是读穿到 scratch 里上一个更长的字符串尾巴。

症状很有迷惑性：报 `'<eof>' expected near 'xxx'`，且**行号比脚本实际行数还大**（14 行的补丁报 `:19`）。之前误判成「chunk 长度上限」，其实是这个。

修法：`_send()` 里写 `I.S(code + "\x00")`，显式补 U+0000（UTF-16 是 `00 00`，C 侧 `strlen` 正好停在这），从此与长度/对齐无关。

### 3.3 信箱地址是按进程的，pid 变了必须先重装

`icall` 的 state 文件里存的是**上一个进程**的 pid + scratch/mailbox/stub 绝对地址。新进程直接拿旧地址写 = **把 il2cpp 的堆写坏**。

崩溃特征：`UserAssembly.dll 0xc0000005`，`Read from location ffffffff`，栈顶在 `LevelDesignManager:CreateLDEventFromTable ← LevelDesignStart`（加载关卡阶段）。

修法：`mailbox_ready(pid)` 检查 state 的 pid 是否等于当前进程且 `string_klass` 存在；不匹配就 `ensure_mailbox(pid)`，装不上就 `return 2`，**装好之前一个字节都不发**。安装本身是安全的，危险的只有「发送」。

### 3.4 健康检查要只读，不能重跑整组补丁

lua 脚本重载会把包装和元表劫持整个冲掉（实测同一个 L 两分钟内从 `already` 变回 `ok`）。但**不能靠每 15 秒重跑 5 段来修**——那是 15 次 `lua_dostring`，把 3.1 的风险放大了 5 倍。

改成 `PATCH_PROBE`：一条只读 Lua，返回 5 字符掩码

```
ChangeHardLevel 包装 | 元表劫持 | 结算拦截 | 补分 | 额外分
```

全在就一个字节都不写；缺了才整组补，补完 45 秒内不再探。间隔 `HEALTH_EVERY = 20.0` 秒。

## 4. 操作手册

### 4.1 开关补丁

补丁**只在打量子时开**。开机常驻会让守护每 0.2s 探测 `g_lua_state`，而客户端切场景/切界面会重建 `lua_State`，在那个窗口写内存就是 `ulua.dll` 崩溃。

GM 页面：左侧「量子深渊修复」→ 启动 / 停止 / 看日志，接口是 `/gm/api/patch/{status,start,stop}`。

```bash
curl -s http://127.0.0.1:8081/gm/api/patch/status
curl -s -X POST http://127.0.0.1:8081/gm/api/patch/start
curl -s -X POST http://127.0.0.1:8081/gm/api/patch/stop
```

手工起：`app/tools/python/python.exe _ext/tools/qt_watch.py`

### 4.2 补丁撤不回，切模式要重启客户端

补丁改的是当前 `lua_State` 的全局表和 `LevelDesign` 元表，**停止守护不会撤销**，只有重启客户端才干净。所以：

> 打完量子要玩迪拉克/主线等其他模式，**先重启客户端**。

`_ext/tmp/qt_patch.dirty` 里记着被打过补丁的 pid，`/patch/status` 的 `dirty` 字段据此判断「补丁是否还在内存」（pid 与当前 BH3.exe 不一致就算客户端已重启，自动清理印记）。

### 4.3 每场都是新 VM

守护必须**全程开着**。中途停掉，下一场就没有补丁（第 6 场越界、第 20 场不刷 BOSS 立刻复现）。

### 4.4 排障顺序

1. `_ext/tmp/qt_finish.log` —— 看的 `src` 和 `lv` 字段，确认分从哪来。
2. 守护日志 —— 每段返回码，`already|already|down|ok|ok` 是正常态。
3. 客户端 `output_log.txt` —— 搜 `LuaScriptException`，这是「地图能进但没怪」的第一现场。
4. 服务端 `_launch/logs/v2_Server.log` —— 搜 `BattleEnd` / `[Abyss]`，看 group、layer、status（`1`=WIN，`3`=全灭）。
