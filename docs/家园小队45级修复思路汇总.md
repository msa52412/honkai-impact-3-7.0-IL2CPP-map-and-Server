# 家园小队45级修复思路汇总

整理日期：2026-11-08。对象为本地BH3 7.0服务端，目标账号UID 1002。用户已于2026-11-03重新登录验收“已显示45级”。

## 1. 问题根因

正常入口是“舰桥 → 右下角家园 → 左下角家园小队”。它使用 Adventure 系列页面和3900/3901协议，并不读取此前尝试修改的活动 Sanctuary 数据。因此只把 Sanctuary 存档和配置改成45，或安装旧活动界面的刷新入口，都不能修好正常家园页面。旧刷新函数执行计数为0，说明没有命中实际页面。

第二个问题是协议模型落后于7.0客户端：服务端旧生成模型把tag 2命名为Level，但7.0客户端将tag 2当作old_level。第一次只把45写进这个旧字段，经验显示和弹窗恢复，当前等级仍为1。

## 2. 如何确认数据源

只读追踪MainUI页面堆栈，确认家园主页为AdventureMainPageContext，小队详情为AdventureEffectDetailPageContextV2；其模块数据由GetAdventureGroupRsp更新。最初服务端缺少GetAdventureGroupReq处理器，客户端保留默认等级。

核对7.0原生Proto读取函数，确认字段为：

| 字段编号 | 7.0含义 | 修复值 |
| --- | --- | --- |
| 2 | old_level，旧等级 | 兼容旧模型保留 |
| 18 | level，当前等级 | 45 |
| 19 | badge，徽章数据 | 0 |
| 20 | extra_badge_cost_num | 0 |

关键是补齐当前等级tag 18，不能仅按旧模型的属性名判断实际线协议。

## 3. 最终实现

服务端新增GetAdventureGroupReqHandler处理请求3900，调用AdventureGroupService构建3901响应。按账号读取server-v2/run/adventure.json；UID 1002设为45，未配置账号默认1，等级限制在1～45。

配置每次请求读取，后续修改等级配置不用重新编译。响应既保留旧模型兼容字段，也通过protobuf-net的IExtensible扩展写入18、19、20，避免手改生成的Common协议文件。当前配置：

```json
{"player_levels":{"1002":45}}
```

当时先以AdventureGroupHook.dll启动扩展补齐缺失处理器，启动器仅为Server.exe配置DOTNET_STARTUP_HOOKS。2026-11-04完整服务端构建已把处理器和服务编入Server.dll；扩展检测到内置处理器会直接返回，避免重复注册。配置文件和源码均保留。

原活动Sanctuary全局配置已还原；旧客户端页面刷新补丁不再参与最终方案。

## 4. 部署和验证

部署脚本检查无在线玩家，确认8081端口对应本项目Server.exe，备份SQLite，再替换扩展并重启服务端。离线后再重启，是为了先保存装备、词缀等在线缓存。

原修复通过12项协议、账号隔离、序列化及7.0字段验证，最终由用户重新登录确认45级。正常使用本项目启动器会加载已有服务端修复，无需每次启动游戏运行VBS。

此次确认的是等级和页面显示；没有代领等级奖励，也没有把截图里的占位属性数值写成家园加成，未逐项验证所有属性加成和奖励。
